# Ghostty

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only Ghostty does.

## Gotchas

- A Ghostty tab whose shell is not at its prompt — Claude Code, vim, ssh, a dev server — cannot hear its focus, so bringing it to the front left the last tab's picture over its colors until its next prompt (parity's `focus-busy`). On macOS Ghostty names the terminal in front through AppleScript (the front window's selected tab's focused terminal, whose `tty` and `pid` — the foreground process — are on main after 1.3.1), so every Ghostty tab records what it wears in `$XDG_STATE_HOME/ttheme/ghostty/<tty>` — its pid, the default it wore it under, its palette (`-` for a tab that leaves the picture alone), its `$TTY` and `painted` while `TTHEME_PAINTED` is set — from every prompt (`__tt_prompted`), paint and reset (`__tt_worn`, but not the hovers preview paints in raw mode) and claim (`__tt_shown`), and one follower per Ghostty session (`__tt_ghostty_follower`, a `zsh -f` sourcing the layer, kept single by a `zsystem flock` on `ghostty/.follow` and started by any prompt that finds it gone) asks Ghostty which terminal is in front and puts up that tab's record when `shown.conf` names another, busy or idle; a record made under another default puts up the new default's picture when the tab never painted (it shows the default Ghostty's reload gave it), a record made before ttheme went off takes the picture down (`__tt_shown ""` forced) and, for a tab whose foreground process is not its shell, resets its colors (`__tt_ghostty_unpaint`: the one reset sequence `__tt_osc_reset` sends, written once to the record's `tty` from outside, then the record rewritten with no startup and no palette so it is never written again — a tab running a program has no prompt to do it at; measured in a sandbox Ghostty, where a second process writing to a painted tab's tty took its background back to the default). It also asks once whenever `palettes.zsh` or the pins file moves, so a default or a pin changed in another terminal while Ghostty sits behind it reaches the picture of Ghostty's front tab — whose idle shell the wake has already moved, while Ghostty, behind, gave none of them focus to claim with (parity's `default-beside`). Otherwise it asks (`__tt_ghostty_ask`, one `osascript` of about 0.1 s) only on a sign that focus moved, polled every 0.1 s with `zstat`: a recorded tty's atime moved (macOS stamps a tty's atime in nanoseconds whenever its foreground program reads, so a program that turned focus reporting on — Claude Code does — marks its tty the moment its tab comes to the front), a tab at its prompt lost focus (`__tt_blur` touches `ghostty/.blur`), or the tab in front took input and then went quiet for 0.3 s — at most every 2 s while it was last seen busy, since its focus-out looks like a keystroke and a program that reports no focus leaves nothing else when its tab is left, and every 10 s while it was last seen at its prompt, whose blur is stamped anyway, so a program started in it without a switch is learned at a later pause. A tab that reads on five ticks running (a program polling its input, which stamps the atime too — an `EAGAIN` read does, measured) is ignored until it stops, and an answer is asked again when `shown.conf` moved while Ghostty answered, so a tab's own claim is never overwritten with a stale one. The question is raw Apple Events addressed to the owning Ghostty's pid (`__tt_ghostty_owner`, the walk `__tt_reload_ghostty` shares; `TTHEME_GHOSTTY_JS`): JXA's `Application(pid)` goes to the bundle's first instance — the user's Ghostty while the sandbox's runs (measured). A Ghostty whose dictionary has no `tty` (1.3.1 and before; the running bundle's `Ghostty.sdef` is read for `code="Gtty"`, since an unknown property fails in JXA before reaching the app, `-1700`, measured) or that names no terminal five times running over at least 30 s (`macos-applescript = false`) is remembered in `ghostty/.blind` by `TERM_PROGRAM_VERSION` for a day — never a Ghostty that quit: the script answers `gone` for a pid no longer running and a `none` from a dead pid counts for nothing, so the follower of a Ghostty quit and reopened leaves instead of marking the new one blind, and `init` removes `.blind` (`forget`, `InitPaths.stateDir`) so the layer an upgrade brings asks again — and a shell records nothing and starts no follower where none can run — checked once per shell and again whenever `.blind` appears, so a shell started before it does not respawn a follower that cannot see (`__tt_ghostty_follows`: `TERM_PROGRAM=ghostty`, an interactive shell with a tty, `osascript`, no tmux, no fresh `.blind`) — Linux Ghostty, tmux and the latency harness among them, so their hot paths pay nothing (`bench --against`: first prompt +0.04 ms, a command +0.02 ms, both inside the noise); where it runs, a new tab's first prompt writes its record, about 1 ms. The follower also runs a watcher (`TTHEME_GHOSTTY_WATCH`, an `osascript -l JavaScript` coprocess `__tt_ghostty_watch` starts once the first answer came back) that polls the window server rather than Ghostty. Each look costs two id lists (`CGWindowListCreate`): whether Ghostty's front window is still on screen and how many windows lie above it. Only when either changed — a tab switch takes the window off screen, a Ghostty window or another app coming forward changes the count — does it read the list (`CGWindowListCopyWindowInfo`) for Ghostty's front window and refresh whether Ghostty is frontmost (`frontmostApplication`, with one run-loop pass, since JXA's `delay` runs none and the property goes stale; also every 40 looks). When Ghostty is frontmost and its front window is not the one it last reported, it prints the answer — the one it cached for that window at once, then the one Ghostty gives through the same raw Apple Events when it differs, cached only if that window is still in front after the question — as `1 <tty> <pid> <time>`. It looks every 50 ms for 1.5 s after a mouse down, key down or modifier change (`CGEventSourceSecondsSinceLastEventType`, which counts every app, so only while Ghostty is frontmost), every 150 ms otherwise, every 0.25 s while Ghostty is behind and every second while it shows no window; JXA hands `NSArray.count` back as a string, hence `+l.count`. The follower waits on it with `zselect` (`__tt_ghostty_heard` → `__tt_ghostty_take`, which drops an answer older than `shown.conf`'s last write, a tab's own claim since), ticks every 0.5 s instead of 0.1 s while it runs, asks nothing about a quiet busy tab in front, and lets neither a blur nor a tab behind taking input make it ask within a second of the watcher's last line; the watcher leaves with its follower or its Ghostty (`getppid`, `terminated`, and at once when Ghostty shows no window and its pid is gone), and a follower leaves when its own `adapters/ghostty.zsh` changes (`TTHEME_GHOSTTY_CODE`), so an upgrade's first prompt starts one on the new code. The watcher takes about 0.5% of a core with Ghostty behind and 0.5–1% in front. The follower leaves when no recorded shell, or its Ghostty, is alive. A switch between two busy tabs that both report no focus still waits for a keystroke in the one in front. The parity model answers the question from `.parity/front`, which only the Ghostty model writes (another terminal's tab coming forward leaves Ghostty's own front tab as it was), through an `osascript` shim, whose watcher mode prints an answer whenever that file changes, and stamps a tab's tty on every write on Linux, whose kernel keeps tty times to 8 s; compat's `front-tty` holds real Ghostty to the answer.
- Preview lays its picture where Ghostty lays `background-image`: on the window's surface, padding included, not on the grid. Its layers hang into the padding through relative placements (`bgrel`, set when Ghostty answers the probe's missing parent with `ENOPARENT`; Ghostty draws one that reaches into the grid, padding and all, and culls one lying wholly above the first row — measured), the fill and veil over a margin of whole cells (`bgmx`, `bgmy`), and the picture on the surface `__tt_bg_surface` estimates from each side's `window-padding-x`/`-y`, `window-padding-balance` and the grid and cell size, since Ghostty reports no window size (`CSI 14t` is the grid, and the pty's pixel size is the surface less the padding): the remainder past the last whole cell, which no report gives, is taken as half a cell, and a `cover` picture is framed on the surface grown by what that guess cannot know (half a cell across, on the far side where the near one is fixed), so it never stops short of the real edge. Balance follows Ghostty's `Size.balancePadding` (`renderer/size.zig`): released 1.3 reads the setting as a bool (`1`, `t`, `T` and `true` balance) and balances evenly, while 1.4 adds `equal`, which does that, and makes `true` cap the top at the mean of the left and right padding plus half a cell, the rest going to the bottom — the layer caps as 1.4 does, so under 1.3 a vertical padding well above the horizontal one is placed too high. `__tt_bg_place` then puts the picture's left and top on the pixel with `X`/`Y` and gives it `c` alone, so its height follows its aspect to the pixel instead of ending on a cell (Ghostty's `pixelSize`: `X` comes off the width either way, and with `r` given `Y` comes off the height); its right edge ends on a cell boundary, past the window's edge where the picture runs on, and up to a cell short of its own end where it ends inside the window; `__tt_bg_write` bakes on the same surface.
- Ghostty 1.3.1 and before (the latest release as of 2026-10) answers an OSC reset by pinning the default the surface holds at that moment (`DynamicRGB.reset` sets `override = default`; main's `7cd2f65f5`, 2026-08-05, sets it to null), so a tab that was reset once — `ttheme off`, `__tt_unwear`, preview's esc in a tab that never painted, a program's OSC 111 — stays on that background, foreground and cursor through every later reload, and a new default or `ttheme on` from another tab never reached it (`mise run compat --linux ghostty`: `follow-default`, `follow-belief`, `on-follow` and `on-belief` fail on 1.3.1 without the step below and pass with it, as they do on `ghostty-tip`, a main build). The palette is not pinned (`DynamicPalette.reset` clears its mask). So where a tab that never painted follows a new startup palette, the ghostty adapter's `__tt_followed` runs once the reload went out — in `__tt_fresh` for a tab told by the wake or its next prompt or focus, and after `__tt_reload` in `__tt_keep` and `__tt_installs_done` for the tab that ran the command, where `__tt_follow` runs before the reload — and asks the background, sending the reset again every 50 ms until it is the new palette's, for at most a second; a main Ghostty already shows it at the first ask, so it costs one query there and no process anywhere. The parity model keeps main's reset, which compat's `ghostty` column on the Mac measured.
- cmux (`manaflow-ai/cmux`) embeds libghostty in an app of its own and is wired as Ghostty, not as a terminal of its own: its surfaces get `GHOSTTY_RESOURCES_DIR`, so the detection block makes them the ghostty adapter, and it reads `$XDG_CONFIG_HOME/ghostty/config` with its `config-file` includes (the `?` form too) and `theme` files. It never answers SIGUSR2 and has no Ghostty dictionary, but it watches every file that include chain reaches and reloads by itself (`GhosttyConfigDiscovery+LiveReload.swift`, read in its source at 42c27fab, 2026-10-27, not measured). So the detection block marks a surface that carries `CMUX_SURFACE_ID` with `TTHEME_GHOSTTY_EMBEDDED`, under which `__tt_reload_ghostty` signals nothing and only sets `TTHEME_GHOSTTY_SENT`, so a claim still waits for the app to read `shown.conf` (`__tt_ghostty_took`), and `__tt_ghostty_follows` stays off: without it the owner walk found no `ghostty` process and fell back to `pkill`, reloading the user's own Ghostty on every cmux claim, and the follower's JXA, given no pid, asked the user's Ghostty which tab is in front. cmux shares `shown.conf` with any Ghostty on the same config, so a claim made in Ghostty reaches cmux at once through its watcher, while one made in cmux reaches Ghostty at its next reload. It tells libghostty the system's appearance (`ghostty_app_set_color_scheme`, `ghostty_surface_set_color_scheme`), so DSR 996 answers as in Ghostty. `ttheme info` names it (`ghostty <version> in cmux`).
- BSD `pgrep`/`pkill` skip their own ancestors, so from inside a Ghostty tab `pkill ghostty` misses that Ghostty. `__tt_reload_ghostty` (`_wired.zsh`) therefore walks up to the Ghostty that owns the shell and signals only it, falling back to `pkill` when the shell sits outside one (tmux, or another terminal such as iTerm2 changing a picture Ghostty shows); the walk runs once per shell and its answer is kept in `TTHEME_GHOSTTY_PID`, since a shell never outlives or changes its Ghostty.
