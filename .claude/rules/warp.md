# Warp

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only Warp does.

## Conventions

- Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes` — the released Warp reads no subfolder there) and, when its `settings.toml` exists (a feature-flagged build), the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/terminals/warp.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 0.5 s later if no later sync has decided Warp's theme since (each one takes back the token `warp.later` holds, `ttheme off` included, whose settings may still read as they did), the settings are still unchanged and the theme file is still there (`WARP_LATER`) — a file 0.1 s old is already worn right, one written in the same moment as the settings is not (measured, three runs at each age). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the warp adapter paints a tab through that key: with Warp wired and a `settings.toml` (`__tt_warp_wired`), `__tt_apply` points the `theme` line at the palette's newest theme file (`__tt_warp_value`, the newest of its hashed themes by a zsh glob, so no fork — which the Warp wiring keeps the one to wear by stamping a pictured theme it finds unchanged (`writePictures`), since a mode switched there and back rewrote the plain theme but left the pictured one as it was, older, and the tab came back without its picture: parity's `auto.back`) through `__tt_put`, so a linked dotfile survives, then puts an identical link in place of a linked one (`__tt_warp_relink`, and `relink` in `src/store/edits.ts` for the CLI's writers — `wearWarp`, `WARP_LATER`, `warpLive` — and uninstall's touch), since Warp hears its settings only through FSEvents on its own folders, which report a write through the link under the target's path and only the link renamed over it under the settings path (measured with an FSEvents watcher, no event for an in-place write or a rename over the target and one for the new link; Warp reloads when an update touches the settings path or its canonical form, and `repository_update_paths` counts both ends of a move, read in its source and measured in Warp 0.2026.10.07: a theme written through the link left Warp on its old theme with the file unread, and `__tt_warp_relink` switched it within 1.5 s, kecan0406/ttheme#11; a link to a directory is left alone, since `zf_mv` would move the new link into it), and writes nothing when the line already says it — every write reaches Warp's `Theme` preference, which its settings sync sends to the account (`SyncToCloud::Globally`) — keeping the user's own value in `warp.base` the way `sync` does; `__tt_osc_reset` puts on the default palette, or while ttheme is off the value in `warp.base` (`"dark"` over none) and removes `warp.base` once the user's theme is back (`__tt_warp_want`, `__tt_warp_wear`, which also waits until a theme file is 0.26 s old, since Warp falls back to its default for one it does not know yet). A new tab hears the default palette instead of asking Warp, whose answer is whatever tab is in front (`__tt_hear`; a shell started inside a painted tab hears the palette Warp wears). Warp tells an idle prompt nothing when its tab comes to the front — its `TerminalView` reports focus only while it holds focus itself, and at a prompt its input editor does — but it saves its session to its sqlite database (`~/Library/Group Containers/<team>.dev.warp/Library/Application Support/dev.warp.Warp-Stable/warp.sqlite`, `$XDG_STATE_HOME/warp-terminal/warp.sqlite` on Linux) at every tab activation and window activation (`should_save_app_state_on_action`, `on_active_window_changed`), at once and while `restore_session` is on (its default), and every shell knows its pane as `WARP_TERMINAL_SESSION_UUID`, the hex of `terminal_panes.uuid`. So every tab records what it wears in `$XDG_STATE_HOME/ttheme/warp/<uuid>` — its pid, the default it wore it under, its palette (none for a tab that never painted, which follows the default), preview's view, and the modification times of the `palettes.zsh` and pins file it last read — from each paint, reset and prompt (`__tt_warp_publish`, `__tt_prompted`), and one follower per user (`__tt_warp_follower`, a `zsh -f` sourcing the layer, kept single by a `zsystem flock` on `warp/.follow` and started by any prompt that finds it gone — one process per Warp session) polls the database's modification time every 0.1 s (`__tt_warp_stamp`), reads the front tab with one query when it moved (`TTHEME_WARP_SQL`: `app.active_window_id`, that window's `active_tab_index`-th tab by id, its focused leaf, `terminal_panes.uuid`; no active window while Warp is in the background, which changes nothing, and `TTHEME_WARP_UP` says which) through one `sqlite3` it keeps open as a coprocess (`__tt_warp_active`: the query and a `select 'end'`, read with a 1 s timeout; one that died or went silent is replaced at the next query) rather than one started per change, which cost 4–9 ms each (the `sqlite3` a PATH finds first may be the Android SDK's, twice as slow as `/usr/bin/sqlite3`), writes it to `warp/.active`, and puts on that tab's palette when the front tab, its record or `palettes.zsh` moved (`__tt_warp_tick`); a record made before ttheme went off gets the user's theme, as Ghostty's tabs turn off at once where they sit idle at their prompt (the wake, `terminals.md`) and otherwise at their next focus, and the follower leaves when no recorded shell is alive (`__tt_warp_live`) and, checked with it every 5 s, execs itself afresh once `adapters/warp.zsh` or `config.zsh` changed (`__tt_warp_code`: its `sqlite3` closed with `coproc :` and its lock released first, so another tab's prompt may win it instead), so an upgrade or a changed setting reaches it without restarting Warp or waiting for a prompt. Most of a switch's delay is Warp's: it reads `settings.toml` only through its data-directory watcher (`WarpManagedPathsWatcher`, notify-debouncer-full at 500 ms with a 125 ms tick), which hands a change on once it is 500 ms old, so Warp re-read the file 0.55–0.81 s after a write (measured through the file's atime, ten writes, Warp in the background); `warpctrl theme set`, the one direct path, is compiled into the stable app but switched on only in dogfood builds (`WarpControlCli`), and per-tab themes (warpdotdev/warp#478) have a merged spec and no implementation. The debouncer ages every event on its own and a reload reads the file as it is then, so the follower keeps it warm (`__tt_warp_warming`): with `TTHEME_WARP_FAST` on (`config.zsh`, default on; `init` asks when Warp is among the terminals it wires, and `ttheme config` changes it — preview's alt-c panel shows the settings every terminal shares, so it carries no row for it), Warp in front, and either the recorded tabs wearing more than one look (`__tt_warp_mixed`, a tab without a palette counting as the default; counted again whenever the front tab, the records directory or `palettes.zsh` moved) or the tab in front having changed the palette or view its record names in the last 3 s (`TTHEME_WARP_WARM`, `TTHEME_WARP_LOOK` — preview's hovers in a single tab; a record that moved only its default or the times it read, as a poke leaves it, warms nothing), it rewrites the first byte of `settings.toml` with itself every 0.25 s (`__tt_warp_prime`: opened read-write, one byte read and written back in place, never truncated — a short file makes Warp log `Failed to reload settings file`; a linked `settings.toml` gets an identical link in its place instead, since a write through it reaches no watcher) and looks at the database every 20 ms instead of 0.1 s (`__tt_warp_wait`), so a switch reaches Warp while an older event matures. Measured: Warp re-read the file 3–291 ms after a write under warming every 0.125 s and 8–298 ms every 0.25 s, instead of 0.55–0.81 s (ten writes each, Warp in the background), and the database write to `settings.toml` took 15 ms at the median instead of 80 (a synthetic database, thirty switches; 50 instead of 86 where the 0.1 s poll stays). Each reload costs Warp a settings parse and a redraw of every window (`SettingsErrorsCleared` notifies the workspace): with a window in front Warp used 2% of a core idle, 8% warmed every 0.25 s and 14% every 0.125 s (no window: about 4.5% either way), and the follower's 20 ms poll costs it about 2% (a wakeup costs it about 0.3 ms — polling that fast all the time tripled the idle follower's CPU), which is why none of it runs while every tab shows the same palette or Warp is behind; 0.25 s is the user's pick between latency and CPU. Tracked for removal in kecan0406/ttheme#10: once Warp can switch a tab's theme itself (warpdotdev/warp#478) or `warpctrl theme set` reaches the stable app, the warming and `TTHEME_WARP_FAST` go. Browse and init's picker in Warp keep the tab's own picture under the colors they show (`warpLive`): the tab's own palette is the one the shell hands over as `TTHEME_WARP_WEARS`, else the default, and a hover wears that palette's own theme file when it is the palette hovered, the hovered palette's plain theme when the tab shows no picture, and otherwise a view theme of the hovered colors whose `background_image` is the laid file the tab's own theme names — a file Warp already holds, so no frame flashes while it loads one; it costs the 0.26 s Warp needs to learn a new theme file. A command's `sync` writes the default (or while off the user's theme) over the key unless the tab that ran it is the one in front and wears an installed palette: `__tt_cli` hands the CLI `TTHEME_WARP_WEARS` through the adapter hook `__tt_cli_env`, and the Warp wiring keeps that palette on the key (`kept`), so a painted tab that runs `ttheme default`, `add` or Browse's apply no longer shows the default before it puts its own back (parity's journal read `kita · miku · kita` for `default`). The warp adapter's `__tt_reloaded`, which `__tt_installs`, `__tt_switch` and `__tt_fresh` call after `palettes.zsh` is read again, still puts the tab's own palette back wherever the key moved — a command run in another terminal or a tab behind. A tab behind another writes nothing itself (`__tt_warp_here` reads `.active`, trusted only while the follower holds its lock); without a follower (no `sqlite3`, no session id) `__tt_prompted` runs `__tt_sync`, so a tab puts its palette back at its prompt. Measured on 0.2026.09.16: seven clicked tab switches each reached the database within milliseconds, and switching two sandbox windows through `warp://session/<uuid>` moved the key 0.17–0.21 s after the switch was asked for, four times out of four, before Warp's own 0.5 s settings debounce (`WarpManagedPathsWatcher`). Split panes are not followed, since `FocusPane` saves nothing. Warp tells an idle prompt nothing when its tab comes to the front (read in its source: a tab switch only moves its own state and saves the session, and CSI I/O go out only while the terminal view itself holds focus), so the follower tells it: when the tab in front changes, or Warp comes back to the front, and that tab's record shows an older `palettes.zsh` or pins file than there is now, it sends the shell the record names SIGURG (`__tt_warp_poke`) — a signal every program ignores by default and nothing in Warp sends or traps (its zsh bootstrap traps EXIT alone), so a pid reused or a shell that `exec`ed something else loses nothing. The layer's `TRAPURG` (`terminals.md`) acts only while the shell is idle at its prompt, where `zsh_eval_context` holds the trap's own `shfunc` alone, with zle or without — a trap held until a command ends shows `toplevel` and one inside preview or a widget shows more (measured) — and there the warp adapter's `__tt_poked` runs `__tt_fresh` and publishes its record under `TTHEME_WARP_HOLD`, which keeps `__tt_warp_here` false, so the shell writes no `settings.toml` and the follower puts on the one look the record ends with. A newer `palettes.zsh` alone never changes that look — a new default, `off` and `on` end where the follower already reads the record — so the follower only signals; a pins file the tab has not read can repaint it, so the follower waits up to 0.15 s for the record to show the current pins before it puts anything on, once per shell and pins change (`TTHEME_WARP_WAITED`), since a busy shell runs the trap only after its command (no `traps_async`). An idle shell answers within milliseconds, so a pin set or moved in another tab, a new default, `ttheme off` and `ttheme on` reach a tab as it comes to the front, as Ghostty's focus does (parity's `pin-reach`, `default`, `off`, `on`), and compat's `prompt-trap` measures the trap at a prompt. On the tty a blocking `read -k -t` returns early when a run of signals lands in it, or one lands in a timeout under 0.1 s, while one in preview's 0.2 s read lets it run its time (0.24 s; six 10 ms apart ended it at 0.06 s), and `zselect` and `sysread` start their timeout again (measured), so preview ignores SIGURG while it is open (`trap '' URG` under its `local_traps`, and only over the layer's own `TRAPURG`, the one that calls `__tt_woken`): thirty wakes 10 ms apart closed it, its key loop taking five reads in a row that came back at once for a hung-up terminal (`latency.zsh check`'s `urged`), and the trap does nothing there anyway.
- Warp shows a picture through its theme: a palette whose `backgrounds/<palette>.conf` names one gets `ttheme-<stem>.<hash>.png`, the picture laid whole on the palette's background (`flatten` at 1, `src/core/png.ts`, written by `encodeRgb` as an RGB PNG, every row Up-filtered and deflated at level 1 with zlib's run-length strategy (`packed`, which `encodeRgba` and `encodeMask` share, since a picture's rows repeat the row above), rather than through pngjs, whose defaults try every filter at level 9 (measured on a 2560×2542 picture: 392 ms and 3.57 MB against 67 ms and 3.69 MB, and the same on a 36-megapixel photograph at +16% in size), or by `flatIndexed` for a tone picture — an indexed PNG whose index is its alpha: it blends the 256 palette entries onto the background, drops the tRNS and copies the pixels as they are, the same colors in 3 ms where `decodePng`, `flatten` and `encodeRgb` took about 73 ms (measured on a copy of a 215-palette install, where `sync` spent 2.5 s on 44 pictures and now spends it, once, on the 12 in their own colors); `warpPictureFile` names it by the 32-bit FNV-1a of the picture's path and the lowercased background), and `ttheme-<stem>.<hash>.yaml` beside its plain theme showing that file at the picture's opacity (`warpThemeFile`/`warpTheme`, `src/terminals/emit/warp.ts` — every theme, the plain one too, is named by a hash of its whole text, so any change of its colors, picture or opacity is a new name, and the layer finds a palette's plain theme in `TTHEME_WARP_PLAIN`). Warp draws a theme's picture first and lays the theme's background color over it at 1 − opacity: a picture with transparent parts turns the window see-through by as much (measured: a fully transparent picture at 80 turned `#204060` into `#aeb3b8`), which is why the picture goes out laid on the background, and a picture laid whole at `opacity: 19` shows the same colors as one laid at 0.19 at `opacity: 100` (measured at five points, exact). While Warp loads a picture it has not shown yet it draws only that color layer for a frame, so the window shows through by the opacity: at 100 that frame is the whole window light grey, at 19 a faint lift (measured six times each: `#bdbdbd` against `#3e3634` over `#211513`) — hence the opacity stays Warp's, and a change of opacity alone keeps the same laid file, which Warp already holds. The Warp wiring's `sync` and `pictures` hooks write them (`laidFiles`, `writePictures`, `src/terminals/warp.ts`; `refreshPictures` calls `pictures` whenever a picture changes) — a palette whose picture cannot be read wears its plain theme — move the `theme` key to the new file while Warp wears that palette and it is still installed (`wearWarp` with `keep`, through `WARP_LATER` when the file is new), and delete the palette's other hashed files unless the key still names one — so a stale one goes a sync later — and every laid file no theme names, bar the one a picture in its own colors has on the other mode's background (`writePictures` names it from `theme.other`), which a switch back then finds laid. Warp reads a theme file once — rewriting the one it wears changes nothing on screen, and neither does renaming another file over it, deleting it or writing it again after a delete (measured) — hence a new name for every change. Warp shows any change of the key 0.58–0.77 s after the write — a plain theme, a picture it has shown and a new one alike, PNG or JPEG, whole or half size, a rename or an in-place write (measured over forty switches); an in-place write that leaves the file short for a moment makes it log `Failed to reload settings file` and keep the old state. Warp has no position or size, and draws every picture as cover, so the Warp wiring `bakes`, and with Warp wired `__tt_bg_write` bakes every tuned size up to 100% onto a window canvas — centered ones too, `__tt_bg_covers` in `_wired.zsh` — and `__tt_bg_aligns` is false, as with iTerm2; `__tt_pictured_warp` runs `ttheme image <palette> tuned` unless iTerm2's hook already did. In preview the warp adapter sources `_bg.zsh` but never draws its kitty layers: `__tt_pv_bg_show` does nothing while a picture is untuned — the palette's theme already carries it — and draws nothing either while keys keep coming (the next within 0.15 s, `zselect -r 0`, which reads nothing), so a held key renders once, when it is let go, not four times a second with a grey frame each; otherwise `__tt_warp_view` writes a short-lived `ttheme-<stem>.view-<n>.yaml` (the plain theme plus the picture at its opacity) first and then has the hidden `ttheme flatten` lay the picture whole on the background in one pass — the saved file itself when it exists (`__tt_warp_saved` names the file `__tt_bg_write` would record for this tuning: the base, the fill, the kept bake or the bake to come), else the source in the frame `__tt_bg_frame` gives on the grid's canvas, passed as `<canvas> <place>` geometry, at the picture's own resolution when Warp would enlarge it anyway (`canvasOf`, so a 140% step is 1926×1349 instead of 2912×2040) — into Warp's themes folder under the name a save gives that picture (`__tt_warp_laid`, the same FNV-1a without a fork, which `sync.test.ts` holds to `warpPictureFile`), so a state seen before is never drawn again, an opacity step draws nothing, and the saved theme shows the very file the view showed, which Warp already holds (measured: no frame changes on applying); the files it made (`TTHEME_WARP_LAID`) that no theme names 10 s after preview closes are removed (`__tt_warp_sweep`), as `sync` removes any other; it points the key at the theme once that is 0.25 s old, setting preview's `applied` and `painted` so its paint does not put the plain theme back, and records the view, so the follower puts it back when the tab returns to the front. A step takes 0.2–0.3 s where five `sips` runs and a second node process took 1.8 s. `__tt_pv_bg_close` wears the palette again and removes the view unless its picture has a kept tuning (`bgedit`) or is the picture chosen to be shown (`bgview`), which the close is about to save: that view stays up while `refreshPictures` moves the key off it to the new pictured theme (`wearWarp` in keep mode, through `WARP_LATER` when that file is new), so the saved picture never flicks back to the old one, and the warp adapter's `__tt_bg_refresh`, which `__tt_bg_saved` calls after the CLI, only removes the view file. A saved tuning is baked with the hidden `ttheme bake` as in every adapter (`__tt_bg_bake`), so closing preview after a save takes 0.68 s where five `sips` runs made it 1.54 (measured in a pty). Nothing is swept sooner, since Warp may fetch a view's picture again until it has moved off it (its log: `Asset fetch failed`). `__tt_bg_cells` divides `CSI 14t` by `CSI 18t` — Warp answers no `CSI 16t` — and doubles it, because Warp reports points and draws at twice that on a Retina Mac. find and the tuning strip draw with kitty graphics, where Warp differs from every other terminal (measured on 0.2026.09.16, `window.zsh --warp`): it refuses `t=f` (`UnsupportedPlatform`), so `TRAITS.warp.files` is false and pictures go out as chunked base64 (`transmit`, `__tt_bg_transmit`, one `base64` fork per picture sent); it ignores a source rectangle, so `bands` is on; it draws every negative `z` above non-default cell backgrounds — so `TRAITS.warp.layers` is false and find draws no cover there, which would hide its loading bar and every colored cell, and preview's `__tt_bg_hide` puts the palette's plain theme on before it runs find; placing an image again under the same `i` and `p` adds a second placement rather than moving the first (`TRAITS.warp.moves`, so find deletes it first; iTerm2 cannot take that, since its `d=i` frees the data), `EL` and `ECH` leave a placement alone, and a relative placement answers OK but is drawn at its parent, ignoring `H`/`V`. `CellProbe` (`src/tui/keys.ts`) reads the window and grid reports when no `CSI 16t` comes back.
