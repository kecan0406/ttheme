# Warp

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only Warp does.

## Conventions

- Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes`) and, when its `settings.toml` exists, the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/terminals/warp.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Every write that puts a ttheme theme over a value that names none keeps that value again (`warpWear`, `__tt_warp_write`, which tell ttheme's by its `path = "ttheme-`), so a theme picked in Warp's own picker while ttheme wore a palette is the one `ttheme off` gives back — it kept only the first and gave back the theme from before ttheme. Warp's `[account] is_settings_sync_enabled = true` (its Settings sync, which signing in turns on) sends `theme` and `selected_system_themes` to the account (`SyncToCloud::Globally`) for every value whose path lies in the themes folder — a device without the same file falls back to Warp's dark theme (warpdotdev/warp#8988) and one running ttheme puts its own back — so init notes it per channel (`notes`) and changes nothing: turning it off is the user's. Warp's Enforce minimum contrast (`[appearance.text] enforce_minimum_contrast`: `only_named_colors` by default, `never`, `always`) redraws a cell's text that reads at most 4.5:1 on that cell's background by blending it toward white or black, whichever contrasts more with the background, at the least opacity that reaches 4.5 (its `foreground_color_with_minimum_contrast`); by default only text in a named color — SGR 30–37 and 90–97, which is also what terminfo's `setaf` sends for colors 8–15 — and never `38;5;n` or truecolor, and always the text under a block cursor unless it is `never`. Measured on the Linux build 0.2026.10.21 with nijika in both modes and all three values, every drawn color exactly what that formula gives: ANSI 8 on the background a little lighter (every built-in palette in both modes, ΔE2000 4.0 dark, 1.6 light at the median), ANSI 0 a visible gray, and light text on ANSI 8 or an accent turned nearly black (dark text nearly white in a light palette) — which no palette can avoid, since in a dark palette an accent that reads 4.5:1 on the background cannot take white text at 4.5:1. So while ttheme wears a palette, `sync` sets it to `never` where the file sets nothing (`withContrast`, in the same write as the theme), keeping in `warp.contrast` whether it added the key or the whole table, and `ttheme off`, no palette and uninstall take back exactly that (`letContrastGo`, `warpBack`, `withoutContrast`); a value the user set — or changed since — is theirs and stays. Only the CLI's `sync` touches it, never the shell's paints or Browse's live ones. While Warp follows the system (`system_theme = true`, its Sync with OS) it reads `selected_system_themes` and never `theme` (`derived_theme_kind` in its `settings/theme.rs`), so every write that names a ttheme theme puts it in both of that table's slots too (`warpWear`, `warpSystemValue`; the adapter's `__tt_warp_write`, and `__tt_warp_says`, which tells a line that already says it), keeping the user's own table in `warp.system` and writing it back with the `theme` line (`warpBack`; `{ light = "light", dark = "dark" }`, Warp's default, over none) — before, a Warp that followed the system showed none of ttheme's palettes while the shell believed it wore them (measured 2026-10-26 on the Linux builds 0.2026.10.21 under Xvfb: with `system_theme = true` Stable answered OSC 11 with Solarized Light's `#fdf6e3` from the user's table while `theme` named miku, moving `theme` alone to asuka changed nothing, `ttheme use rei` showed rei's `#12181d` and `ttheme off` put the table back word for word; Preview did the same through `ttheme default`). compat's `system-theme` holds it in the Linux build, where the sandbox's Warp reads its own settings (Warp turns Sync with OS on, then `ttheme use` must show the palette): it passes, and failed on the code before this change; macOS skips it, as every case that needs Warp to take a palette. Each Warp channel keeps its own folder and settings — Stable `~/.warp`, Preview `~/.warp-preview`, Dev `~/.warp-dev`, the open-source build `~/.warp-oss`, and on Linux `warp-terminal`, `warp-terminal-preview`, `warp-terminal-dev` and `warp-oss` under the XDG folders (its `paths.rs`) — and its own session database under its bundle id, while every one sets `TERM_PROGRAM=WarpTerminal`. A tab names its channel by `__CFBundleIdentifier`, which macOS hands every process of an app it launched (`dev.warp.Warp-Stable`, `-Preview`, `-Dev`, `dev.warp.WarpOss`), else by the channel its `TERM_PROGRAM_VERSION` ends in (`v0.2026.10.21.08.25.stable_02`), else it is Stable (`warpChannelOf`, and the `case` at the top of the adapter, which sets `TTHEME_WARP_NAME`: the channel's settings, themes, records, follower lock and database, and its `<name>.base`, `.system` and `.later` — Stable's name stays `warp`). `sync` wears the default in every channel whose folder exists (`warpChannels`) and writes a themes folder they share once (`shelvesOf`, by real path): Preview's first launch links every entry of `~/.warp` but `settings.toml` into `~/.warp-preview` (its `preview_config_migration.rs`), so its `themes` is Stable's. `TTHEME_WARP_WEARS` keeps a palette on the key only in the channel the command ran in. Measured on Linux 0.2026.10.21 (2026-10-26): Preview read `~/.config/warp-terminal-preview/settings.toml` and the themes under `~/.local/share/warp-terminal-preview`, kept its database at `~/.local/state/warp-terminal-preview/warp.sqlite`, carried `v0.2026.10.21.08.26.preview_02` as its tag (its log; Stable's shells carry theirs, `…stable_02`, as `TERM_PROGRAM_VERSION`), and never looked at Stable's `settings.toml`, which is all ttheme wrote before; Preview opens no tab until it is signed in (its channel forces sign-in), so its shells and the follower there are not measured — only its window's colors, which its sign-in screen draws under a scrim at about 0.3 of the theme's background. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 0.5 s later, or 0.7 s after the settings' last write when that is later (`warpReady`, the rule below) if no later sync has decided Warp's theme since (each one takes back the token `warp.later` holds, `ttheme off` included, whose settings may still read as they did), the settings are still unchanged and the theme file is still there (`WARP_LATER`) — a file 0.1 s old is already worn right, one written in the same moment as the settings is not (measured, three runs at each age). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the warp adapter paints a tab through that key: with Warp wired and a `settings.toml` (`__tt_warp_wired`), `__tt_apply` points the `theme` line at the palette's newest theme file in the mode worn (`__tt_warp_value`, the newest of its `ttheme-<stem>.<mode>.<hash>.yaml` by a zsh glob over `TTHEME_MODE_WORN`, so no fork — both modes' themes stay on disk, and a palette's pictured theme is written after its plain one and dropped with its picture, so while it exists it is the newer; the Warp wiring used to stamp a pictured theme it found unchanged, since a mode switched there and back rewrote the plain theme and left the pictured one older, parity's `auto.back`, and the stamp made the file look new to `__tt_warp_ripe`) through `__tt_put`, so a linked dotfile survives, then puts an identical link in place of a linked one (`__tt_warp_relink`, and `relink` in `src/store/edits.ts` for the CLI's writers — `wearWarp`, `WARP_LATER`, `warpLive` — and uninstall's touch), since Warp hears its settings only through FSEvents on its own folders, which report a write through the link under the target's path and only the link renamed over it under the settings path (measured with an FSEvents watcher, no event for an in-place write or a rename over the target and one for the new link; Warp reloads when an update touches the settings path or its canonical form, and `repository_update_paths` counts both ends of a move, read in its source and measured in Warp 0.2026.10.07: a theme written through the link left Warp on its old theme with the file unread, and `__tt_warp_relink` switched it within 1.5 s, kecan0406/ttheme#11, which compat's `linked-settings` holds — `settings.toml` moved into another folder and linked back, then `ttheme use` must reach the theme; a link to a directory is left alone, since `zf_mv` would move the new link into it), and writes nothing when the line already says it — every write reaches Warp's `Theme` preference, which its settings sync sends to the account (`SyncToCloud::Globally`) — keeping the user's own value in `warp.base` the way `sync` does; `__tt_osc_reset` puts on the default palette, or while ttheme is off the value in `warp.base` (`"dark"` over none) and removes `warp.base` once the user's theme is back (`__tt_warp_want`, `__tt_warp_wear`). Every settings write that names a theme file younger than 0.75 s waits first (`__tt_warp_ripe`, in `__tt_warp_set` and the preview jobs below) until the file is 0.26 s old and the previous settings write 0.7 s old — once the settings are known not to say it already, since a `sync` has usually just written that line (a mode switch's shell waited the 0.7 s to write nothing, every time, measured in a real Warp window with the settings watched every 5 ms; comparing first, preview's Mode row takes the next key 149–165 ms after the enter instead of 851–893, while the window still changes when Warp reads its settings, 720–806 ms): Warp resolves the theme the settings name only when the settings change, against the themes it has loaded, and loads them again only when a change in the themes folder is itself 500 ms old (`load_theme_configs` on any change there, read in its source), so settings read before the new file was loaded put on Warp's default dark theme and keep it until the settings change again — measured on 0.2026.10.21 with a window in front: a theme file written with the settings fell back every time, one 0.25 s older never (3 of 3, then 22 of 22 with settings 0.27–0.4 s apart), a settings change it already knew showed 0.58–0.68 s after the write, and a new file named 0.25 s after it was written 0.57–0.71 s after the settings. A new tab hears the default palette instead of asking Warp, whose answer is whatever tab is in front (`__tt_hear`; a shell started inside a painted tab hears the palette Warp wears). Warp tells an idle prompt nothing when its tab comes to the front — its `TerminalView` reports focus only while it holds focus itself, and at a prompt its input editor does — but it saves its session to its sqlite database (`~/Library/Group Containers/<team>.dev.warp/Library/Application Support/dev.warp.Warp-Stable/warp.sqlite`, `$XDG_STATE_HOME/warp-terminal/warp.sqlite` on Linux) at every tab activation and window activation (`should_save_app_state_on_action`, `on_active_window_changed`), at once and while `restore_session` is on (its default), and every shell knows its pane as `WARP_TERMINAL_SESSION_UUID`, the hex of `terminal_panes.uuid`. So every tab records what it wears in `$XDG_STATE_HOME/ttheme/warp/<uuid>` — its pid, the default it wore it under, its palette (none for a tab that never painted, which follows the default), preview's view, and the modification times of the `palettes.zsh` and pins file it last read — from each paint, reset and prompt (`__tt_warp_publish`, `__tt_prompted`), and one follower per user (`__tt_warp_follower`, a `zsh -f` sourcing the layer, kept single by a `zsystem flock` on `warp/.follow` and started by any prompt that finds it gone — one process per Warp session) polls the database's modification time every 0.1 s (`__tt_warp_stamp`), reads the front tab with one query when it moved (`TTHEME_WARP_SQL`: `app.active_window_id`, that window's `active_tab_index`-th tab by id, its focused leaf, `terminal_panes.uuid`; no active window while Warp is in the background, which changes nothing, and `TTHEME_WARP_UP` says which) through one `sqlite3` it keeps open as a coprocess (`__tt_warp_active`: the query and a `select 'end'`, read with a 1 s timeout; one that died or went silent is replaced at the next query) rather than one started per change, which cost 4–9 ms each (the `sqlite3` a PATH finds first may be the Android SDK's, twice as slow as `/usr/bin/sqlite3`), writes it to `warp/.active`, and puts on that tab's palette when the front tab, its record or `palettes.zsh` moved (`__tt_warp_tick`); a record made before ttheme went off gets the user's theme, as Ghostty's tabs turn off at once where they sit idle at their prompt (the wake, `terminals.md`) and otherwise at their next focus, and the follower leaves when no recorded shell is alive (`__tt_warp_live`) and, checked with it every 5 s, execs itself afresh once `adapters/warp.zsh` changed (`__tt_warp_code`: its `sqlite3` closed with `coproc :` and its lock released first, so another tab's prompt may win it instead), so an upgrade reaches it without restarting Warp or waiting for a prompt. Most of a switch's delay is Warp's: it reads `settings.toml` only through its data-directory watcher (`WarpManagedPathsWatcher`, notify-debouncer-full at 500 ms with a 125 ms tick), which hands a change on once it is 500 ms old, so Warp re-read the file 0.55–0.81 s after a write (measured through the file's atime, ten writes, Warp in the background); `warpctrl theme set`, the one direct path, is compiled into the stable app but switched on only in dogfood builds (`WarpControlCli`), and per-tab themes (warpdotdev/warp#478) have a merged spec and no implementation. So a switch shows about 0.6 s after the follower writes it. There is no warming: rewriting the settings in place every 0.25 s, so that an older change was always about to be reloaded, brought a switch to known themes down to 0.09–0.28 s but put Warp on its default dark theme for every new theme file — a preview view, a hover over a palette not installed, the pictured theme a save writes — named while it ran (fallback 3 of 3 with the file 0.25 s older than the settings, 2 of 3 at 0.5 s, measured on 0.2026.10.21), cost Warp 6–12% of a core and the follower a 20 ms poll, and is gone with `TTHEME_WARP_FAST` (kecan0406/ttheme#10). Browse and init's picker in Warp keep the tab's own picture under the colors they show (`warpLive`): the tab's own palette is the one the shell hands over as `TTHEME_WARP_WEARS`, else the default, and a hover wears that palette's own theme file when it is the palette hovered, the hovered palette's plain theme when the tab shows no picture, and otherwise a view theme of the hovered colors whose `background_image` is the laid file the tab's own theme names — a file Warp already holds, so no frame flashes while it loads one; it costs the 0.26 s Warp needs to learn a new theme file, and 0.7 s after the settings' last write where that is later (`warpReady`, which `__tt_warp_ripe` mirrors). A command's `sync` writes the default (or while off the user's theme) over the key unless the tab that ran it is the one in front and wears an installed palette: `__tt_cli` hands the CLI `TTHEME_WARP_WEARS` through the adapter hook `__tt_cli_env`, and the Warp wiring keeps that palette on the key (`kept`), so a painted tab that runs `ttheme default`, `add` or Browse's apply no longer shows the default before it puts its own back (parity's journal read `kita · miku · kita` for `default`). The warp adapter's `__tt_reloaded`, which `__tt_installs`, `__tt_switch` and `__tt_fresh` call after `palettes.zsh` is read again, still puts the tab's own palette back wherever the key moved — a command run in another terminal or a tab behind. A tab behind another writes nothing itself (`__tt_warp_here` reads `.active`, trusted only while the follower holds its lock); without a follower (no `sqlite3`, no session id) `__tt_prompted` runs `__tt_sync`, so a tab puts its palette back at its prompt. Measured on 0.2026.09.16: seven clicked tab switches each reached the database within milliseconds, and switching two sandbox windows through `warp://session/<uuid>` moved the key 0.17–0.21 s after the switch was asked for, four times out of four, before Warp's own 0.5 s settings debounce (`WarpManagedPathsWatcher`). Split panes are not followed, since `FocusPane` saves nothing. Warp tells an idle prompt nothing when its tab comes to the front (read in its source: a tab switch only moves its own state and saves the session, and CSI I/O go out only while the terminal view itself holds focus), so the follower tells it: when the tab in front changes, or Warp comes back to the front, and that tab's record shows an older `palettes.zsh` or pins file than there is now, it sends the shell the record names SIGURG (`__tt_warp_poke`) — a signal every program ignores by default and nothing in Warp sends or traps (its zsh bootstrap traps EXIT alone), so a pid reused or a shell that `exec`ed something else loses nothing. The layer's `TRAPURG` (`terminals.md`) acts only while the shell is idle at its prompt, where `zsh_eval_context` holds the trap's own `shfunc` alone, with zle or without — a trap held until a command ends shows `toplevel` and one inside preview or a widget shows more (measured) — and there the warp adapter's `__tt_poked` runs `__tt_fresh` and publishes its record under `TTHEME_WARP_HOLD`, which keeps `__tt_warp_here` false, so the shell writes no `settings.toml` and the follower puts on the one look the record ends with. A newer `palettes.zsh` alone never changes that look — a new default, `off` and `on` end where the follower already reads the record — so the follower only signals; a pins file the tab has not read can repaint it, so the follower waits up to 0.15 s for the record to show the current pins before it puts anything on, once per shell and pins change (`TTHEME_WARP_WAITED`), since a busy shell runs the trap only after its command (no `traps_async`). An idle shell answers within milliseconds, so a pin set or moved in another tab, a new default, `ttheme off` and `ttheme on` reach a tab as it comes to the front, as Ghostty's focus does (parity's `pin-reach`, `default`, `off`, `on`), and compat's `prompt-trap` measures the trap at a prompt. On the tty a blocking `read -k -t` returns early when a run of signals lands in it, or one lands in a timeout under 0.1 s, while one in preview's 0.2 s read lets it run its time (0.24 s; six 10 ms apart ended it at 0.06 s), and `zselect` and `sysread` start their timeout again (measured), so preview ignores SIGURG while it is open (`trap '' URG` under its `local_traps`, and only over the layer's own `TRAPURG`, the one that calls `__tt_woken`): thirty wakes 10 ms apart closed it, its key loop taking five reads in a row that came back at once for a hung-up terminal (`latency.zsh check`'s `urged`), and the trap does nothing there anyway.
- Warp shows a picture through its theme: a palette whose `backgrounds/<palette>.conf` names one gets `ttheme-<stem>.<hash>.png`, the picture laid whole on the palette's background (`flatten` at 1, `src/core/png.ts`, written by `encodeRgb` as an RGB PNG, every row Up-filtered and deflated at level 1 with zlib's run-length strategy (`packed`, which `encodeRgba` and `encodeMask` share, since a picture's rows repeat the row above), rather than through pngjs, whose defaults try every filter at level 9 (measured on a 2560×2542 picture: 392 ms and 3.57 MB against 67 ms and 3.69 MB, and the same on a 36-megapixel photograph at +16% in size), or by `flatIndexed` for a tone picture — an indexed PNG whose index is its alpha: it blends the 256 palette entries onto the background, drops the tRNS and copies the pixels as they are, the same colors in 3 ms where `decodePng`, `flatten` and `encodeRgb` took about 73 ms (measured on a copy of a 215-palette install, where `sync` spent 2.5 s on 44 pictures and now spends it, once, on the 12 in their own colors); `warpPictureFile` names it by the 32-bit FNV-1a of the picture's path and the lowercased background), and `ttheme-<stem>.<mode>.<hash>.yaml` beside its plain theme showing that file at the picture's opacity (`warpThemeFile`/`warpTheme`, `src/terminals/emit/warp.ts` — every theme, the plain one too, is named by its mode and a hash of its whole text, so any change of its colors, picture or opacity is a new name, and the layer finds a palette's plain theme in `TTHEME_WARP_PLAIN`). The `name` inside it is what Warp's theme picker lists — `<palette> · <mode>`, and ` · picture` after it for a pictured theme or a view with a picture (`warpThemeName`; the adapter's `__tt_warp_job` adds the suffix to the plain theme it copies), since four themes a palette all named `<palette>` crowded the picker with lookalikes — and Warp finds a theme by that name and its path together (its `ThemeKind::Custom` key; a pair it has not loaded gets its dark theme), so every write of the key reads the name from the file it names (`warpRef`, `__tt_warp_ref`) and the palette a value wears is the name up to ` · ` (`warpWorn`, `TTHEME_WARP_WORN`); parity's Warp look shows no theme where the two differ. Warp draws a theme's picture first and lays the theme's background color over it at 1 − opacity: a picture with transparent parts turns the window see-through by as much (measured: a fully transparent picture at 80 turned `#204060` into `#aeb3b8`), which is why the picture goes out laid on the background, and a picture laid whole at `opacity: 19` shows the same colors as one laid at 0.19 at `opacity: 100` (measured at five points, exact). While Warp loads a picture it has not shown yet it draws only that color layer for a frame, so the window shows through by the opacity: at 100 that frame is the whole window light grey, at 19 a faint lift (measured six times each: `#bdbdbd` against `#3e3634` over `#211513`) — hence the opacity stays Warp's, and a change of opacity alone keeps the same laid file, which Warp already holds. The Warp wiring's `sync` and `pictures` hooks write them (`laidFiles`, `writePictures`, `src/terminals/warp.ts`; `refreshPictures` calls `pictures` whenever a picture changes) — a palette whose picture cannot be read wears its plain theme — move the `theme` key to the new file while Warp wears that palette and it is still installed (`wearWarp` with `keep`, through `WARP_LATER` when the file is new), and delete the palette's other hashed files but its other mode's unless the key still names one — so a stale one goes a sync later — and every laid file no theme names, bar the one a picture has on the other mode's background. The other mode stays on disk ready: the emitter writes both modes' plain themes, as Ghostty's does, and `writePictures` lays a picture in its own colors on the other mode's background at once, once, and writes that mode's pictured theme beside it (`inOther`; a picture that is indexed — `indexed` reads its header — is a tone picture, drawn again in the other ink when its mode comes and laid then in 3 ms), so a mode switch moves only the `theme` key, to a file Warp has loaded — where it wrote every palette's themes anew and removed the old ones, which Warp had to load before the settings could name them, so a tab wearing any palette but the startup one waited out `__tt_warp_ripe` after a switch. Warp reads a theme file once — rewriting the one it wears changes nothing on screen, and neither does renaming another file over it, deleting it or writing it again after a delete (measured) — hence a new name for every change. Warp shows any change of the key 0.58–0.77 s after the write — a plain theme, a picture it has shown and a new one alike, PNG or JPEG, whole or half size, a rename or an in-place write (measured over forty switches); an in-place write that leaves the file short for a moment makes it log `Failed to reload settings file` and keep the old state. Warp has no position or size, and draws every picture as cover, so the Warp wiring `bakes`, and with Warp wired `__tt_bg_write` bakes every tuned size up to 100% onto a window canvas — centered ones too, `__tt_bg_covers` in `_wired.zsh` — and `__tt_bg_aligns` is false, as with iTerm2; `__tt_pictured_warp` runs `ttheme image <palette> tuned` unless iTerm2's hook already did. In preview the warp adapter sources `_bg.zsh` but never draws its kitty layers: `__tt_pv_bg_show` puts a tuned or other picture on as a view theme and hands the work to `_bg.zsh`'s background runner (`__tt_bg_ask`, `terminals.md`), so the key loop answers every key at once (9–15 ms a tuning step where a step held it 0.41 s, measured in a pty) and keys pressed while a view is laid fold into the last of them. `__tt_warp_view` names the view (`"<palette> <laid file> <opacity>"`): a view shown before keeps its theme for the session (`TTHEME_WARP_KNOWN`), so going back to it writes no file, else `__tt_warp_job` writes `ttheme-<stem>.view-<pid>-<n>.yaml` (the plain theme plus the picture at its opacity) first and then has the hidden `ttheme flatten` lay the picture whole on the background in one pass — the saved file itself when it exists (`__tt_warp_saved` names the file `__tt_bg_write` would record for this tuning: the base, the fill, the kept bake or the bake to come), else the source in the frame `__tt_bg_frame` gives on the grid's canvas, passed as `<canvas> <place>` geometry, at the picture's own resolution when Warp would enlarge it anyway (`canvasOf`, so a 140% step is 1926×1349 instead of 2912×2040) — into Warp's themes folder under the name a save gives that picture (`__tt_warp_laid`, the same FNV-1a without a fork, which `sync.test.ts` holds to `warpPictureFile`), so a state seen before is never drawn again, an opacity step draws nothing, and the saved theme shows the very file the view showed, which Warp already holds (measured: no frame changes on applying); then it waits as every settings write does (`__tt_warp_ripe`, above) and points the key at the view and records it, so the follower puts it back when the tab returns to the front. The runner's completion (`__tt_bg_done`) moves `TTHEME_WARP_SHOWING`; a view that never reached the settings in the tab in front is not asked for again (`TTHEME_BG_FAILED`). A picture back at its saved state is a `plain` job, the palette's own theme, again behind the key loop. The views stay until preview closes, since deleting one Warp may still be reading its settings onto put it on its default theme once in eight steps 0.27 s apart (measured); `__tt_warp_sweep`, 10 s after the close, removes the views and laid files (`TTHEME_WARP_MADE`, `TTHEME_WARP_LAID`) that the settings and no theme name, as `sync` removes any other, and preview's `applied` and `painted` are set when a view is asked for, so its paint does not put the plain theme back. Measured in a real Warp window (0.2026.10.21), from the key to the picture changing: an opacity step 0.57–0.67 s where it took 0.83–1.10 s, the first view of a session 0.86 s. `__tt_pv_bg_close` waits for the runner (`__tt_bg_settle`), then wears the palette again and removes the view unless its picture has a kept tuning (`bgedit`) or is the picture chosen to be shown (`bgview`), which the close is about to save: that view stays up while `refreshPictures` moves the key off it to the new pictured theme (`wearWarp` in keep mode, through `WARP_LATER` when that file is new), so the saved picture never flicks back to the old one, and the warp adapter's `__tt_bg_refresh`, which `__tt_bg_saved` calls after the CLI, only removes the view file. A saved tuning is baked with the hidden `ttheme bake` as in every adapter (`__tt_bg_bake`), so closing preview after a save takes 0.68 s where five `sips` runs made it 1.54 (measured in a pty).
