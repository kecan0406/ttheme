# iTerm2

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only iTerm2 does.

## Conventions

- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/pictures/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image <palette> show|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshPictures`, which runs every wired terminal's `pictures`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture — where the shell may switch profiles, the paint already moved the tab there (below), so it finds the tab on that profile undyed and sends nothing — and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`, and `default` while the tab is still on `ttheme · default`, read through `TTHEME_STARTUP` so it follows a default changed elsewhere; an empty `SetProfile=` lands on iTerm2's default profile, which the adapter names `default` only when the tab opened on `ttheme · default` (`__tt_iterm_home`, from `ITERM_PROFILE`) — iTerm2 keeps the default it launched with, so a tab opened on the user's own profile, before `ttheme on` moved the default and iTerm2 restarted, names none, while one opened on `ttheme · default` still names it after `ttheme off`, so `ttheme on` in a directory pinned to a palette without a picture takes the default's picture down, parity's `on-pin-plain`); it never asks for a reload, and since iTerm2 reports focus changes the layer binds focus reporting there as it does in Ghostty, so a tab syncs at every prompt and focus. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown` and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band cut first, into a scratch dir `__tt_pv_bg_close` removes). A size the terminal cannot scale is baked by `__tt_bg_bake`, the hidden `ttheme bake` in every adapter, where it took five `sips` runs: measured through the bundle on a 2142×2214 figure, 131 ms at 60% and 152 at 140% against 389 and 762, and on a pattern drawn exactly at both sizes its alpha is off by 0.33 and 0.15 on average (59 and 47 at most) at 60% and 33% against `sips`' 0.41 and 0.36 (92 and 109), the tone exact in every pixel where `sips` left pixels up to 6 levels off once composited, and no `gAMA`, `cHRM`, `eXIf` or `iTXt` chunk — so every size is offered on every system.
- iTerm2 has no config file, so `sync` owns `~/Library/Application Support/iTerm2/DynamicProfiles/ttheme.json` whole: one `ttheme · <palette>` profile per listed palette (`itermProfiles`, `src/terminals/emit/iterm2.ts`), rewritten on every add/remove/browse and reloaded by iTerm2 on its own, plus `ttheme · default` (Guid `ttheme-default`), a copy of the startup palette's profile: `ttheme default` rewrites it, and every tab still on it — new ones and ones never painted — follows within about 0.3 s, which is iTerm2's side of Ghostty's `theme =` and reload. It is also iTerm2's default profile, so a new tab or window is created wearing it and never switches after it opens — a shell that moved a new tab onto it would flash the old profile first, which is never acceptable. `init` and `ttheme default`, and an add, remove or browse that makes a startup palette appear or vanish (never any other, so a default the user picked in iTerm2 stays), point `Default Bookmark Guid` at it through `defaults` (iTerm2's `defaults.point`, `src/terminals/iterm2.ts`, run by `pointDefaults`) and write the profile they replace to `installed.json` as `itermBase`, which every ttheme profile names as its `Dynamic Profile Parent GUID` so fonts, keys and the rest keep coming from the user's own profile; Removing the last palette gives `itermBase` back, and so does uninstall (`pointDefaults` with no palettes); a running iTerm2 takes a new default only at its next start — the notes say so. While off, `ttheme · default` stays as a bare child of `itermBase` (`keeps`: its name, Guid, parent and an empty picture, no colors), and the default stays on it: iTerm2 rebuilds a dynamic profile from its parent and the file's keys at every reload, so a tab on it shows the user's own profile at once and takes the palette back at `ttheme on`, neither needing a restart — while a profile dropped from the file leaves its tabs on a copy of it that `SetProfile=` does not reach (measured on 3.7.3: `mise run compat`'s `on-follow`, and a tab kept its palette through `ttheme off` before). With no palette installed there is no `ttheme · default`; `ttheme on` and `ttheme default` turn it back on, and init's "pick a default palette in ttheme?" answered no installs off. An OSC color divorces a session from its profile until the next `SetProfile`, and a reset does not marry it again (measured: a tab painted and reset kept the old default through a `ttheme · default` rewrite, the model's `kept`), so the iterm2 adapter keeps `TTHEME_ITERM_DYED` — set by every OSC color it sends (`__tt_osc_apply`, `__tt_pv_paint`), cleared by its `SetProfile`s (`__tt_profile`) — and a tab takes a new default only while it is on `ttheme · default` undyed (`__tt_takes_default`; a tab that went off on a profile other than `ttheme · default`, which it cannot name, asks its background once). `TTHEME_ITERM_SUITE` names the preferences domain (`com.googlecode.iterm2` by default); the sandbox sets it to its own suite so nothing reaches the user's iTerm2. `palettes.zsh` carries the startup palette as `TTHEME_STARTUP`, so a shell that opens on `ttheme · default` knows whose picture it shows. Measured on 3.7.2: iTerm2 reads OSC colors as Display P3 (its `p3` default) and reports an sRGB profile color converted, so the profiles and `.itermcolors` are written in P3 or the shell's OSC 11 palette match fails; and a newly added dynamic profile inherits its parent's light/dark split and then ignores unsuffixed color keys, so every profile sets `Use Separate Colors for Light and Dark Mode` false outside `auto` (below).
- Once iTerm2 lets a control sequence change the profile — `PreventEscapeSequenceFromChangingProfile` false, which its Always Allow sets and `sync` reads through `defaults` (`switches`, the iTerm2 wiring's `layer`, which takes the `Host` `sync` is given) into `palettes.zsh` as `TTHEME_ITERM_SWITCH=1`, beside the profiles' path as `TTHEME_ITERM_PROFILES` — the iterm2 adapter wears every palette that has a profile (one in `TTHEME_ORDER`, `__tt_profiled`) by switching the tab to it: its `__tt_osc_apply` sends `OSC 1337;SetProfile=ttheme · <palette>` (`__tt_profile`), its `__tt_osc_reset` switches to iTerm2's default profile (`SetProfile=`, the one new tabs open on) unless the tab is on it undyed already, and its `__tt_pv_paint` hovers that way and records the palette in preview's `painted`, so the frame keeps its ANSI colors. A switch is one profile change where twenty OSC colors are twenty (measured on 3.7.3 at 80×25, a frame and the paint against a DSR 0.15 s apart: 38 ms against 211 ms for the twenty and 51 ms for the background and foreground alone; back to back 13 against 152 and 27 ms; a picture iTerm2 had not shown yet added nothing measurable), and a held arrow key in preview settled 5–15 ms after the last frame either way, at 80×25 and 160×50. A color preset (`OSC 1337;SetColors=preset=…`, read from the domain's `Custom Color Presets`) is no shortcut: iTerm2 sets each of its colors as a profile change of its own (`setColorsFromPresetNamed`), 158 ms. A tab on its palette's profile is never dyed, follows a rewrite of that profile (a tone or picture changed in another tab), and keeps its palette through a program's OSC 111/112, since iTerm2 resets a slot to the value of the profile the tab sits on (compat's `reset-worn`, parity's `program-reset`) — unless an OSC color set the slot earlier: iTerm2 keeps the color a slot had before its first OSC (`_preEscapeSequenceColors`) through every `SetProfile`, and the next reset goes back to that and only then forgets it (measured on 3.7.3: an OSC 11 on konata, a switch to miku, and the first reset showed konata, the second miku — compat's `reset-baseline`, the model's `baseline`). So `__tt_profile` resets the slots the shell dyed (all twenty for `TTHEME_ITERM_DYED=1`, the background and foreground for 2, preview's hover) before it switches, in one synchronized update unless preview holds one already (`TTHEME_RAW`) — about 120 ms more, paid only by a dyed tab, never where the shell may not switch, since a refused switch would leave the reset colors up — and `itermLive`'s `restore` resets the slots it sent before it switches back (parity's `browse-reset`). `__tt_shown` moves a dyed tab onto its palette's profile at its next prompt or focus. iTerm2 reads a rewritten `ttheme.json` about 0.3 s later and ignores a switch to a profile it has not read, so `__tt_profiled` paints OSC colors instead for a second after the file's modification time (`zstat` against `EPOCHREALTIME`, no process) — `ttheme add kita && ttheme use kita` still paints. Without the permission (iTerm2 raises its bar at every `SetProfile` until the user picks, and drops them all after Always Deny) the adapter paints OSC colors and switches profiles only for pictures, as it always did, byte for byte, so a palette still goes on, and the first `sync` after Always Allow moves it over. There a tab that goes on to wear palettes with no picture stays on the profile of the last palette it switched to, and a picture that palette gains later shows in the tab until it switches again: Ghostty's `shown.conf` moves at every claim (`terminals.md`), but here every move would raise the bar, and Always Allow, which puts every wear on its own profile, ends it. Preview puts the tab back on its own palette before another screen takes it (`__tt_pv_leave`, `terminals.md`), since browse leaves the tab's picture where the hover's profile carries the hovered palette's, and believes the tab dyed when it takes it back (the adapter's `__tt_pv_forget` sets `TTHEME_ITERM_DYED` to 1), since browse's hovers dye slots the shell never saw, so its next switch resets them first.
- Under `TTHEME_MODE=auto` every ttheme profile carries both modes (`itermProfiles`' `modes`: each color key twice, ` (Light)` and ` (Dark)`, from `bothModes`, and `Use Separate Colors for Light and Dark Mode` true), so iTerm2 switches a tab on its palette's profile by itself when the system's appearance changes (`sessionViewDidChangeEffectiveAppearance` reloads the profile's colors), as Ghostty's `light:…,dark:…` theme does. The tab hears it as `CSI ? 997 ; Ps n`, which iTerm2 sends under mode 2031 whenever the background's darkness changes and answers DSR 996 with (`terminalIsInDarkMode` is the background's `isDark`, a perceived brightness `0.30r + 0.59g + 0.11b` under 0.5 — the palette's darkness, as Contour's spec has it, not the system's), so the adapter reports it (`__tt_reports_appearance`, `TRAITS.appears: 'reports'`) and reads each report through `__tt_appearance_of`: only from a tab on a ttheme profile undyed (`TTHEME_ITERM_SHOWN` set, `TTHEME_ITERM_DYED` 0) whose palette's two backgrounds read apart (`__tt_iterm_dark`, the same sum in zsh's integers), where a report of the other background's darkness is the other mode and one of the worn mode's counts only while a remode runs (the system switched back meanwhile) — so a tab an OSC color dyed, a tab on the user's own profile and ttheme's own repaints are never taken for the system. Colors ttheme's profiles do not set (`Link Color`, `Use Bold Color`, `Smart Cursor Color`…) are then read from their ` (Light)` and ` (Dark)` keys, which the parent supplies only where its own split is on, else iTerm2's defaults. Measured on 3.7.6, 2026-10-24, in a sandbox iTerm2 (`--trust`) wearing gojo: with the tab idle, switching the system rewrote `palettes.zsh` in the new mode 0.29–0.37 s after the switch began, both ways, and the window showed gojo's light background as P3 `#f2fbfe` and its dark one as `#11191c`; the user's own iTerm2 settings were the same before and after.

## Gotchas

- iTerm2 3.7 keeps its sessions alive in `iTermServer` across a quit and saves dynamic profiles into its prefs (`New Bookmarks`), so a test run can come back on an old session or an old profile's values; a dynamic profile without `Dynamic Profile Parent Name` merges into the default profile, which can be itself. Like Ghostty, it starts shells through `login`, which resets `HOME`.
- iTerm2 3.7 shares kitty placement ids across images — a second image placed with `p=1` removes the first one's — so every placement takes its own image's id (preview's layers, find's tiles). Its `a=d,d=i` frees the image's data along with its placements (the spec keeps the data for lowercase), so preview takes a picture down with `d=i,i=N,p=N` and places it again later without resending; a picture sent earlier and deleted by id alone came back as nothing. iTerm2 drops the least recently used images past 320 MB (about 42 pictures at 1880×1008; Ghostty's `image-storage-limit` defaults to the same size), so `__tt_bg_send` keeps the most recently shown up to 128 MB decoded (sized with `__tt_bg_dim`; a tuned picture can be a full 25 MP original) and frees the rest itself (`d=I`), resending one when it comes back, and `__tt_bg_forget` frees them all at a resize, `find` and close. It leaves `CSI 16t` unanswered, so cell sizes come from `OSC 1337;ReportCellSize` (points and a scale) first. `SetProfile` raises a permission bar until the user picks Always Allow; any keystroke dismisses it as a denial.
- iTerm2 3.7 turns every OSC color into a profile change: its parser pauses on each one (`addUnmanagedPausedSideEffect`) while the main thread copies the session's profile, logs the change and reloads every setting from it (`setSessionSpecificProfileValues`) — about 6 ms apiece at 80×25 and 9 ms at 160×50 (3.7.3, against a DSR round trip), so a palette's twenty kept iTerm2 busy for 170–200 ms a preview hover and an arrow key held at 30 Hz kept preview moving for 0.8–1.9 s after release, where Ghostty answers such a frame in 0.1 ms. A hover therefore paints through `__tt_pv_paint`: the default paints the whole palette and records it in preview's `painted`; the iterm2 adapter paints the background and foreground alone (OSC 11, 10), and while the terminal does not hold the hovered palette (`applied` ≠ `painted`) the frame spells its ANSI colors out in truecolor — bold blue as bright blue, as iTerm2's default Brighten bold text draws it — which iTerm2 reads in the same space as an OSC color (`p3`), so the frame looks the same, iTerm2 answers a hover in about 35 ms (mostly its 1/30 s report tick) and a held key stops within 25 ms of release. Picking paints the other eighteen once (110–160 ms, paid once) inside the synchronized update that leaves the alternate screen, so the shell's screen comes back in its final colors rather than changing one color at a time; `find` gets the whole palette painted first, since it draws with ANSI colors. This is the path where the shell may not switch profiles; where it may, a hover is one profile switch instead (above). `latency.zsh check` fails when a hover in iTerm2 paints an ANSI color again, or any OSC color where it may switch profiles. Timing iTerm2 behind other windows needs its `DisableAppNap` setting: napping, a bare DSR round trip takes about 200 ms instead of 20, and a DSR answer always waits for iTerm2's side-effect tick (1/30 s).
- iTerm2 3.6 and later symbolicate a call stack for every profile they replace: `-[ProfileModel setBookmark:atIndex:sideEffects:]` logs `[NSThread callStackSymbols]` unless `performWithLessLogging` (which only tmux sessions take; 3.5.14 logged no stack), so every OSC color — a session profile change — and every dynamic profile at a reload pays a `backtrace_symbols`, whose `dladdr` scans iTerm2's symbol table. Sampled on 3.7.6 with the 217 profiles of a copy of a 216-palette install: a rewrite of `ttheme.json` held the main thread 1.5–2.6 s whether or not anything in it changed (a mode switch's sync included, and from another terminal's tab as much as iTerm2's), 78–86% of it in `backtrace_symbols` and the rest in `indexOfProfileWithGuid:`, which matches an empty filter against every profile before the one it looks for; timed from inside a session (a cursor report kept in flight; one session open), a copy of 3.7.6 took 2.34–2.38 s to answer after an unchanged rewrite of the 217, 362–399 ms with `reloadDynamicProfiles` run under `performWithLessLogging`, and 121–136 ms with `indexOfProfileWithGuid:` also skipping the filter when it is empty (both swizzled in, the fast path checked against the original on every lookup), and as long with four sessions open (2.36–2.38 s in three of four rewrites, 112–124 ms with both) where the measuring session is the one in front — one hidden behind the others answered 0.7–1.0 s after a reload with both changes in, iTerm2's slower pace for a session out of sight rather than the reload's —, while twenty OSC colors took 207–285 ms and 125–179 ms with no stack symbolicated at all — the rest of an OSC color is iTerm2's own pause for each. Nothing ttheme writes changes the cost per profile — only how many profiles the folder holds, how often it is rewritten and how many reloads a rewrite starts: iTerm2 reloads the folder once for every FSEvents event it hears there (`iTermDynamicProfileManager`'s `pathWatcher:eventOccurred:`, which SCEvents calls once per event), and four saves through a temp file made in the folder reloaded it eight times where a `touch` reloaded it once (counted on 3.7.6, 2026-10-24), so `sync` makes `ttheme.json`'s temp file in `iTerm2/` beside the folder and renames it in (`itermSupport`, `Out.write`'s `aside`, `writeAtomic`), which also keeps iTerm2 — which reads every file there but dotfiles and `~` backups as a profile file — from ever reading a half-written copy; `tests/costs.tsv` counts the entries each action makes in a folder a terminal watches, so a write that puts one back there fails it.
- iTerm2 3.7 keeps its default profile in memory: it reads `Default Bookmark Guid` at launch (and then adopts a dynamic profile it names), and writes its in-memory value back whenever that profile is replaced — a dynamic default is replaced on every dynamic-profile reload, so while the default is dynamic an outside write is undone within a second. No AppleScript command, escape sequence or dynamic-profile key sets the default (it strips `Default Bookmark`, issue 4115), a dynamic profile whose Guid a regular profile has is refused, and the Python API that can is off until the user enables it. A child profile's `Keyboard Map` replaces its parent's whole, so ttheme sets no key bindings.
- iTerm2 3.7's Metal renderer flips the `y` of a kitty source rectangle (asking for the top half draws the bottom one; the legacy renderer, which iTerm2 falls back to on battery, does not — `mise run compat`'s `kitty-crop`, measured again on 3.7.3, and the sandbox keeps Metal on whatever the power source so that a run on battery measures it), and it draws no placement that leaves the grid, relative or not — so there is no way to show part of a picture vertically except cutting it first, which find's band worker does for the tiles its grid cuts and the iterm2 adapter's `__tt_bg_crop` does unless the crop is centered — one `ttheme bake` with the band's rows as its canvas, an exact copy, on preview's first hover on each picture when the window is wider than the picture (95 ms through the bundle on a 2142×2214 figure, where `sips` took 206 for a top band, which it had to pad first since `--cropOffset 0` means centered, and 94 for any other), baked by `_bg.zsh`'s background runner (`terminals.md`): the picture on screen stays until the band is there (`__tt_bg_crop` answers 2, so `__tt_pv_bg_show` leaves the placement and forgets `bgname`), and a band that could not be baked is not asked for again (`__tt_bg_done`) — a tuning step that needs a new band answered in 98–110 ms and answers in 9–13 ms; each band is sent once and placed after that. Its `ED 2`, and `CSI H CSI J` in the alternate screen, push the whole screen into scrollback, kitty placements included, so preview and find clear with `\e[K\e[2H\e[J` and delete images with `a=d,d=A` instead.
