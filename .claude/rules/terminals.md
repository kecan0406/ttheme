# Terminals, pictures and the shell layer

## Conventions

- A palette keeps every picture installed on it, and `backgrounds/images.json` (`Store`, `src/pictures/backdrop.ts`, versioned) is the one record of them: per palette the pictures in install order — key `<site>_<id>`, stem, `@fill` crop, default opacity, the `tone` and `blur` its files were drawn with and the `window` its fill was framed for, `# from` source, the `artist` names and the artwork's `source` page, original under `originals/` and, for a Vision cut-out, the cut's alpha beside it (`cut`, the mask as Vision made it, which every draw mattes, and `matte`, the `MATTING` its files were drawn with) — and which one is `active`. Only the CLI writes it (`installBackdrop`, and `ttheme image <palette> show|drop [<picture>]`, a hidden verb in `src/cli/images.ts` that preview calls when its tuning panel's picture strip is kept and on `D`), and every write regenerates that palette's `backgrounds/<palette>.conf` from it, which is a view for the terminals: the active picture's `# by <artist>,<artist>` (names with no space or comma, only when it has any) and `# from`, `# image <key> <at>/<of>` (the shell reads the count from it), a `# picture <key> <stem> <fill> <opacity> <artists|-> [<from>]` line for every picture the palette holds (preview's strip reads them; `bgby` carries the artists, which the credit line of preview's Image box names first and keeps longest as the box narrows (`__tt_pv_bg_credit`: `by <artists> · ⧉ <artwork> · ⧉ <post>`, the post dropped before the artwork), and `bgurl` the `# from` line's page, which makes the post a link marked `⧉` in its site's color — `TTHEME_SITE_ANSI` in `palettes.zsh`, from `SITES` — where the adapter opens OSC 8 links), and per picture a `# credit <key> <line>` (`creditLine`, `src/core/artists.ts`: the artists, each with a page to follow them on — X, else pixiv or Bluesky, never the artwork page's own site —, then the artwork's page or else the post's, `shima.donmai.us` named `danbooru.donmai.us`; control characters dropped), a `# source <key> <label> <url>` for an artwork page (`pageLabel`: `pixiv <id>`, `x <handle>`, else the host) and a `# profile <key> <artist> <kind> <url>…` per artist with pages (`bgcred`, `bgpage`, `bgprof`, keyed `<palette>:<key>` and read with the palette's own conf); the Image box is 19 rows, its second line the artists' pages marked `⧉` in the accent (`__tt_pv_bg_profiles`, empty where the tab opens no links), and `y` copies the `# credit` line (`__tt_pv_bg_copy`: `pbcopy`, `wl-copy` or `xclip`, else and over SSH an OSC 52 through `__tt_out`), with no CLI verb behind it; its `@fill` crop, and includes of that picture's own `<stem>.tune.conf` and `<stem>.off.conf`. `sync` rewrites every conf whose text differs from what the store makes (`freshenConfs`), so an upgrade's first init brings the older confs up to date. A picture's files are `<palette>.<hash>.png` (the figure), `<palette>.<hash>@fill-N.png`, the bakes preview makes on the same stem, and its tuning — all beside each other and never moved, so switching only changes `active` and the conf, and `drop` deletes the stem's files and the original. The hash is of the key and the images' content, because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name. Every picture file (figure, fill, the CLI's bakes) is an 8-bit indexed PNG whose 256 palette entries are all the tone and whose tRNS ramp makes the index the alpha — the ink, luma × alpha of the original, lifted until its top 1% reaches the tone (at most ×2, `liftOf`) and blurred by `TTHEME_BG_BLUR` — so the terminal's own straight-alpha blend over the background draws the tint (Ghostty's `bg_image` shader, and iTerm2, which then draws the same gamma-linear ramp Ghostty does where it used to darken a full-color tint's midtones — measured) and no pixel carries the background; the bakes preview saves keep that format, since `ttheme bake` (`runBake`, `src/cli/images.ts`) lays a tone picture as its alpha alone (`layMask`, with the tone `toneOf` reads off the file's palette) and an original-coloring one as RGBA. A palette whose `backdrop` tone changes is repainted by `sync` (`retint`): the files' PLTE is swapped (a file that is not indexed is re-encoded from its alpha), they move to a new stem and the tuning moves with them; the opacity never follows the palette — a picture keeps the one it was installed with (or switched coloring to) and any it was tuned to. A `blur` that no longer matches the setting, a picture with no `tone` (drawn before this format), a cut-out whose `matte` is not `MATTING`, or a tone picture whose palette changed mode (`inkDue`) is drawn again from its original by `redrawPictures` (`src/cli/redraw.ts`, a pool of render workers running `redrawOne`, `src/pictures/redrawing.ts`) — or laid from the drawing cache with no worker and no original where the cache holds its drawing for that blur and ink (below) — at every `init` after it applies, in the hidden `ttheme sync` before it writes a terminal's file (`runSync`, which `ttheme dark`, `light` and `auto`, `ttheme config`, preview's Mode row and `auto`'s remode all run through `__tt_resync`, so the pictures of a mode and the files that name them are written once, where a `sync` and then a `redraw` wrote Warp's and iTerm2's twice and recolored pictures the redraw drew again), and through the hidden `ttheme redraw` that `ttheme config` runs when the `TTHEME_BG_BLUR` line changed and preview's alt-c panel runs when its `blur` row is saved; a picture drawn before cuts were kept finds its cut in the find cache or asks Vision again, and one without an original is left as it was. The CLI reads `TTHEME_BG_BLUR` from `config.zsh` itself (`blurOf`), never from the environment `__tt_cli` hands it, since an older shell still holds the old value and would draw every picture back. Tuning belongs to the picture, not the palette; the shell layer takes the file names from the conf's includes (`bgtunef`/`bgofff` in `__tt_bg_load`), falling back to `<palette>.tune.conf` for a conf the user wrote. In preview a picture's state is keyed by the palette for the active one and `<palette>:<key>` for the others (`__tt_bg_load` makes their conf lines from the `# picture` line); the tuning panel's strip (`__tt_pv_bg_strip`, up to five thumbnails of the pictures' fills as kitty placements `p=700001`–`700005` at `z=-1`, drawn by `__tt_pv_flush` after the frame so a resize's `d=A` cannot take them) follows `,` `.`, which only change what preview shows (`tpick`); enter keeps the tuning of every picture touched (`bgedit`) and the choice (`bgview`, `bgswap`), esc puts back every picture's state from when the panel opened (`tsnaps`), and the preview's close writes the tuning first and then shows the kept picture with `ttheme image <palette> show <key>`. `=` puts the field under the cursor back to the conf's defaults and `+` all of them, and a `↺` marks each field off its default. `f` and `D` change what the palette holds, so they write its kept tuning first and read it again after (`__tt_pv_bg_commit`, `__tt_pv_bg_reset`); installing the same post again starts from the defaults (the old stem's files go). A missing `images.json` is built once from the layout before it (`migrate`: the shown conf plus `backgrounds/shelf/<palette>/<key>/`), keeping a picture whose conf has no `# image` line under `picture_<hash>` rather than dropping it, and leaving a conf ttheme did not write alone and out of the store; `sync` opens the store, so an upgrade migrates at its first `init`, add or remove. Every file a terminal or another shell reads — the store, the confs, `palettes.zsh`, `installed.json`, the iTerm2 profiles — is written to a temp file and renamed over (`writeAtomic`, `src/store/edits.ts`; `__tt_put` in `ttheme.zsh`, which writes through a symlink to its target, ignores `noclobber` and renames with zsh/files' `zf_mv`, so a picture change forks nothing — `config.zsh`, the pins file and the remembered colors go through it too), so a reload never reads half a file. There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which ttheme's `~/.config/ttheme/ghostty.conf` (the file the ghostty block includes) always includes. Wearing a palette — `ttheme use <name>`, preview's enter, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: focus reporting (mode 1004) is on at every prompt and off during each command (`__tt_preexec`), Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd), which sets `TTHEME_FRONT`, and `\e[O` on `__tt_blur`, which clears it — so the picture belongs to the tab you are looking at, not to the last tab that switched. Only a tab the terminal has said is in front takes it: the ghostty adapter's `__tt_shown` writes nothing unforced while `TTHEME_FRONT` is 0, every prompt a command ended in sets it to 0 (`__tt_prompt`, while `TTHEME_RAN`: focus may have moved while the command ran with reporting off) until the answer to the reporting `line-init` turns on says otherwise, and a verb typed in the tab (`ttheme use`, preview's enter, `on`) claims with `force` — so a command that ends in a tab behind leaves the picture of the tab in front (parity's `prompt-behind`; it used to take it at its prompt). A shell that never heard a focus answer (`TTHEME_FRONT` stays -1: a `.zshrc` that replaces `zle-line-init`, so reporting never turns on) claims at every prompt as before. A tab busy with a program cannot hear its focus at all; Ghostty's follower (`ghostty.md`) puts its picture up. Where a verb changes this tab's colors and its picture together — `ttheme use`, `on`, a pin reached by `cd` or set in another tab — it goes through `__tt_wear` (spec, palette, `force`), and the ghostty adapter's claims first and paints after: it writes `shown.conf`, reloads, and waits for Ghostty to read the new file (`__tt_ghostty_took`: `shown.conf`'s atime passing its mtime — APFS stamps the first read after a write — at most 0.1 s, then 3 ms more so the reload reaches the surfaces), so the OSC colors land while the renderer decodes the picture and both change in one frame (measured frame by frame in a sandbox Ghostty, with and without twelve tabs and a custom shader; painting first showed the new colors over the old picture for 45–165 ms). The wait runs only when `__tt_reload_ghostty` signaled a Ghostty (`TTHEME_GHOSTTY_SENT`), and every other adapter's `__tt_wear` paints first as before. Preview's enter does the same before it closes (`__tt_pv_claim`), while its kitty layers still cover the grid, unless the panel changed a picture (`bgedit`, `bgswap`), whose save reloads again. A tab switch still shows the previous tab's picture for a moment, which no layer can prevent: the picture is one app-wide setting while the colors belong to each surface, and a tab shown again first presents what it last drew (or, hidden long enough, only its background color), then Ghostty draws it live with the picture the app holds, and only the reload its claim sends brings its own — Ghostty queues the surface's `visible` message ahead of that reload on its main thread, so even a tab at its prompt, which claims on its focus-in within a millisecond, shows the old picture for a frame or two (0–33 ms measured). Ghostty's `Path.equal` compares the path slices by pointer (`std.meta.eql`), so every reload also decodes the picture again in every surface and, with a `custom-shader`, recompiles every shader — the new tab once when it is shown and again on its claim's reload (its log says `loaded custom shader` each time). A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own — though `shown.conf` still moves to the new one: it always names the palette the tab in front claimed, picture or not, since a line left naming a palette whose last picture went would bring that palette's next picture up behind whichever tab is in front (`shell/check.zsh`).
- A picture can keep its own colors instead of the tone (`Picture.coloring`, `'tone'` when absent; `Coloring` in `src/core/backdrop-tone.ts`): an 8-bit RGBA PNG of the original's colors and its own alpha (a cut-out's, or none), blurred as premultiplied planes (`blurColors`), placed with the same `fillFrame`, lifted by nothing, and carrying no `tone` — `undrawn` is a picture with neither. Every terminal lays it over its background at `background-image-opacity` exactly as it lays a tone's ramp, and preview's veil and the kitty and WezTerm handlers never read a pixel, so no adapter names the coloring; the only shell code that does is the `# colors <key> original` conf line (`confText`; `bgcolors`, `__tt_bg_coloring`) and the tuning panel's fourth row and its `c` key from any row, which call the hidden `ttheme image <palette> tone|original [<picture>]` (`redrawColoring`, `src/cli/redraw.ts`) and reopens on the same picture (`__tt_pv_bg_recolor`) — the coloring is a redraw from the original, so it is never staged or undone with esc. The redraw takes 0.5–0.75 s on a 3000×3000 cut-out JPEG and about twice that at 25 megapixels (end to end through the bundle, measured with `redrawOne` as 98% of it), so `__tt_pv_bg_recolor` and `__tt_pv_redraw` draw their note first and take nothing off the screen while the CLI runs (no `__tt_pv_bg_close`, no `__tt_pv_bg_strip_off`, and `__tt_pv_tune_stage` — `__tt_pv_tune_keep` without the strip's removal — runs after the draw): the old picture, thumbnails and sliders stay up, and the next frame is a `resized` one, whose wipe and show sit in one `2026` frame. The drawing itself is kept (`src/pictures/drawn.ts`, `$XDG_CACHE_HOME/ttheme/drawn/<key>`, one file per drawing holding the figure, the fill, their names and the tone its palette carried, at most 512 MB with the least recently used going first — a hit counts as a use — and a write that never finished going an hour after it began): `drawnFor` in `src/pictures/backdrop.ts` keys it on `DRAWING` (bump it whenever `draw`, `made` or the encoders change what they produce), the palette's file stem, the picture's key, the original's and the cut's size and modification time, `MATTING` for a cut-out, the window, the blur, the coloring and, in the palette's tone, whether its ink is the light one — not the tone color, which only fills the file's palette: a hit swaps it for the tone the palette has now (`toned`, `retone`), the same bytes and so the same stem a fresh drawing in that tone gives, so a tone edit or a release that moved a mode's colors leaves the kept drawings good — and a hit skips the decode, the draw and the encode (`redrawOne` decodes only through the thunk `redrawn` calls on a miss). `redrawn` also keeps the drawing a coloring or ink change replaces (`remembered`, from the picture's own record and files, only when `blur` and `window` are on it), so going back is a hit, and `ttheme image <palette> prepare [<picture>]` (`prepareColoring`, `prepareOne`) draws the other coloring into the cache without touching the store or `backgrounds/` — which `__tt_pv_bg_prepare` runs detached, once per picture and coloring and never beside another (`bgprep`, `bgprepid`), whenever the tuning opens on a picture or moves to another (`__tt_pv_tune_open`, `__tt_pv_bg_pick`; a recolor marks the coloring it left as ready). A mode switch needs no such call: `redrawPictures` draws the other ink of every tone picture that is not turning ink in this pass and whose original starts as a PNG or a JPEG (`decodable`: a one-byte original is never retried at every `sync`) into the cache (`prepareOne` with the other mode's paint, `inMode`, as a `prepare` job on the pool after the pictures that are due), at every `init` and every `sync`, so the first switch finds it ready as the later ones find what the switch before kept, and it lays a picture whose drawing is cached in the main thread (`cached`, then `redrawOne`; 72 pictures took 76 ms) and sends only the misses to the pool. A drawing that writes a cut-out (`cut`) is never cached. Measured through the bundle on a 3000×3000 cut-out JPEG: 0.70 s (original colors) and 0.38 s (tone) without it, 45 ms with a hit. Measured on a copy of a 215-palette install with 72 tone pictures, Ghostty, iTerm2 and Warp wired, on an Apple M4: a switch took 8.3 s (`sync` 2.85 s, `redraw` 5.4 s, 17.6 s of CPU and 2 GB at its peak) and takes 0.23 s with the other ink ready (an unchanged `sync` takes 0.13 s) and 4.1 s with the cache empty, the first `sync` after an upgrade takes 4.8 s to get the other ink ready once, and the pictures laid are the ones `sync` then `redraw` laid, byte for byte (102 of 102 stems, 205 files). Its default opacity comes from its `peak`, the color of the brightest 1% of its visible pixels by relative luminance (`peakOf`): `originalOpacity` is the highest opacity at which the palette's text passes the gate on that color and it is no brighter than a tone picture may be (`fade`, shared with `toneFor`, which leaves out the rules the palette misses with no picture at all, so a palette that already misses the gate still gets the opacity its picture allows), so a picture with white in it opens at about half a tone's opacity. A palette whose colors change leaves it as it is; redrawing into the other coloring keeps size and position and drops a tuned opacity, whose scale differs. `TTHEME_BG_COLORS` (`coloringFor`, read from `config.zsh` like the blur) only names what `find` and `add` install from now on; it never redraws.
- The `<palette>.conf` a terminal reads has one grammar, and `src/pictures/conf.ts` owns it: the keys it names (`CONF_KEYS`), the include it follows (`CONF_INCLUDE`, `CONF_OPTIONAL`) and how deep (`CONF_DEPTH`). `readConf` reads it, `confText` writes it, and the kitty watcher (`emit/kitty.ts`) and the wezterm module (`emit/wezterm.ts`) read it through readers generated from the same constants (`confReaderPython`, `confReaderLua`) — so the three readers cannot disagree on what a conf says, and the shell layer (`_bg.zsh`) reads the same keys and its own metadata lines (`# picture`, `# credit`, `# source`, `# profile`), which no other reader takes. `src/pictures/conf.test.ts` holds the format, the depth at which an include chain ends, and the shell layer's copy of the keys; `src/terminals/conf-readers.test.ts` runs the generated Python and Lua under their interpreters where they are installed and holds them to the TypeScript reader, so a change to the format reaches all of them at once. A palette's file stem is one rule too (`STEM_RULES` in `src/core/theme.ts`, `stem`), rendered into Python, Lua and zsh from it (`src/terminals/emit/stem.ts`), and `src/terminals/stem.test.ts` fails on a mangling anywhere in `shell/` that is not the canonical form — the way `style.test.ts` fails on an SGR written outside `style.ts`.
- One setup can wire several terminals, and a change made from any reaches all of them. `palettes.zsh` carries the wired terminals as `TTHEME_TERMINALS`; preview's saved pictures go through `__tt_bg_saved` (`_bg.zsh`) to `__tt_pictured` (`_wired.zsh`), which rewrites `ttheme.json` when iTerm2 is wired and reloads Ghostty when `shown.conf` names one of them; `ttheme default` and an install change that moves the startup palette (`__tt_installs`) reload Ghostty too. `__tt_reload` reloads only the wired terminals that have a `__tt_reload_<id>` (Ghostty). Tuning is written for every wired terminal: with iTerm2 wired, a picture that is not centered is baked at the window size even when it is tuned in Ghostty (`__tt_bg_aligns`, and `aligns` on the CLI's side, from the wirings' `bakes`), since iTerm2 cannot place one.
- Every terminal ttheme wires is one module in `src/terminals/` (`WIRINGS` in `index.ts`, ids in `WIRED`) implementing `Wiring` (`types.ts`), and `src/cli/sync.ts` only orchestrates, naming none: `sync` builds one `Ctx` and runs every wired terminal's `sync` through one `Out` (`write` content-compared and atomic, `wire` through `editUserFile`, `themes` for the emitter's files under its `shelf`, `remove`, and `repaint` when open tabs must repaint), then rewrites `palettes.zsh` with each wiring's `layer` values; `wiringPlan`, `wiringNotes` and `wiringNext` are init's lines, `forget` drops removed palettes' theme files, `refreshPictures` follows a picture change, and `unwire` gives uninstall its edits, removals and touches (every wiring, whatever `installed.json` says). A terminal whose default is a profile (iTerm2, Konsole, Terminal.app) has `defaults`: `base` keeps the user's own in `installed.json` (`itermBase`, `konsoleBase`, `terminalBase`), and `point` moves new tabs to ttheme's profile or gives the user's back, returning whether a running app needs a restart; `commit` runs them (`withBases`, `pointDefaults`) when a startup palette appears or vanishes, when `default`, `on` or init ask (`take`), or when the startup palette changes — without `take`, a terminal whose current default is not ttheme's keeps it. Every external command a wiring runs (`defaults`, `pgrep`, `dbus-send`, `cmd.exe`, `wslpath`) goes through `Host.run` (`systemHost`), which the tests fake. A new terminal is a module, an emitter, a `TRAITS` row and an adapter, and `src/terminals/index.test.ts` holds them together and to the support tables.
- An `Emitter` (`src/terminals/emit/types.ts`) writes the **archive** — what `ttheme build` puts in `dist/` and a release carries, and what a user installs by hand — while a terminal's `Wiring` writes the **install**: the same theme files under the user's own paths (`out.themes` puts the emitter's files under the wiring's `shelf`), plus the terminal's block, profile or scheme. The two are different artifacts and never pretend to be one: `src/cli/archive.test.ts` holds every file an emitter ships to the file the install writes, byte for byte, and a terminal whose install writes another form of what it ships names the file and the reason in that test — iTerm2's dynamic profile against the archive's color scheme plist (the profile carries the picture, the plist cannot), Windows Terminal's fragment against the archive's scheme files (the fragment also names the profile to update, which a user-agnostic archive cannot), Konsole's scheme with the palette's picture against the archive's without. A terminal that writes its own theme file instead of `out.themes` fails that test, and one that changes a color in one form and not the other fails it too.
- The shell layer names a terminal only in `ttheme.zsh`'s detection block; `preview.zsh`, `_osc.zsh` and `_bg.zsh` name none, and an adapter names only itself (`terminal.test.ts`). Everything a terminal does differently is an adapter hook overriding `_osc.zsh`'s default — the paint and reset (`__tt_osc_apply`, `__tt_osc_reset`, `__tt_pv_paint`, `__tt_reset_reloaded`), what it hears at start (`__tt_hear`, `__tt_heard`), pictures (`__tt_shown`, `__tt_unshown`, `__tt_bg_*`), `__tt_reloaded`, `__tt_worn`, `__tt_keepable`, `__tt_follows_focus` (bind focus reporting: every terminal that reports focus changes — Ghostty, iTerm2, kitty, Alacritty, WezTerm, Windows Terminal, Konsole, and Terminal.app, which answers no DECRQM but sends `ESC [ I` and `ESC [ O` (measured by hand on 2.15, 2026-10-02: activating Terminal, raising another of its windows and coming back gave in, out, in — recorded as its `focus-event`, which the harness itself skips on macOS); `latency.zsh forks` reads it from the adapters), `__tt_takes_default` (whether a tab that never painted shows a new startup palette, below), `__tt_reverts` (whether a program's OSC reset takes a painted tab back to the config's colors, below) and `__tt_paints`/`__tt_unpainted`: in a terminal the layer cannot paint (a Warp that is unwired or has no settings file, and an editor's built-in terminal) the layer stays inactive and refuses the tab verbs (`TTHEME_TAB_VERBS`, from `src/cli/verbs.ts`) and the bare menu with that terminal's own message, unless its `__tt_unpainted` makes it paint — an interactive Warp with a `settings.toml` that init did not wire runs `ttheme wire warp` (`src/cli/wire.ts`, a hidden setup verb that lists what the wiring edits, as init does, asks, and syncs that one terminal in, pointing only its defaults), then reloads `palettes.zsh`, registers the layer's hooks (`__tt_hook`, which a shell inactive at start never ran) and goes on with the verb; `__tt_links` says whether the tab opens OSC 8 links (`TTHEME_LINKS`, and Konsole's own, `konsole.md`); `__tt_follows_prompt` has the layer add the adapter's `__tt_prompted` to every prompt (Warp). What a wired terminal needs when another tab changes the state they share lives in `_wired.zsh`, one `__tt_<event>_<id>` per terminal behind `__tt_reload` and `__tt_pictured`.
- A tab that never painted (`TTHEME_PAINTED` unset: a new tab in `off`, or one reset since) shows what its terminal shows new tabs, so when `palettes.zsh` names another startup palette — seen by `__tt_fresh` at a prompt, a focus, the start of every `ttheme` command and the wake below, and by `__tt_keep` and `__tt_installs` in the tab that ran the command — `__tt_follow` moves the shell's belief to it and syncs its picture wherever the adapter's `__tt_takes_default` says the tab shows it: Ghostty's reload, kitty's and Alacritty's, WezTerm's, Windows Terminal's reset and Warp's theme repaint such a tab themselves, iTerm2 only while the tab is on `ttheme · default` undyed, Konsole once the adapter switches its scheme, Terminal.app once its adapter paints the new palette where init wired it (never where it did not). Such a tab stays one when something only passes over it: leaving a pin it entered unpainted wearing the default (`TTHEME_BASE_BARE`), an ssh session it started that way (`TTHEME_SSH_BARE`), and in a tab that was unpainted when preview opened (`pvbare`) preview's esc (`__tt_pv_unpaint`), its Default picking the palette that already is the default, a pin preview sets (which hands `__tt_pin_save` that flag, since a hover has painted the tab by then) and the hub handing the tab to Browse (`__tt_pv_leave`) all give it back with the adapter's reset (`__tt_osc_reset`, reached through `__tt_unwear` — which also believes the startup palette where `__tt_takes_default` says the tab shows it — for a pin left, an ssh session ended and the pin preview sets) rather than by painting the palette again, so it keeps following the default; a palette picked — `ttheme use`, preview's This tab — and `ttheme on` paint it. `ttheme default` changes the default alone: the tab that ran it keeps its own palette and picture (`__tt_keep` syncs the picture of what the tab wears, forced only for preview's Default, which paints the tab first unless it picked the default the tab already follows). `ttheme()` runs `__tt_fresh` before any verb (`__tt_verb`, once its help and unknown-command checks pass), so a palette added in another tab is worn at once even where no focus is reported, and an uninstalled layer drops out right there.
- Preview shows one palette at a time, its subject — `an`, the palette row the cursor last stood on (a catalog row keeps it), or the palette its panel edits — and draws both halves of it from there on every frame: `applied` is its colors and `__tt_pv_want` names its picture, while `painted` and the layers' `bgname`, `bgshown`, `bganchor`, `bgsent` and `bgthumb` only say what the terminal is believed to hold. Whatever deletes the layers forgets them in the same breath (`__tt_pv_bg_lost`, an adapter hook, from the `resized` frame's wipe and from every adapter's `__tt_pv_bg_close`), so no caller resets them by hand — a change to the shown picture's own tuning only marks it to be shown again (`bgname=""`) — and that frame lays the subject's picture again (`__tt_pv_flush`) wherever the cursor stands — the hub's `tab`, which switches from a catalog row, used to come back with `bgname` empty, so no layer came back, and with Ghostty's `bganchor` still 1 for an anchor the wipe had deleted, so every relative placement after it failed silently (`q=2`) and the picture stopped following the cursor while the colors did. ## Gotchas

- The layer runs inside the user's shell, under whatever options their `.zshrc` set, while every test runs it under zsh's defaults — and `no_clobber` (Prezto sets it) made its writes fail, `ksh_arrays` and `sh_word_split` misread its arrays and arguments, and `no_unset` stopped it loading at all. So every function the shell calls on its own — `ttheme`, each hook, zle widget and the completion — and each block that runs while the layer is sourced starts with `emulate -L zsh ${=${options[xtrace]:#off}:+-o xtrace}` (about 3 µs; the xtrace clause keeps `set -x` and the fork counts working in hooks and functions, which a bare `emulate` switches off — zle turns xtrace off for a widget's whole run, so inside a widget the clause has nothing to keep). `terminal.test.ts` holds every function the layer registers to it, and `latency.zsh check` sources the layer under such a `.zshrc` and uses it.
- Every question the layer asks the terminal goes through `__tt_ask` (`_osc.zsh`): it opens the tty as `{ exec {fd}<>/dev/tty } 2>/dev/null`, because an `exec` with no command applies all its redirections to the shell for good — the plain `exec {fd}<>/dev/tty 2>/dev/null` sent every later command's stderr to /dev/null (measured). It sets the tty up in one `stty` subshell (save, raw, then restore: about 5.7 ms of forks against a 0.1 ms answer, measured) only while the tty is still cooked — never inside zle, which holds it raw already (`zle` answers true there), nor inside preview, which holds it `-echo -icanon` for its whole session (`TTHEME_RAW`) because zsh's own `read -s -k` restores the modes between characters: keys arriving while preview drew were echoed into its frame (39 of 60 held arrows at 160×50, measured; `latency.zsh check` types into it). It appends a DSR (`\e[5n`), reads whole chunks with `sysread -t 0.3` until its `\e[0n`, so it ends as soon as the terminal has answered everything, and then splits the bytes with one pattern: a byte outside an escape sequence is a key the user typed ahead: it goes to `TTHEME_TYPED`, which the `__tt_typed` line-init widget hands back to zle (`zle -U`), so a command typed while the shell starts still runs. Preview drops them (`__tt_pv_bg_open`) — those keys were meant for it.

- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. An app `open` starts keeps that environment in every tab until it quits, and Warp hands it on through its update relaunch (`open -n` from Warp itself), so the sandbox opens the user's own Warp and Terminal.app from `env -i`. Started from Claude's shell, Warp carried `CLAUDECODE`, the sandbox's `HOME` and `ZDOTDIR` and every other variable of that shell into each tab: the user's own tabs sourced the sandbox's `.zshenv` hook, so a run's hang-up and compat's `exit` closed them, and Warp read the sandbox's `~/.warp`, which failed compat's `osc-reset`, `restore` and `layer-query` (measured 2026-09-30; a probe app took the whole environment through `open <url>` and `open -a` alike). It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- Ghostty, Alacritty and Warp leave OSC 17 (selection) queries unanswered (`mise run compat`'s osc-selection; Ghostty's `stream_handler.zig` logs "reporting dynamic color highlight_background not implemented"), so a query that waits for every color it asked stalls until its deadline — `queryTerminalColors` (`src/terminals/osc.ts`, browse and init's picker) ends at a DSR answer instead, which took 120 ms off every browse in those terminals.
- Preview's search box is browse's — a `Preview (n/m)` heading over a boxed `⌕` search from 22 rows (`tall`; `hd` rows above the list, which the list's rows, its zones, the page step `pvhd` and the help's top follow), one `⌕` line with the counts below that — and its hint animates on a timer, and those ticks redraw the search row alone (`tick`, `__tt_pv_draw hint`, `pvsr`): a full frame is about 4 KB and 3.6 ms at 160×50, and the hint had been 9 KB a second of redraws while preview sat idle. The row starts with ECH over the list's columns, never `\e[K`, which would take the right panel on the same row with it — and it must, since the box's right edge is placed with CHA, which would leave the old text between the typed filter and the edge.
- Ghostty applies a SIGUSR2 reload asynchronously, an OSC reset returns a surface to the defaults Ghostty holds at that moment, and a reload does not repaint a surface's current colors (measured) — so a reset sent right after the config changes brings back the old `theme =`. `ttheme off` therefore writes everything first, reloads once, and `__tt_reset_reloaded` (ghostty adapter) resets again every 50 ms while the tab still shows the palette's background, for at most a second. Every other open tab turns itself off too (`__tt_off_here`) when `__tt_fresh` sees `TTHEME_STARTUP` go empty: at once where it sits idle at its prompt, since the wake below signals it, and otherwise at its next prompt or focus (parity's `off-idle`) — and the tab that ran `off`, in whatever terminal, first empties Ghostty's `shown.conf` where Ghostty is wired (`__tt_unpictured`, `_wired.zsh`, from `__tt_switch`) before its reload, so Ghostty's picture goes with that one reload whichever Ghostty tabs exist, are busy or are in front, and the woken ones find nothing left to claim (parity's `off-beside`) — and a tab running a program, which has neither, is reset by Ghostty's follower through its tty when it comes to the front (`__tt_ghostty_unpaint`, `ghostty.md`), which takes the picture down with it (`off-reach-busy`); a pin paints nothing while `TTHEME_STARTUP` is empty (`__tt_dir_sync` and `__tt_ran` return at once), and neither does a rotating new tab (the layer's start and `launch-tab.zsh` check it too, parity's `off-seq`), so off is off for pins, ssh hosts and the rotation too until `ttheme on`; `ttheme on` paints the tab that ran it with its directory's pin, else the default (`__tt_resume`), and every tab that went off takes the default back from the reloaded config and learns so at its next prompt or focus (`__tt_follow`), where its directory's pin then goes on (`__tt_dir_sync`).
- A change one tab makes reaches every other tab idle at its prompt at once, not at its next prompt or focus: every interactive shell whose layer is active records itself as an empty file `$XDG_STATE_HOME/ttheme/shells/<pid>` (`__tt_enlist`, from `__tt_hook`; a `zshexit` hook, `__tt_bye`, and `__tt_gone` remove it — no process), and `ttheme()` compares the modification times of `palettes.zsh` and the pins file before and after the verb it runs (`__tt_stamp`, around `__tt_verb`, so every way a verb changes them counts — a default, `off`, `on`, an install, a pin, preview's and Browse's apply, and bash and fish through zsh) and, when either moved, sends SIGURG to every recorded shell but itself (`__tt_wake`, a builtin `kill` per shell; a file whose pid is gone is removed, and a reused pid ignores SIGURG, as every program does by default). The layer's `TRAPURG` (defined at the top level, since a function under `emulate -L zsh` has `local_traps` and would take it back; never over a `.zshrc`'s own `TRAPURG`, though one set with `trap '…' URG` is replaced: only the `trap` builtin's output tells it apart, and a shell start reads nothing through a fork) runs only where `zsh_eval_context` holds the trap alone — a shell idle at its prompt, with zle or without — the adapter's `__tt_poked` (`__tt_fresh woke`, which Warp wraps in `TTHEME_WARP_HOLD`); a key a woken tab's query reads meanwhile waits in `TTHEME_TYPED` for the next `line-init`, since a `zle -U` from the trap lands behind the next key zle reads (measured: `abc` pushed, then `x` typed, read as `xabc`); what a woken tab has to say (`__tt_note`: a pin naming a palette that is not installed) waits in the trap's `TTHEME_NOTES` until its work is done and goes out after `zle -I`, on a line of its own with the prompt and the line being edited drawn again under it — printed from the trap it landed inside that line and left zle drawing the next keys a line below the buffer they went into, and a `zle -I` before a query would hand the tty back cooked for the answer to be echoed (`latency.zsh check`'s `noted`); a shell running a command runs the trap after it, at `toplevel`, where it does nothing, and catches up at its prompt as before. Inside tmux only the pane tmux last reported in front acts on a wake (`__tt_woken`, `TTHEME_FRONT` 1), since the colors belong to the terminal tab, not the pane: a pane behind repainted the whole tab with its own palette (a pin set elsewhere for its directory, measured in a real tmux 3.7c); the others catch up when tmux reports their focus (`__tt_rewear`). A woken tab is a tab at its prompt in every other way: it reads what changed and acts as at a focus, except that Windows Terminal's `__tt_reloaded` waits for the reset as the tab that ran the command does (no `behind`). compat's `prompt-trap` measures the trap in every terminal, and the parity model ignores SIGURG where `promptTrap` is false.
- Ghostty answers focus reporting (`\e[?1004h`) with the current focus the moment it goes on (`stream_handler.zig`, `.focus_event`), and until zle takes the tty raw the kernel echoes that answer as `^[[I` above the next prompt. So the layer turns it on from zle's `line-init` hook (`__tt_focus_on`, last in `__tt_line_init`, after the recheck whose read would otherwise take Ghostty's `\e[I` for itself), where the `^[[I` binding reads it, never from precmd; preexec still turns it off.
