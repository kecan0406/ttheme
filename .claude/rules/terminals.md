# Terminals, pictures and the shell layer

## Conventions

- A palette keeps every picture installed on it, and `backgrounds/images.json` (`Store`, `src/backdrop.ts`, versioned) is the one record of them: per palette the pictures in install order — key `<site>_<id>`, stem, `@fill` crop, default opacity, the `tone` and `blur` its files were drawn with and the `window` its fill was framed for, `# from` source, the `artist` names and the artwork's `source` page, original under `originals/` and, for a Vision cut-out, the cut's alpha beside it (`cut`) — and which one is `active`. Only the CLI writes it (`installBackdrop`, and `ttheme image <palette> show|drop [<picture>]`, a hidden verb in `src/images.ts` that preview calls when its tuning panel's picture strip is kept and on `D`), and every write regenerates that palette's `backgrounds/<palette>.conf` from it, which is a view for the terminals: the active picture's `# by <artist>,<artist>` (names with no space or comma, only when it has any) and `# from`, `# image <key> <at>/<of>` (the shell reads the count from it), a `# picture <key> <stem> <fill> <opacity> <artists|-> [<from>]` line for every picture the palette holds (preview's strip reads them; `bgby` carries the artists, which the tuning panel's title names before the post and keeps longest as the title narrows (`__tt_pv_bg_title`), and `bgurl` the `# from` line's page, which makes the post a link marked `⧉` in its site's color — `TTHEME_SITE_ANSI` in `palettes.zsh`, from `SITES` — where the adapter opens OSC 8 links), its `@fill` crop, and includes of that picture's own `<stem>.tune.conf` and `<stem>.off.conf`. `sync` rewrites every conf whose text differs from what the store makes (`freshenConfs`), so an upgrade's first init brings the older confs up to date. A picture's files are `<palette>.<hash>.png` (the figure), `<palette>.<hash>@fill-N.png`, the bakes preview makes on the same stem, and its tuning — all beside each other and never moved, so switching only changes `active` and the conf, and `drop` deletes the stem's files and the original. The hash is of the key and the images' content, because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name. Every picture file (figure, fill, the CLI's bakes) is an 8-bit indexed PNG whose 256 palette entries are all the tone and whose tRNS ramp makes the index the alpha — the ink, luma × alpha of the original, lifted until its top 1% reaches the tone (at most ×2, `liftOf`) and blurred by `TTHEME_BG_BLUR` — so the terminal's own straight-alpha blend over the background draws the tint (Ghostty's `bg_image` shader, and iTerm2, which then draws the same gamma-linear ramp Ghostty does where it used to darken a full-color tint's midtones — measured) and no pixel carries the background; `sips` bakes come back RGBA with the tone in every pixel, which is still the same picture. A palette whose `backdrop` tone or opacity changes is repainted by `sync` (`retint`): the files' PLTE is swapped (a `sips` bake is re-encoded from its alpha), they move to a new stem, the tuning moves with them and an opacity equal to the old default follows the new one. A `blur` that no longer matches the setting, or a picture with no `tone` (drawn before this format), is drawn again from its original by `redrawPictures` (`src/redraw.ts`, a pool of render workers running `redrawOne`, `src/pictures.ts`) — at every `init` after it applies, and through the hidden `ttheme redraw` that `ttheme config` runs when the `TTHEME_BG_BLUR` line changed and preview's alt-c panel runs when its `blur` row is saved; a picture drawn before cuts were kept finds its cut in the find cache or asks Vision again, and one without an original is left as it was. The CLI reads `TTHEME_BG_BLUR` from `config.zsh` itself (`blurOf`), never from the environment `__tt_cli` hands it, since an older shell still holds the old value and would draw every picture back. Tuning belongs to the picture, not the palette; the shell layer takes the file names from the conf's includes (`bgtunef`/`bgofff` in `__tt_bg_load`), falling back to `<palette>.tune.conf` for a conf the user wrote. In preview a picture's state is keyed by the palette for the active one and `<palette>:<key>` for the others (`__tt_bg_load` makes their conf lines from the `# picture` line); the tuning panel's strip (`__tt_pv_bg_strip`, up to five thumbnails of the pictures' fills as kitty placements `p=700001`–`700005` at `z=-1`, drawn by `__tt_pv_flush` after the frame so a resize's `d=A` cannot take them) follows `,` `.`, which only change what preview shows (`tpick`); enter keeps the tuning of every picture touched (`bgedit`) and the choice (`bgview`, `bgswap`), esc puts back every picture's state from when the panel opened (`tsnaps`), and the preview's close writes the tuning first and then shows the kept picture with `ttheme image <palette> show <key>`. `=` puts the field under the cursor back to the conf's defaults and `+` all of them, and a `↺` marks each field off its default. `f` and `D` change what the palette holds, so they write its kept tuning first and read it again after (`__tt_pv_bg_commit`, `__tt_pv_bg_reset`); installing the same post again starts from the defaults (the old stem's files go). A missing `images.json` is built once from the layout before it (`migrate`: the shown conf plus `backgrounds/shelf/<palette>/<key>/`), keeping a picture whose conf has no `# image` line under `picture_<hash>` rather than dropping it, and leaving a conf ttheme did not write alone and out of the store; `sync` opens the store, so an upgrade migrates at its first `init`, add or remove. Every file a terminal or another shell reads — the store, the confs, `palettes.zsh`, `installed.json`, the iTerm2 profiles — is written to a temp file and renamed over (`writeAtomic`, `src/edits.ts`; `__tt_put` in `ttheme.zsh`, which writes through a symlink to its target, ignores `noclobber` and renames with zsh/files' `zf_mv`, so a picture change forks nothing — `config.zsh`, the pins file and the remembered colors go through it too), so a reload never reads half a file. There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which the ghostty block always includes. Wearing a palette — `ttheme use <name>`, preview's enter, `ttheme next`, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: focus reporting (mode 1004) is on at every prompt and off during each command (`__tt_preexec`), Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd), which sets `TTHEME_FRONT`, and `\e[O` on `__tt_blur`, which clears it — so the picture belongs to the tab you are looking at, not to the last tab that switched. Only a tab the terminal has said is in front takes it: the ghostty adapter's `__tt_shown` writes nothing unforced while `TTHEME_FRONT` is 0, every prompt sets it to 0 (`__tt_prompt`: focus may have moved while the command ran with reporting off) until the answer to the reporting `line-init` turns on says otherwise, and a verb typed in the tab (`ttheme use`, `next`, preview's enter, `on`) claims with `force` — so a command that ends in a tab behind leaves the picture of the tab in front (parity's `prompt-behind`; it used to take it at its prompt). A shell that never heard a focus answer (`TTHEME_FRONT` stays -1: a `.zshrc` that replaces `zle-line-init`, so reporting never turns on) claims at every prompt as before. A tab busy with a program cannot hear its focus at all; the follower below puts its picture up. Where a verb changes this tab's colors and its picture together — `ttheme use`, `next`, `on`, a pin reached by `cd` or set in another tab — it goes through `__tt_wear` (spec, palette, `force`), and the ghostty adapter's claims first and paints after: it writes `shown.conf`, reloads, and waits for Ghostty to read the new file (`__tt_ghostty_took`: `shown.conf`'s atime passing its mtime — APFS stamps the first read after a write — at most 0.1 s, then 3 ms more so the reload reaches the surfaces), so the OSC colors land while the renderer decodes the picture and both change in one frame (measured frame by frame in a sandbox Ghostty, with and without twelve tabs and a custom shader; painting first showed the new colors over the old picture for 45–165 ms). The wait runs only when `__tt_reload_ghostty` signaled a Ghostty (`TTHEME_GHOSTTY_SENT`), and every other adapter's `__tt_wear` paints first as before. Preview's enter does the same before it closes (`__tt_pv_claim`), while its kitty layers still cover the grid, unless the panel changed a picture (`bgedit`, `bgswap`), whose save reloads again. A tab switch still shows the previous tab's picture for a moment, which no layer can prevent: the picture is one app-wide setting while the colors belong to each surface, and a tab shown again first presents what it last drew (or, hidden long enough, only its background color), then Ghostty draws it live with the picture the app holds, and only the reload its claim sends brings its own — Ghostty queues the surface's `visible` message ahead of that reload on its main thread, so even a tab at its prompt, which claims on its focus-in within a millisecond, shows the old picture for a frame or two (0–33 ms measured). Ghostty's `Path.equal` compares the path slices by pointer (`std.meta.eql`), so every reload also decodes the picture again in every surface and, with a `custom-shader`, recompiles every shader — the new tab once when it is shown and again on its claim's reload (its log says `loaded custom shader` each time). A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is written or reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own.
- A picture can keep its own colors instead of the tone (`Picture.coloring`, `'tone'` when absent; `Coloring` in `src/backdrop.ts`): an 8-bit RGBA PNG of the original's colors and its own alpha (a cut-out's, or none), blurred as premultiplied planes (`blurColors`), placed with the same `fillFrame`, lifted by nothing, and carrying no `tone` — `undrawn` is a picture with neither. Every terminal lays it over its background at `background-image-opacity` exactly as it lays a tone's ramp, and preview's veil and the kitty and WezTerm handlers never read a pixel, so no adapter names the coloring; the only shell code that does is the `# colors <key> original` conf line (`confText`; `bgcolors`, `__tt_bg_coloring`) and the tuning panel's fourth row and its `c` key from any row, which call the hidden `ttheme image <palette> tone|original [<picture>]` (`redrawColoring`, `src/redraw.ts`) and reopens on the same picture (`__tt_pv_bg_recolor`) — the coloring is a redraw from the original, so it is never staged or undone with esc. The redraw takes 0.5–0.75 s on a 3000×3000 cut-out JPEG and about twice that at 25 megapixels (end to end through the bundle, measured with `redrawOne` as 98% of it), so `__tt_pv_bg_recolor` and `__tt_pv_redraw` draw their note first and take nothing off the screen while the CLI runs (no `__tt_pv_bg_close`, no `__tt_pv_bg_strip_off`, and `__tt_pv_tune_stage` — `__tt_pv_tune_keep` without the strip's removal — runs after the draw): the old picture, thumbnails and sliders stay up, and the next frame is a `resized` one, whose wipe and show sit in one `2026` frame. The drawing itself is kept (`src/drawn.ts`, `$XDG_CACHE_HOME/ttheme/drawn/<key>`, one file per drawing holding the figure, the fill and their names, the twelve latest by modification time): `drawnFor` in `src/backdrop.ts` keys it on `DRAWING` (bump it whenever `draw`, `made` or the encoders change what they produce), the palette's file stem, the picture's key, the original's and the cut's size and modification time, the window, the blur, the coloring and, in the palette's tone, the tone color, and a hit skips the decode, the draw and the encode (`redrawOne` decodes only through the thunk `redrawn` calls on a miss). `redrawn` also keeps the drawing a coloring change replaces (`remembered`, from the picture's own record and files, only when `blur` and `window` are on it), so going back is a hit, and `ttheme image <palette> prepare [<picture>]` (`prepareColoring`, `prepareOne`) draws the other coloring into the cache without touching the store or `backgrounds/` — which `__tt_pv_bg_prepare` runs detached, once per picture and coloring and never beside another (`bgprep`, `bgprepid`), whenever the tuning opens on a picture or moves to another (`__tt_pv_tune_open`, `__tt_pv_bg_pick`; a recolor marks the coloring it left as ready). A drawing that writes a cut-out (`cut`) is never cached. Measured through the bundle on a 3000×3000 cut-out JPEG: 0.70 s (original colors) and 0.38 s (tone) without it, 45 ms with a hit. Its default opacity comes from its `peak`, the color of the brightest 1% of its visible pixels by relative luminance (`peakOf`): `originalOpacity` is the highest opacity at which the palette's text passes the gate on that color and it is no brighter than a tone picture may be (`fade`, shared with `toneFor`), so a picture with white in it opens at about half a tone's opacity. A palette whose text colors change moves it without drawing again (`retint` with a `Paint` per palette, `restrength`); redrawing into the other coloring keeps size and position and drops a tuned opacity, whose scale differs. `TTHEME_BG_COLORS` (`coloringFor`, read from `config.zsh` like the blur) only names what `find` and `add` install from now on; it never redraws.
- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image next|prev|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshPictures`, which runs every wired terminal's `pictures`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture — where the shell may switch profiles, the paint already moved the tab there (below), so it finds the tab on that profile undyed and sends nothing — and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`, and `default` while the tab is still on `ttheme · default`, read through `TTHEME_STARTUP` so it follows a default changed elsewhere); it never asks for a reload, and since iTerm2 reports focus changes the layer binds focus reporting there as it does in Ghostty, so a tab syncs at every prompt and focus. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown` and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band `sips` cut first, into a scratch dir `__tt_pv_bg_close` removes).
- One setup can wire several terminals, and a change made from any reaches all of them. `palettes.zsh` carries the wired terminals as `TTHEME_TERMINALS`; preview's saved pictures go through `__tt_bg_saved` (`_bg.zsh`) to `__tt_pictured` (`_wired.zsh`), which rewrites `ttheme.json` when iTerm2 is wired and reloads Ghostty when `shown.conf` names one of them; `ttheme default` and a catalog change that moves the startup palette (`__tt_catalog`) reload Ghostty too. `__tt_reload` reloads only the wired terminals that have a `__tt_reload_<id>` (Ghostty). Tuning is written for every wired terminal: with iTerm2 wired, a picture that is not centered is baked at the window size even when it is tuned in Ghostty (`__tt_bg_aligns`, and `aligns` on the CLI's side, from the wirings' `bakes`), since iTerm2 cannot place one.
- Every terminal ttheme wires is one module in `src/terminals/` (`WIRINGS` in `index.ts`, ids in `WIRED`) implementing `Wiring` (`types.ts`), and `src/palettes.ts` only orchestrates, naming none: `sync` builds one `Ctx` and runs every wired terminal's `sync` through one `Out` (`write` content-compared and atomic, `wire` through `editUserFile`, `themes` for the emitter's files under its `shelf`, `remove`, and `repaint` when open tabs must repaint), then rewrites `palettes.zsh` with each wiring's `layer` values; `wiringPlan`, `wiringNotes` and `wiringNext` are init's lines, `forget` drops removed palettes' theme files, `refreshPictures` follows a picture change, and `unwire` gives uninstall its edits, removals and touches (every wiring, whatever `installed.json` says). A terminal whose default is a profile (iTerm2, Konsole) has `defaults`: `base` keeps the user's own in `installed.json` (`itermBase`, `konsoleBase`), and `point` moves new tabs to ttheme's profile or gives the user's back, returning whether a running app needs a restart; `commit` runs them (`withBases`, `pointDefaults`) when a startup palette appears or vanishes, when `default`, `on` or init ask (`take`), or when the startup palette changes — without `take`, a terminal whose current default is not ttheme's keeps it. Every external command a wiring runs (`defaults`, `pgrep`, `dbus-send`, `cmd.exe`, `wslpath`) goes through `Host.run` (`systemHost`), which the tests fake. A new terminal is a module, an emitter, a `TRAITS` row and an adapter, and `src/terminals/index.test.ts` holds them together and to the support tables.
- The shell layer names a terminal only in `ttheme.zsh`'s detection block; `preview.zsh`, `_osc.zsh` and `_bg.zsh` name none, and an adapter names only itself (`terminal.test.ts`). Everything a terminal does differently is an adapter hook overriding `_osc.zsh`'s default — the paint and reset (`__tt_osc_apply`, `__tt_osc_reset`, `__tt_pv_paint`, `__tt_reset_reloaded`), what it hears at start (`__tt_hear`, `__tt_heard`), pictures (`__tt_shown`, `__tt_unshown`, `__tt_bg_*`), `__tt_reloaded`, `__tt_worn`, `__tt_keepable`, `__tt_follows_focus` (bind focus reporting: every terminal that reports focus changes — Ghostty, iTerm2, kitty, Alacritty, WezTerm, Windows Terminal, Konsole; `latency.zsh forks` reads it from the adapters), `__tt_takes_default` (whether a tab that never painted shows a new startup palette, below), `__tt_reverts` (whether a program's OSC reset takes a painted tab back to the config's colors, below) and `__tt_paints`/`__tt_unpainted`: in a terminal the layer cannot paint (a Warp that is unwired or has no settings file, and an editor's built-in terminal) the layer stays inactive and refuses the tab verbs (`TTHEME_TAB_VERBS`, from `src/verbs.ts`) and the bare menu with that terminal's own message; `__tt_follows_prompt` has the layer add the adapter's `__tt_prompted` to every prompt (Warp). What a wired terminal needs when another tab changes the state they share lives in `_wired.zsh`, one `__tt_<event>_<id>` per terminal behind `__tt_reload` and `__tt_pictured`.
- A tab that never painted (`TTHEME_PAINTED` unset: a new tab in `off`, or one reset since) shows what its terminal shows new tabs, so when `palettes.zsh` names another startup palette — seen by `__tt_fresh` at a prompt, a focus or the start of every `ttheme` command, and by `__tt_keep` and `__tt_catalog` in the tab that ran the command — `__tt_follow` moves the shell's belief to it and syncs its picture wherever the adapter's `__tt_takes_default` says the tab shows it: Ghostty's reload, kitty's and Alacritty's, WezTerm's, Windows Terminal's reset and Warp's theme repaint such a tab themselves, iTerm2 only while the tab is on `ttheme · default` undyed, Konsole once the adapter switches its scheme, Terminal.app never. `ttheme default` changes the default alone: the tab that ran it keeps its own palette and picture (`__tt_keep` syncs the picture of what the tab wears, forced only for preview's Default, which paints the tab first). `ttheme()` runs `__tt_fresh` before anything else, so a palette added in another tab is worn at once even where no focus is reported, and an uninstalled layer drops out right there.
- WezTerm, Windows Terminal and Warp are wired by `sync` too, each through the one file ttheme may own there. WezTerm's config is Lua, so `sync` writes `~/.config/ttheme/wezterm.lua` (`weztermModule`, `src/emit/wezterm.ts`: the startup `color_scheme`, the colors dir, and a picture handler) and keeps a `-- ttheme begin`/`-- ttheme end` block that `dofile`s it just before the user config's last `return config` (`upsertLuaBlock`; `~/.wezterm.lua` wins over `$XDG_CONFIG_HOME/wezterm/wezterm.lua`, as in WezTerm) — a config with no such line is left alone and init says so; WezTerm reloads the module on its own because it watches it. Its OSC palette is per pane but a `background` is per window: the shell's `__tt_shown` (wezterm adapter) sets the pane's `ttheme_shown` user var, and the module's `user-var-changed` and `update-status` handlers put the active pane's picture on its window through `set_config_overrides`, reading `backgrounds/<palette>.conf` with its `.tune`/`.off` includes itself, so nothing reloads when a picture changes elsewhere; while preview is open it sends `ttheme_view` instead — the frame `__tt_bg_frame` computed over the grid, with the picture, its opacity and position — which the module (`framed`) maps onto the window the way WezTerm draws the saved conf, the grid canvas scaled to cover the window and aligned by the position, so its tuning panel shows what saving writes (measured: the live and the saved picture's edges within 2 px); closing preview clears it and the window goes back to `ttheme_shown`. A tuned picture is written through `_bg.zsh` as in every other terminal, and `__tt_bg_refresh` sends `ttheme_shown` again so the module rereads the confs. Windows Terminal reads fragments but watches only `settings.json`: `sync` writes `%LOCALAPPDATA%/Microsoft/Windows Terminal/Fragments/ttheme/ttheme.json` (every scheme, plus an `updates` of the profile init ran in — `WT_PROFILE_ID`, else `defaultProfile` — wearing the startup palette) and then touches every `settings.json` it finds so the terminal reloads; init resolves `%LOCALAPPDATA%` (from WSL through `cmd.exe` and `wslpath`) and keeps it as `wtHome` in `installed.json`. A settings reload makes Windows Terminal reset every OSC color in every pane (`Terminal::UpdateColorScheme`, read in its source, not measured), so `sync` touches `settings.json` only when the fragment changed, the windows-terminal adapter's `__tt_reloaded` repaints a painted tab whenever `palettes.zsh` moves (`sync` moves it whenever it touched `settings.json`, even when its content is the same), once the reset has reached it: it asks the background every 50 ms for up to a second while the tab still shows its own palette, which only the tab that ran the command ever sees (every other one reads `palettes.zsh` again at its next prompt or focus, long after), and it leaves a tab that never painted to the reset, which puts on the profile the fragment gives the new startup palette. Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes` — the released Warp reads no subfolder there) and, when its `settings.toml` exists (a feature-flagged build), the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/terminals/warp.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 0.5 s later if the settings are still unchanged and the theme file is still there (`WARP_LATER`) — a file 0.1 s old is already worn right, one written in the same moment as the settings is not (measured, three runs at each age). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the warp adapter paints a tab through that key: with Warp wired and a `settings.toml` (`__tt_warp_wired`), `__tt_apply` points the `theme` line at the palette's newest theme file (`__tt_warp_value`, the newest hashed one by a zsh glob, so no fork) through `__tt_put`, so a linked dotfile survives, and writes nothing when the line already says it — every write reaches Warp's `Theme` preference, which its settings sync sends to the account (`SyncToCloud::Globally`) — keeping the user's own value in `warp.base` the way `sync` does; `__tt_osc_reset` puts on the default palette, or while ttheme is off the value in `warp.base` (`"dark"` over none) and removes `warp.base` once the user's theme is back (`__tt_warp_want`, `__tt_warp_wear`, which also waits until a theme file is 0.26 s old, since Warp falls back to its default for one it does not know yet). A new tab hears the default palette instead of asking Warp, whose answer is whatever tab is in front (`__tt_hear`; a shell started inside a painted tab hears the palette Warp wears). Warp tells an idle prompt nothing when its tab comes to the front — its `TerminalView` reports focus only while it holds focus itself, and at a prompt its input editor does — but it saves its session to its sqlite database (`~/Library/Group Containers/<team>.dev.warp/Library/Application Support/dev.warp.Warp-Stable/warp.sqlite`, `$XDG_STATE_HOME/warp-terminal/warp.sqlite` on Linux) at every tab activation and window activation (`should_save_app_state_on_action`, `on_active_window_changed`), at once and while `restore_session` is on (its default), and every shell knows its pane as `WARP_TERMINAL_SESSION_UUID`, the hex of `terminal_panes.uuid`. - The layer's hot paths start no process: a new tab in `off` and `seq` (all but Terminal.app's `seq`, which asks its 20 colors at start), every prompt's hooks, preexec, `line-init`, a focus-in, a `cd`, and a paint or picture change during preview (`__tt_apply`, `__tt_pv_paint`, `__tt_shown`, `__tt_bg_send`, `__tt_bg_dim`, which reads a PNG's size with `sysread`) — save Warp's follower, which a prompt starts once per Warp session when none runs, and whose `sqlite3` reads run in it, never in a tab. - In `off`, a new tab never waits on the terminal to learn what it shows. - Konsole (`KONSOLE_VERSION`, which Konsole's session sets, so Yakuake and the Dolphin and Kate panels too; 23.08.5 measured under Xvfb, its source read up to 26.04) draws the background and foreground an OSC 10/11 sets, about 20 ms later, and no OSC 12 or 17; it never draws an OSC 4 — it keeps the colors only to answer OSC 4 queries, which therefore report what an OSC 4 set rather than what it draws (`#b21818` after a scheme switch drew `#f47e6b`, measured), so compat's `wear` leaves ansi 1 to `wear-ansi`'s screenshot in any terminal whose `ansi-painted` failed in the same run; its bare OSC 104/110/111/112 resets do nothing (`110;` and `111;` reset from 25.12); and it parses an OSC 10/11 color with Qt's `QColor`, which reads `#rrggbb` and never `rgb:`, so a TUI restores it in hex (`hex`). The konsole adapter wears an installed palette with one `OSC 50 ColorScheme=<versioned name>;UseCustomCursorColor=true;customCursorColor=<cursor>` (`__tt_scheme`, which falls back to the stable name when the versioned file is gone; lowercase: Konsole's own `CustomCursorColor=` shortcut sets the cursor only for the moment) and never an OSC 11 in the same burst, and remembers what the tab shows (`TTHEME_KONSOLE_SHOWN`, the payload, and `TTHEME_KONSOLE_NAME`, the palette whose picture it carries): `__tt_reloaded` sends the payload again whenever the version of what the tab wears moved, so a picture tuned or a tone changed in another tab reaches it, and a new tab moves off the profile's stable scheme onto the versioned one before its first prompt (no process; the colors are the same, and no tab is then left holding a stale stable scheme a later tab would share). Colors no palette holds — a tone being tuned in preview's panel, a palette of an unwired Konsole — go through a view scheme the shell writes itself (`__tt_konsole_view`: the same 30 entries, faint by the same rounding, `Description=ttheme · <palette>`, no wallpaper) as `ttheme-view.<pid>.<n>.colorscheme`, keeping the two latest (the one Konsole may still be about to read after its 20 ms debounce) and deleting both at exit (`__tt_konsole_bye`, a `zshexit` hook); browse, init's picker and the palette editor do the same from the CLI (`konsoleLive`, `src/terminal.ts`: `ttheme-view.<10 hex of the content>.colorscheme`, three kept, all swept when it ends) once the shell hands it what the tab shows as `TTHEME_KONSOLE_LOOK` (`__tt_cli_env`), copying that scheme's wallpaper lines so a hover keeps the tab's own picture, and restore with that payload. An unwired Konsole therefore paints too, through view schemes, and resets to the user's own look, which the adapter reads from `konsolerc`'s `DefaultProfile` and the profiles it names, following `Parent=` (`__tt_konsole_own`, no process); it takes no default and keeps none. A reset goes to the look a new tab opens with: the startup palette's scheme, or while off the user's own (`TTHEME_KONSOLE_BASE`, the `layer` value `baseLook` reads through the base profile's parents). Before the hub hands the tab to browse, `__tt_pv_leave` puts on the tab's own look again, so browse copies the tab's picture rather than preview's last hover. Konsole loads its profiles and `konsolerc` once per process, so `point` sets `[Desktop Entry] DefaultProfile` in `konsolerc` (giving `konsoleBase` back while off, removing the key when there was none) and then calls `setDefaultProfile` on every running Konsole over D-Bus (`dbus-send`: each `org.kde.konsole-<pid>`, its first `/Windows/<n>`), checking `defaultProfile` after — a Konsole started before that profile existed needs a restart, and ttheme says so. It reports focus changes (mode 1004) though it answers no DECRQM at all, so compat's `focus-report` skips there and `focus-event` measures it — `xdotool` moving focus away and back on the Xvfb display — and the layer binds focus reporting; and since an open tab never reads a new default profile, the konsole adapter's `__tt_takes_default` switches a tab that never painted to the new startup palette's scheme itself (`__tt_osc_reset`). It passes compat's kitty graphics cases with Ghostty's layer order (every negative `z` under the cells with a background of their own and over the wallpaper; EL leaves images), so preview's layers, tuning and find work as in Ghostty (`__tt_bg_cells` through `CSI 16t`, crops through the source rectangle), and after preview saves a picture `__tt_pictured_konsole` refreshes the schemes through the CLI and `__tt_bg_refresh` puts the new version on the tab. It opens an OSC 8 link only where the profile allows escaped links (`AllowEscapedLinks`, off by default), which ttheme leaves to the user, since it writes colors only — so preview marks no post with `⧉` there (`TRAITS.konsole.links` false). The sandbox (`--konsole`, Linux) runs it on its own Xvfb display and D-Bus session (`dbus-run-session`), with `XDG_DATA_HOME` scrubbed, so nothing reaches the user's Konsole.
- Parity is measured against one spec, not against a terminal: `tests/parity/` walks every journey in `journeys.ts` in a model of each terminal (`TERMS`, Ghostty first; `parity.test.ts` fails when a wired terminal has no column), every look states what the tab in front should show (`want`, the palette — or `own` — whose colors, picture and belief follow from it, with `picture`, `opacity` and `repaints` where it differs or matters, and `unpainted` where the tab never painted, so it shows what the terminal shows new tabs), and `facts.tsv` records each look's facts against that spec (its `spec` column; a screen's spec is Ghostty's, approved with `--update`, the one place Ghostty stands for the spec). Ghostty is judged like every other terminal, so its misses get rows too, a terminal that shows more than Ghostty is never a gap, and a layer bug every terminal shares fails the spec instead of being recorded as the new `=`. `gaps.tsv` explains every miss — `cannot` (the terminal cannot express it), `layer` (the shell layer or the CLI could close it: this is the parity backlog, and a fix shows up as a changed fact to lock in with `mise run parity --update` and a reason to drop) or `deferred` (left out on purpose, Terminal.app's wiring) — narrowly: a row must explain every fact its glob names (`loose gaps` otherwise), and a terminal that lacks a capability (`CAPABILITIES`: `pictures` from `BEHAVIOR.pictures`, `wired` from `WIRING`) says why once, in a `@pictures` or `@wired` row, which explains every fact that needs it and must agree with the model both ways. The model claims nothing compat has not measured: `BEHAVIOR` (`terms.ts`) says what an OSC set draws, which queries it answers, whether resets work, how focus is reported, which cell-size reports it answers, kitty graphics, queries inside a synchronized update, what a config reload does to painted colors, where pictures live and whether a shell idle at its prompt runs a signal's trap at once (`promptTrap`; the harness's `.zshrc` ignores SIGURG where it is false), and `MEASURED` maps each field to the compat case that decides it; a field compat left `?` or `skip` is the model's assumption from the rules above or the terminal's source, and Windows Terminal, which compat cannot open, is modeled from its source alone — every parity run lists those assumptions per terminal at the end of its report (`unmeasured`, `facts.ts`), where cases that decide one claim together (`focus-report` and `focus-event` share `reportsFocus`) count as decided once either is. How a terminal turns files into looks is its `Kind` in `model.ts`: Ghostty re-reads its config (theme, `shown.conf`) only on the reload the `pkill` shim records, and a reload moves every slot no OSC set while painted ones keep their colors (Ghostty's `DynamicRGB`/`DynamicPalette` in its source, and compat's `follow-default` in the real app); iTerm2 opens tabs on the profile its preferences named at launch, follows a rewritten `ttheme.json` where a tab did not paint, and `SetProfile` drops what a tab painted (`remarry`), while a reset returns a slot to the color it had before an OSC first set it, once, even across a `SetProfile` (`baseline`, compat's `reset-baseline`); kitty's reload resets every window and the watcher re-wears `ttheme_worn`, and its logo follows `ttheme_shown` only where kitty.conf loads the watcher; WezTerm pictures follow the pane's user vars only where its config `dofile`s the module; Windows Terminal resets every pane 250 ms after `settings.json` moves; Warp's tabs share the theme its `settings.toml` names, the follower switching it from the session database the harness rewrites on every focus — in WAL mode with a 1 s busy timeout and each tab's rows in one transaction, as Warp keeps `warp.sqlite` (its `persistence/sqlite.rs`), so a read never fails a write; Konsole draws `OSC 50` schemes — a scheme a tab shows held as it was read until no tab shows it (`cache: 'weak'`, compat's `scheme-held`, `scheme-released` and `scheme-fresh`), its wallpaper the tab's picture — and takes a new default only through the D-Bus call the `dbus-send` shim records; Terminal.app is never wired; a look whose screen shows what a capability brings says so (`text: 'pictures'` for the tuning panel's picture rows), and the screen of a look marked `unpainted` needs `wired` as its colors do. A new journey is one entry in `journeys.ts`, observed through `look` (colors, picture, wears, and optionally text, repaints or opacity), `wire` adds Ghostty for the cross-terminal ones and `unwired` runs on a home init never wired; a new terminal needs a `TERMS` entry, a `BEHAVIOR` row, an `identity`, a `Kind`, a compat column, and its facts and gaps.

## Gotchas

- The layer runs inside the user's shell, under whatever options their `.zshrc` set, while every test runs it under zsh's defaults — and `no_clobber` (Prezto sets it) made its writes fail, `ksh_arrays` and `sh_word_split` misread its arrays and arguments, and `no_unset` stopped it loading at all. So every function the shell calls on its own — `ttheme`, each hook, zle widget and the completion — and each block that runs while the layer is sourced starts with `emulate -L zsh ${=${options[xtrace]:#off}:+-o xtrace}` (about 3 µs; the xtrace clause keeps `set -x` and the fork counts working, which a bare `emulate` switches off). `terminal.test.ts` holds every function the layer registers to it, and `latency.zsh check` sources the layer under such a `.zshrc` and uses it.
- Every question the layer asks the terminal goes through `__tt_ask` (`_osc.zsh`): it opens the tty as `{ exec {fd}<>/dev/tty } 2>/dev/null`, because an `exec` with no command applies all its redirections to the shell for good — the plain `exec {fd}<>/dev/tty 2>/dev/null` sent every later command's stderr to /dev/null (measured). It sets the tty up in one `stty` subshell (save, raw, then restore: about 5.7 ms of forks against a 0.1 ms answer, measured) only while the tty is still cooked — never inside zle, which holds it raw already (`zle` answers true there), nor inside preview, which holds it `-echo -icanon` for its whole session (`TTHEME_RAW`) because zsh's own `read -s -k` restores the modes between characters: keys arriving while preview drew were echoed into its frame (39 of 60 held arrows at 160×50, measured; `latency.zsh check` types into it). It appends a DSR (`\e[5n`), reads whole chunks with `sysread -t 0.3` until its `\e[0n`, so it ends as soon as the terminal has answered everything, and then splits the bytes with one pattern: a byte outside an escape sequence is a key the user typed ahead: it goes to `TTHEME_TYPED`, which the `__tt_typed` line-init widget hands back to zle (`zle -U`), so a command typed while the shell starts still runs. Preview drops them (`__tt_pv_bg_open`) — those keys were meant for it.

- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. An app `open` starts keeps that environment in every tab until it quits, and Warp hands it on through its update relaunch (`open -n` from Warp itself), so the sandbox opens the user's own Warp and Terminal.app from `env -i`. Started from Claude's shell, Warp carried `CLAUDECODE`, the sandbox's `HOME` and `ZDOTDIR` and every other variable of that shell into each tab: the user's own tabs sourced the sandbox's `.zshenv` hook, so a run's hang-up and compat's `exit` closed them, and Warp read the sandbox's `~/.warp`, which failed compat's `osc-reset`, `restore` and `layer-query` (measured 2026-09-30; a probe app took the whole environment through `open <url>` and `open -a` alike). It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- Ghostty, Alacritty and Warp leave OSC 17 (selection) queries unanswered (`mise run compat`'s osc-selection; Ghostty's `stream_handler.zig` logs "reporting dynamic color highlight_background not implemented"), so a query that waits for every color it asked stalls until its deadline — `queryTerminalColors` (`src/osc.ts`, browse and init's picker) ends at a DSR answer instead, which took 120 ms off every browse in those terminals.
- Preview's search hint animates on a timer, and those ticks redraw its first row alone (`tick`, `__tt_pv_draw hint`): a full frame is about 4 KB and 3.6 ms at 160×50, and the hint had been 9 KB a second of redraws while preview sat idle. The row is cleared with ECH over the list's columns, never `\e[K`, which would take the right panel's header on the same row with it.
- Ghostty applies a SIGUSR2 reload asynchronously, an OSC reset returns a surface to the defaults Ghostty holds at that moment, and a reload does not repaint a surface's current colors (measured) — so a reset sent right after the config changes brings back the old `theme =`. `ttheme off` therefore writes everything first, reloads once, and `__tt_reset_reloaded` (ghostty adapter) resets again every 50 ms while the tab still shows the palette's background, for at most a second. Every other open tab turns itself off too (`__tt_off_here`) at its next prompt or focus, when `__tt_fresh` sees `TTHEME_STARTUP` go empty; `ttheme on` paints the default in the tab that ran it, and every tab that went off takes it back from the reloaded config and learns so at its next prompt or focus (`__tt_follow`).
- Ghostty answers focus reporting (`\e[?1004h`) with the current focus the moment it goes on (`stream_handler.zig`, `.focus_event`), and until zle takes the tty raw the kernel echoes that answer as `^[[I` above the next prompt. So the layer turns it on from zle's `line-init` hook (`__tt_focus_on`, last in `__tt_line_init`, after the recheck whose read would otherwise take Ghostty's `\e[I` for itself), where the `^[[I` binding reads it, never from precmd; preexec still turns it off. That answer is also how a prompt learns whether its tab is in front (`TTHEME_FRONT`, above), and only Ghostty gives one (compat's `focus-answer`), which is why the claim gate lives in the ghostty adapter.
- A program may reset what a tab wears: Neovim sends OSC 112 whenever it enters or leaves `:terminal` mode with its default `guicursor` (`t:…-TermCursor`, reverse, which its TUI reads as the terminal's default and resets) and on its way out when `guicursor` names a colored highlight, and a background sync such as mini.nvim's `setup_termbg_sync()` sends OSC 111 on its way out and at `VimSuspend` (measured on 0.12.5 through a pty, and in a sandbox Ghostty: a tab wearing miku came back with the startup palette's cursor, and after the sync its background, while the layer still believed miku). A reset returns to the config's colors, the startup palette, in Ghostty, kitty, Alacritty, WezTerm and Windows Terminal, so every command sets `TTHEME_RAN` (`__tt_ran`, the non-tmux preexec that also spots `tmux`) and a painted tab's next `line-init` asks its background and cursor (`__tt_mend`: one `__tt_ask`, answers read by `__tt_colors`, which `__tt_query_bg` and Terminal.app's `__tt_hear` share) and repaints when either differs — 0.2–0.5 ms in Ghostty (median 0.25 ms, thirty asks), no process. `__tt_reverts` is false where a reset does not land there: Terminal.app and Konsole ignore resets, Warp paints through its theme, and an iTerm2 tab sits on its palette's own profile once the shell may switch profiles (above), so a reset lands on the palette — while it may not, the tab is dyed and a reset takes it back to its profile's colors, and the layer does not ask, since iTerm2's answers wait for its 1/30 s tick (1.7–20 ms after an idle 0.2 s, 14–33 ms back to back, measured in the sandbox). compat's `reset-worn` runs a reset and the next prompt's `__tt_mend` in each terminal. The latency harness answers a query with the color an OSC set (`SHOWN`), as a terminal does, so a painted tab mends nothing there, and the fork ratchet's `mend` row walks a command that resets the cursor.
- An editor's built-in terminal inherits every variable that names the terminal around it, so the detection block tests for one first — `$NVIM` (Neovim's `:terminal`), `$VIM_TERMINAL` (Vim's), `$INSIDE_EMACS`, `TERM_PROGRAM=vscode` — and makes it the `editor` adapter (`editorOf`, `detectTerminal`), which paints nothing: the layer stays inactive, and the tab verbs and the bare menu refuse with its message. Neovim's vterm applies no OSC color and drops APC (they reach only `TermRequest`), answers OSC 10/11 with pure black or white by its `background`, and hands the shell a focus-in and focus-out as terminal mode starts and ends (`terminal_focus`), so a layer that took it for Ghostty claimed the app-wide picture from inside the editor — `ttheme use kita` there put kita's picture over a tab wearing miku, and a rotating new-tab palette spent a slot (measured in a sandbox Ghostty) — parity's `editor-terminal`. `ttheme info` names the editor (`editor (nvim)`).
- A Ghostty tab whose shell is not at its prompt — Claude Code, vim, ssh, a dev server — cannot hear its focus, so bringing it to the front left the last tab's picture over its colors until its next prompt (parity's `focus-busy`). On macOS Ghostty names the terminal in front through AppleScript (the front window's selected tab's focused terminal, whose `tty` and `pid` — the foreground process — are on main after 1.3.1), so every Ghostty tab records what it wears in `$XDG_STATE_HOME/ttheme/ghostty/<tty>` — its pid, the default it wore it under, its palette (`-` for a tab that leaves the picture alone) and its `$TTY` — from every prompt (`__tt_prompted`), paint and reset (`__tt_worn`, but not the hovers preview paints in raw mode) and claim (`__tt_shown`), and one follower per Ghostty session (`__tt_ghostty_follower`, a `zsh -f` sourcing the layer, kept single by a `zsystem flock` on `ghostty/.follow` and started by any prompt that finds it gone) asks Ghostty which terminal is in front and puts up that tab's record when `shown.conf` names another, busy or idle; a record made before ttheme went off leaves the picture alone. It asks (`__tt_ghostty_ask`, one `osascript` of about 0.1 s) only on a sign that focus moved, polled every 0.1 s with `zstat`: a recorded tty's atime moved (macOS stamps a tty's atime in nanoseconds whenever its foreground program reads, so a program that turned focus reporting on — Claude Code does — marks its tty the moment its tab comes to the front), a tab at its prompt lost focus (`__tt_blur` touches `ghostty/.blur`), or the tab in front took input and then went quiet for 0.3 s — at most every 2 s while it was last seen busy, since its focus-out looks like a keystroke and a program that reports no focus leaves nothing else when its tab is left, and every 10 s while it was last seen at its prompt, whose blur is stamped anyway, so a program started in it without a switch is learned at a later pause. A tab that reads on five ticks running (a program polling its input, which stamps the atime too — an `EAGAIN` read does, measured) is ignored until it stops, and an answer is asked again when `shown.conf` moved while Ghostty answered, so a tab's own claim is never overwritten with a stale one. The question is raw Apple Events addressed to the owning Ghostty's pid (`__tt_ghostty_owner`, the walk `__tt_reload_ghostty` shares; `TTHEME_GHOSTTY_JS`): JXA's `Application(pid)` goes to the bundle's first instance — the user's Ghostty while the sandbox's runs (measured). A Ghostty whose dictionary has no `tty` (1.3.1 and before; the running bundle's `Ghostty.sdef` is read for `code="Gtty"`, since an unknown property fails in JXA before reaching the app, `-1700`, measured) or that names no terminal five times running over at least 30 s (`macos-applescript = false`) is remembered in `ghostty/.blind` by `TERM_PROGRAM_VERSION` for a day — never a Ghostty that quit: the script answers `gone` for a pid no longer running and a `none` from a dead pid counts for nothing, so the follower of a Ghostty quit and reopened leaves instead of marking the new one blind (measured 2026-09-30: a quick double restart wrote `.blind` and kept every follower off for a day), and `init` removes `.blind` (`forget`, `InitPaths.stateDir`) so the layer an upgrade brings asks again — and a shell records nothing and starts no follower where none can run — checked once per shell and again whenever `.blind` appears, so a shell started before it does not respawn a follower that cannot see (`__tt_ghostty_follows`: `TERM_PROGRAM=ghostty`, an interactive shell with a tty, `osascript`, no tmux, no fresh `.blind`) — Linux Ghostty, tmux and the latency harness among them, so their hot paths pay nothing (`bench --against`: first prompt +0.04 ms, a command +0.02 ms, both inside the noise); where it runs, a new tab's first prompt writes its record, about 1 ms. The follower also runs a watcher (`TTHEME_GHOSTTY_WATCH`, an `osascript -l JavaScript` coprocess `__tt_ghostty_watch` starts once the first answer came back) that polls the window server rather than Ghostty. Each look costs two id lists (`CGWindowListCreate`): whether Ghostty's front window is still on screen and how many windows lie above it. Only when either changed — a tab switch takes the window off screen, a Ghostty window or another app coming forward changes the count — does it read the list (`CGWindowListCopyWindowInfo`) for Ghostty's front window and refresh whether Ghostty is frontmost (`frontmostApplication`, with one run-loop pass, since JXA's `delay` runs none and the property goes stale; also every 40 looks). When Ghostty is frontmost and its front window is not the one it last reported, it prints the answer — the one it cached for that window at once, then the one Ghostty gives through the same raw Apple Events when it differs, cached only if that window is still in front after the question — as `1 <tty> <pid> <time>`. It looks every 50 ms for 1.5 s after a mouse down, key down or modifier change (`CGEventSourceSecondsSinceLastEventType`, which counts every app, so only while Ghostty is frontmost), every 150 ms otherwise, every 0.25 s while Ghostty is behind and every second while it shows no window; JXA hands `NSArray.count` back as a string, hence `+l.count`. The follower waits on it with `zselect` (`__tt_ghostty_heard` → `__tt_ghostty_take`, which drops an answer older than `shown.conf`'s last write, a tab's own claim since), ticks every 0.5 s instead of 0.1 s while it runs, asks nothing about a quiet busy tab in front, and lets neither a blur nor a tab behind taking input make it ask within a second of the watcher's last line; the watcher leaves with its follower or its Ghostty (`getppid`, `terminated`, and at once when Ghostty shows no window and its pid is gone), and a follower leaves when its own `adapters/ghostty.zsh` changes (`TTHEME_GHOSTTY_CODE`), so an upgrade's first prompt starts one on the new code.
