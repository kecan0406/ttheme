# Terminals, pictures and the shell layer

## Conventions

- A palette keeps every picture installed on it, and `backgrounds/images.json` (`Store`, `src/backdrop.ts`, versioned) is the one record of them: per palette the pictures in install order — key `<site>_<id>`, stem, `@fill` crop, default opacity, `# from` source, original under `originals/` — and which one is `active`. Only the CLI writes it (`installBackdrop`, and `ttheme image <palette> next|prev|drop`, a hidden verb in `src/images.ts` that preview's tune keys `,` `.` `D` call), and every write regenerates that palette's `backgrounds/<palette>.conf` from it, which is a view for the terminals: the active picture's `# from`, `# image <key> <at>/<of>` (the shell reads the count from it), its `@fill` crop, and includes of that picture's own `<stem>.tune.conf` and `<stem>.off.conf`. A picture's files are `<palette>.<hash>.png` (the figure), `<palette>.<hash>@fill-N.png`, the bakes preview makes on the same stem, and its tuning — all beside each other and never moved, so switching only changes `active` and the conf, and `drop` deletes the stem's files and the original. The hash is of the images' content, because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name. Tuning belongs to the picture, not the palette; the shell layer takes the file names from the conf's includes (`bgtunef`/`bgofff` in `__tt_bg_load`), falling back to `<palette>.tune.conf` for a conf the user wrote. Preview writes tuning that has not been confirmed to the picture before `,` `.` move off it; installing the same post again starts from the defaults (the old stem's files go). A missing `images.json` is built once from the layout before it (`migrate`: the shown conf plus `backgrounds/shelf/<palette>/<key>/`), keeping a picture whose conf has no `# image` line under `picture_<hash>` rather than dropping it, and leaving a conf ttheme did not write alone and out of the store; `sync` opens the store, so an upgrade migrates at its first `init`, add or remove. Every file a terminal or another shell reads — the store, the confs, `palettes.zsh`, `installed.json`, the iTerm2 profiles — is written to a temp file and renamed over (`writeAtomic`, `src/edits.ts`; `__tt_put` in `_bg.zsh`), so a reload never reads half a file. There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which the ghostty block always includes. Wearing a palette — `ttheme use <name>`, preview's enter, `ttheme next`, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: `__tt_precmd` turns focus reporting (mode 1004) on at every prompt, `__tt_preexec` turns it off before each command, and Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd) — so the picture belongs to the tab you are looking at, not to the last tab that switched, and a busy tab catches up at its next prompt. A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is written or reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own.
- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image next|prev|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshProfiles`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`, and `default` while the tab is still on `ttheme · default`, read through `TTHEME_STARTUP` so it follows a default changed elsewhere); it never asks for a reload, and with no focus tracking the layer syncs once at shell start instead. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown` and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band `sips` cut first, into a scratch dir `__tt_pv_bg_close` removes).
- One setup can wire Ghostty and iTerm2 together, and a change made from either reaches both. `palettes.zsh` carries the wired terminals as `TTHEME_TERMINALS`; preview's saved pictures go through `__tt_bg_saved` (`_bg.zsh`), which rewrites `ttheme.json` when iTerm2 is wired and reloads Ghostty when `shown.conf` names one of them; `ttheme default` and a catalog change that moves the startup palette (`__tt_catalog`) reload Ghostty too. `__tt_reload` (`ttheme.zsh`) does nothing unless Ghostty is wired. Tuning is written for every wired terminal: with iTerm2 wired, a picture that is not centered is baked at the window size even when it is tuned in Ghostty (`__tt_bg_aligns`), since iTerm2 cannot place one.
- WezTerm, Windows Terminal and Warp are wired by `sync` too, each through the one file ttheme may own there. WezTerm's config is Lua, so `sync` writes `~/.config/ttheme/wezterm.lua` (`weztermModule`, `src/emit/wezterm.ts`: the startup `color_scheme`, the colors dir, and a picture handler) and keeps a `-- ttheme begin`/`-- ttheme end` block that `dofile`s it just before the user config's last `return config` (`upsertLuaBlock`; `~/.wezterm.lua` wins over `$XDG_CONFIG_HOME/wezterm/wezterm.lua`, as in WezTerm) — a config with no such line is left alone and init says so; WezTerm reloads the module on its own because it watches it. Its OSC palette is per pane but a `background` is per window: the shell's `__tt_shown` (wezterm adapter) sets the pane's `ttheme_shown` user var, and the module's `user-var-changed` and `update-status` handlers put the active pane's picture on its window through `set_config_overrides`, reading `backgrounds/<palette>.conf` with its `.tune`/`.off` includes itself, so nothing reloads when a picture changes elsewhere; preview's hover sends the same var. Windows Terminal reads fragments but watches only `settings.json`: `sync` writes `%LOCALAPPDATA%/Microsoft/Windows Terminal/Fragments/ttheme/ttheme.json` (every scheme, plus an `updates` of the profile init ran in — `WT_PROFILE_ID`, else `defaultProfile` — wearing the startup palette) and then touches every `settings.json` it finds so the terminal reloads; init resolves `%LOCALAPPDATA%` (from WSL through `cmd.exe` and `wslpath`) and keeps it as `wtHome` in `installed.json`. A settings reload makes Windows Terminal reset every OSC color in every pane (`Terminal::UpdateColorScheme`, read in its source, not measured), so `sync` touches `settings.json` only when the fragment changed, the windows-terminal adapter's `__tt_reloaded` repaints the tab whenever `palettes.zsh` moves (`sync` moves it whenever it touched `settings.json`, even when its content is the same), and the adapter binds focus reporting as Ghostty does, so a tab repaints at its next prompt or focus. Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes` — the released Warp reads no subfolder there) and, when its `settings.toml` exists (a feature-flagged build), the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/wiring.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 1.5 s later if the file is still unchanged (`WARP_LATER`). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the zsh layer treats `TERM_PROGRAM=WarpTerminal` as inactive and `ttheme use <palette>` there points at Warp's settings instead of half-painting. Terminal.app (`TERM_PROGRAM=Apple_Terminal`) takes every OSC color but ignores the OSC resets, so its startup answer is all 20 colors rather than the background alone (`__tt_hear`, one batched query): `__tt_heard` keeps them as the base `__tt_osc_reset` puts back, and `__tt_start_bg` takes the startup background from them.
- kitty is wired through a watcher `sync` writes to `~/.config/ttheme/kitty.py` (`kittyWatcher`, `src/emit/kitty.ts`), loaded by the kitty block (`watcher`, plus `window_logo_scale 100` and `window_logo_alpha 1` unless kitty.conf sets them itself). The kitty adapter talks to it through user vars (`__tt_kitty_var`, the value base64'd in zsh by `__tt_b64s`, so a paint — every preview hover among them — forks nothing): `ttheme_worn` on every paint and reset (the `__tt_worn` hook in `_osc.zsh`), `ttheme_shown` from `__tt_shown`, and `ttheme_startup` from `__tt_reloaded` after `palettes.zsh` moves. A window's picture is its logo, read from `backgrounds/<palette>.conf` with its includes and re-read on focus; kitty 0.49 draws logos at the global alpha and scale only (`draw_window_logo`), so the watcher fades the PNG's alpha to the opacity itself (`load_png_data`/`png_from_32bit_rgba_data`, about 0.3 s for a 1880×1008 picture, cached). kitty's `auto_reload_config` (on by default) reloads when `kitty.conf` or any file it includes changes, and a reload resets every OSC color (measured): the watcher wraps `boss.load_config_file` and puts each window's `ttheme_worn` palette back right after it, and `ttheme_startup` patches the configured colors (`patch_colors(…, True, ())`, which leaves open windows alone) for a kitty whose auto reload is off. Preview and find reuse `_bg.zsh`: kitty draws below-background placements above the logo, so preview's layers cover it; the adapter places them absolutely (no relative placements, no margins). `sync` writes a file only when its content changed, so an add or remove that leaves kitty's files alone reloads nothing.
- Alacritty takes its startup palette through `general.import`: `upsertAlacrittyImport` (`src/wiring.ts`) appends a `[general]` block to a config without that table, or puts the import line inside the config's own `[general]` (TOML defines a table once), and leaves a config that already imports there or defines `general` otherwise alone — init notes it. Alacritty live-reloads the config and its imports and keeps OSC colors through a reload (measured).
- iTerm2 has no config file, so `sync` owns `~/Library/Application Support/iTerm2/DynamicProfiles/ttheme.json` whole: one `ttheme · <palette>` profile per listed palette (`itermProfiles`, `src/emit/iterm2.ts`), rewritten on every add/remove/browse and reloaded by iTerm2 on its own, plus `ttheme · default` (Guid `ttheme-default`), a copy of the startup palette's profile: `ttheme default` rewrites it, and every tab still on it — new ones and ones never painted — follows within about 0.3 s, which is iTerm2's side of Ghostty's `theme =` and reload. It is also iTerm2's default profile, so a new tab or window is created wearing it and never switches after it opens — a shell that moved a new tab onto it would flash the old profile first, which is never acceptable. `init` and `ttheme default`, and an add, remove or browse that makes a startup palette appear or vanish (never any other, so a default the user picked in iTerm2 stays), point `Default Bookmark Guid` at it through `defaults` (`pointItermDefault`, `src/palettes.ts`) and write the profile they replace to `installed.json` as `itermBase`, which every ttheme profile names as its `Dynamic Profile Parent GUID` so fonts, keys and the rest keep coming from the user's own profile; `ttheme off` or removing the last palette gives `itermBase` back. A running iTerm2 takes the new default only at its next start — the notes say so. While off, or with no palette installed, there is no startup palette and no `ttheme · default`; `ttheme on` and `ttheme default` turn it back on, and init's "pick a default palette in ttheme preview?" answered no installs off. `TTHEME_ITERM_SUITE` names the preferences domain (`com.googlecode.iterm2` by default); the sandbox sets it to its own suite so nothing reaches the user's iTerm2. `palettes.zsh` carries the startup palette as `TTHEME_STARTUP`, so a shell that opens on `ttheme · default` knows whose picture it shows. Measured on 3.7.2: iTerm2 reads OSC colors as Display P3 (its `p3` default) and reports an sRGB profile color converted, so the profiles and `.itermcolors` are written in P3 or the shell's OSC 11 palette match fails; and a newly added dynamic profile inherits its parent's light/dark split and then ignores unsuffixed color keys, so every profile sets `Use Separate Colors for Light and Dark Mode` false.
- The layer's hot paths start no process: a new tab in `off` and `seq` (all but Terminal.app's `seq`, which asks its 20 colors at start), every prompt's hooks, preexec, `line-init`, a focus-in, a `cd`, and a paint or picture change during preview (`__tt_apply`, `__tt_pv_paint`, `__tt_shown`, `__tt_bg_send`, `__tt_bg_dim`, which reads a PNG's size with `sysread`). A fork costs 1.5–2.5 ms on macOS against microseconds for a builtin, so reach for `$(<file)`, `zstat`, `sysread -t`, `__tt_b64s` and parameter expansion there, never `$(…)`, a pipe or an external command. `tests/forks.tsv` is the ratchet `shell:check` holds every journey to (`mise run forks`), and `shell/check.zsh`'s `forks_of` holds the paint helpers to zero; a change that removes a fork lowers the file with `mise run forks --update`. `__tt_cli` hands node `NODE_COMPILE_CACHE` under the ttheme cache dir, about 4 ms of every CLI call; node keys the cache by the file's path, so an upgrade overwrites it instead of adding one.
- In `off`, a new tab never waits on the terminal to learn what it shows. The answer its shell needs at start — the background, which names the palette the tab wears (`__tt_wearing`, the startup palette first), or Terminal.app's 20 colors — is kept per adapter in `$XDG_STATE_HOME/ttheme/colors.<adapter>` beside the startup palette it was heard under (`__tt_recall`, `__tt_remember`, `__tt_listen`). A shell uses it before its first prompt and asks again from its first `line-init` (`__tt_line_init` → `__tt_recheck`), where zle already holds the tty raw, so no `stty` runs: a different answer rewrites the file and moves the tab's palette — or a pin's base — and its picture to the fresh one, while an announce already printed stays. Only a tab's own colors may be kept, so every paint exports `TTHEME_PAINTED` (`__tt_osc_apply`; a reset unsets it): a shell that inherits it (`exec zsh`, a nested shell) or paints before its first prompt (a pinned directory) neither keeps nor rechecks, and asks at start as before — as does a miss (no file, another startup palette, `seq`, tmux, no zle, nothing installed), which then writes the file. `line-init` is one widget (`__tt_line_init`: the recheck, then `__tt_typed`, then `__tt_focus_on` where focus is bound), since each `add-zle-hook-widget` costs about 0.5 ms of every start. Measured with `mise run bench --against`: a new tab's first prompt went from +7.2 to +2.6 ms over a bare shell in `off` and from +8.2 to +3.2 ms in Terminal.app, and no adapter adds a process to a start, a prompt, a focus change or a `cd` (a `fork`/`execve`-counting `DYLD_INSERT_LIBRARIES` shim on a re-signed copy of zsh — PIDs cannot tell, the Mac forks about 500 times a second on its own).

## Gotchas

- Every question the layer asks the terminal goes through `__tt_ask` (`_osc.zsh`): it opens the tty as `{ exec {fd}<>/dev/tty } 2>/dev/null`, because an `exec` with no command applies all its redirections to the shell for good — the plain `exec {fd}<>/dev/tty 2>/dev/null` sent every later command's stderr to /dev/null (measured). It sets the tty up in one `stty` subshell (save, raw, then restore: about 5.7 ms of forks against a 0.1 ms answer, measured) only while the tty is still cooked — never inside zle, which holds it raw already (`zle` answers true there), nor inside preview, which holds it `-echo -icanon` for its whole session (`TTHEME_RAW`) because zsh's own `read -s -k` restores the modes between characters: keys arriving while preview drew were echoed into its frame (39 of 60 held arrows at 160×50, measured; `latency.zsh check` types into it). It appends a DSR (`\e[5n`), reads whole chunks with `sysread -t 0.3` until its `\e[0n`, so it ends as soon as the terminal has answered everything, and then splits the bytes with one pattern: a byte outside an escape sequence is a key the user typed ahead: it goes to `TTHEME_TYPED`, which the `__tt_typed` line-init widget hands back to zle (`zle -U`), so a command typed while the shell starts still runs. Preview drops them (`__tt_pv_bg_open`) — those keys were meant for it.

- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- Ghostty, Alacritty and Warp leave OSC 17 (selection) queries unanswered (`mise run compat`'s osc-selection; Ghostty's `stream_handler.zig` logs "reporting dynamic color highlight_background not implemented"), so a query that waits for every color it asked stalls until its deadline — `queryTerminalColors` (`src/osc.ts`, browse and init's picker) ends at a DSR answer instead, which took 120 ms off every browse in those terminals.
- Preview's search hint animates on a timer, and those ticks redraw its first row alone (`tick`, `__tt_pv_draw hint`): a full frame is about 4 KB and 3.6 ms at 160×50, and the hint had been 9 KB a second of redraws while preview sat idle. The row is cleared with ECH over the list's columns, never `\e[K`, which would take the right panel's header on the same row with it.
- Ghostty applies a SIGUSR2 reload asynchronously, an OSC reset returns a surface to the defaults Ghostty holds at that moment, and a reload does not repaint a surface's current colors (measured) — so a reset sent right after the config changes brings back the old `theme =`. `ttheme off` therefore writes everything first, reloads once, and `__tt_reset_reloaded` (ghostty adapter) resets again every 50 ms while the tab still shows the palette's background, for at most a second. Every other open tab turns itself off too (`__tt_off_here`) at its next prompt or focus, when `__tt_fresh` sees `TTHEME_STARTUP` go empty; `ttheme on` wears the default only in the tab that ran it, and new tabs.
- Ghostty answers focus reporting (`\e[?1004h`) with the current focus the moment it goes on (`stream_handler.zig`, `.focus_event`), and until zle takes the tty raw the kernel echoes that answer as `^[[I` above the next prompt. So the layer turns it on from zle's `line-init` hook (`__tt_focus_on`, last in `__tt_line_init`, after the recheck whose read would otherwise take Ghostty's `\e[I` for itself), where the `^[[I` binding reads it, never from precmd; preexec still turns it off.
- BSD `pgrep`/`pkill` skip their own ancestors, so from inside a Ghostty tab `pkill ghostty` misses that Ghostty. `__tt_reload` therefore walks up to the Ghostty that owns the shell and signals only it, falling back to `pkill` when the shell sits outside one (tmux, or another terminal such as iTerm2 changing a picture Ghostty shows); the walk runs once per shell and its answer is kept in `TTHEME_GHOSTTY_PID`, since a shell never outlives or changes its Ghostty.
- `shell/ttheme.zsh` only runs from an installed layer, with `palettes.zsh` beside it — there is no source-from-checkout path. `shell/check.zsh` assembles such a layer in a temp dir.
- The installed layer `zcompile`s the files it sources (`ttheme.zsh`, `palettes.zsh`, the adapters) into `.zwc` beside them at shell start, and zsh's `source` takes a `.zwc` stamped in the same second as a newer source — so whatever rewrites one of those files deletes its `.zwc` (`applyInit`, `sync`).
- iTerm2 3.7 keeps its sessions alive in `iTermServer` across a quit and saves dynamic profiles into its prefs (`New Bookmarks`), so a test run can come back on an old session or an old profile's values; a dynamic profile without `Dynamic Profile Parent Name` merges into the default profile, which can be itself. Like Ghostty, it starts shells through `login`, which resets `HOME`.
- iTerm2 3.7 shares kitty placement ids across images — a second image placed with `p=1` removes the first one's — so every placement takes its own image's id (preview's layers, find's tiles). It leaves `CSI 16t` unanswered, so cell sizes come from `OSC 1337;ReportCellSize` (points and a scale) first. `SetProfile` raises a permission bar until the user picks Always Allow; any keystroke dismisses it as a denial.
- iTerm2 3.7 turns every OSC color into a profile change: its parser pauses on each one (`addUnmanagedPausedSideEffect`) while the main thread copies the session's profile, logs the change and reloads every setting from it (`setSessionSpecificProfileValues`) — about 6 ms apiece at 80×25 and 9 ms at 160×50 (3.7.3, against a DSR round trip), so a palette's twenty kept iTerm2 busy for 170–200 ms a preview hover and an arrow key held at 30 Hz kept preview moving for 0.8–1.9 s after release, where Ghostty answers such a frame in 0.1 ms. A hover therefore paints through `__tt_pv_paint`: the default paints the whole palette and records it in preview's `painted`; the iterm2 adapter paints the background and foreground alone (OSC 11, 10), and while the terminal does not hold the hovered palette (`applied` ≠ `painted`) the frame spells its ANSI colors out in truecolor — bold blue as bright blue, as iTerm2's default Brighten bold text draws it — which iTerm2 reads in the same space as an OSC color (`p3`), so the frame looks the same, iTerm2 answers a hover in about 35 ms (mostly its 1/30 s report tick) and a held key stops within 25 ms of release. Picking paints the other eighteen once (110–160 ms, paid once) inside the synchronized update that leaves the alternate screen, so the shell's screen comes back in its final colors rather than changing one color at a time; `find` gets the whole palette painted first, since it draws with ANSI colors. `latency.zsh check` fails when a hover in iTerm2 paints an ANSI color again. Timing iTerm2 behind other windows needs its `DisableAppNap` setting: napping, a bare DSR round trip takes about 200 ms instead of 20, and a DSR answer always waits for iTerm2's side-effect tick (1/30 s).
- iTerm2 3.7 keeps its default profile in memory: it reads `Default Bookmark Guid` at launch (and then adopts a dynamic profile it names), and writes its in-memory value back whenever that profile is replaced — a dynamic default is replaced on every dynamic-profile reload, so while the default is dynamic an outside write is undone within a second. No AppleScript command, escape sequence or dynamic-profile key sets the default (it strips `Default Bookmark`, issue 4115), a dynamic profile whose Guid a regular profile has is refused, and the Python API that can is off until the user enables it. A child profile's `Keyboard Map` replaces its parent's whole, so ttheme sets no key bindings.
- iTerm2 3.7's Metal renderer flips the `y` of a kitty source rectangle (asking for the top half draws the bottom one; the legacy renderer, which iTerm2 falls back to on battery, does not), and it draws no placement that leaves the grid, relative or not — so there is no way to show part of a picture vertically except cutting it first, which the iterm2 adapter's `__tt_bg_crop` does unless the crop is centered — two `sips` runs, about 100 ms of preview's first hover on each picture when the window is wider than the picture (`sips --cropOffset 0` means centered, so a top band is padded first); each band is sent once and placed after that. Its `ED 2`, and `CSI H CSI J` in the alternate screen, push the whole screen into scrollback, kitty placements included, so preview and find clear with `\e[K\e[2H\e[J` and delete images with `a=d,d=A` instead.
- tmux keeps an OSC 11 as the pane's own background and then paints every cell with an explicit `48;2;…` (`input_osc_11` → `tty_default_colours`), and Ghostty draws an explicit cell background opaque over `background-image` (and iTerm2's) — so inside tmux the layer never tells tmux its colors: `__tt_tmux` (once, at shell start) turns the pane's `allow-passthrough` on when it is off and the server's `focus-events` on, and sets `TTHEME_TMUX` unless the client is control mode (`tmux -CC`, where iTerm2 reads the pane's raw output itself); then `__tt_out` wraps every color OSC and iTerm2's `SetProfile` in `\ePtmux;…\e\\` for the outer terminal, as tinted-shell does. The colors therefore belong to the terminal tab, not the pane: a pane re-wears its palette when tmux reports focus (`__tt_rewear`), the tab's current bg is kept in the session option `@ttheme_bg` (tmux answers OSC 11 from a bg it cached at attach, so `__tt_query_bg` reads the option first) and iTerm2's shown profile in `@ttheme_shown`, a pane ignores the `TTHEME_SPEC` inherited from the tmux server's environment, a shell outside tmux re-wears itself at the prompt after a `tmux` command (`__tt_mux`/`__tt_unmux`) — one that wears no palette sends iTerm2 an empty `SetProfile`, which iTerm2 reads as its default profile (`screenSetProfileToProfileNamed`), so the tab looks like a new one (`__tt_unshown`) — and `__tt_reload` walks up from the tmux client (`#{client_pid}`) instead of the shell. tmux answers `CSI 16t` but turns a kitty APC into the pane title (`input_exit_apc`, `allow-set-title`), so preview skips its picture layers, tuning and find inside tmux (`__tt_pv_bg_open` leaves `bgcw` 0).
- Alacritty's parser (vte) keeps at most 16 OSC parameters and drops an OSC 4 whose count then comes out even, so a palette in one OSC 4 never reached Alacritty's ANSI colors: every OSC 4 carries one color (`__tt_osc_apply`, `paletteOsc`).
- kitty on macOS draws nothing while its window is occluded or the screen is locked (`windowDidChangeOcclusionState`), and `get_window_logo_settings_if_not_default` reads a logo only once it has been drawn — so a kitty screenshot needs the window in front on an unlocked screen, while OSC queries and user vars work either way. `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked` tells.
- `tests/tui.zsh` unsets the terminal-identity variables (`GHOSTTY_RESOURCES_DIR`, `KITTY_WINDOW_ID`, …) before each capture: its tmux server inherits the environment of whatever terminal runs it, so without that the ghostty adapter loads locally but not on CI and the screens diverge.
