# Terminals, pictures and the shell layer

## Conventions

- A palette keeps every picture installed on it, and `backgrounds/images.json` (`Store`, `src/backdrop.ts`, versioned) is the one record of them: per palette the pictures in install order — key `<site>_<id>`, stem, `@fill` crop, default opacity, the `tone` and `blur` its files were drawn with and the `window` its fill was framed for, `# from` source, the `artist` names and the artwork's `source` page, original under `originals/` and, for a Vision cut-out, the cut's alpha beside it (`cut`) — and which one is `active`. Only the CLI writes it (`installBackdrop`, and `ttheme image <palette> show|drop [<picture>]`, a hidden verb in `src/images.ts` that preview calls when its tuning panel's picture strip is kept and on `D`), and every write regenerates that palette's `backgrounds/<palette>.conf` from it, which is a view for the terminals: the active picture's `# by <artist>,<artist>` (names with no space or comma, only when it has any) and `# from`, `# image <key> <at>/<of>` (the shell reads the count from it), a `# picture <key> <stem> <fill> <opacity> <artists|-> [<from>]` line for every picture the palette holds (preview's strip reads them; `bgby` carries the artists, which the tuning panel's title names before the post and keeps longest as the title narrows (`__tt_pv_bg_title`), and `bgurl` the `# from` line's page, which makes the post a link marked `⧉` in its site's color — `TTHEME_SITE_ANSI` in `palettes.zsh`, from `SITES` — where the adapter opens OSC 8 links), its `@fill` crop, and includes of that picture's own `<stem>.tune.conf` and `<stem>.off.conf`. `sync` rewrites every conf whose text differs from what the store makes (`freshenConfs`), so an upgrade's first init brings the older confs up to date. A picture's files are `<palette>.<hash>.png` (the figure), `<palette>.<hash>@fill-N.png`, the bakes preview makes on the same stem, and its tuning — all beside each other and never moved, so switching only changes `active` and the conf, and `drop` deletes the stem's files and the original. The hash is of the key and the images' content, because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name. Every picture file (figure, fill, the CLI's bakes) is an 8-bit indexed PNG whose 256 palette entries are all the tone and whose tRNS ramp makes the index the alpha — the ink, luma × alpha of the original, lifted until its top 1% reaches the tone (at most ×2, `liftOf`) and blurred by `TTHEME_BG_BLUR` — so the terminal's own straight-alpha blend over the background draws the tint (Ghostty's `bg_image` shader, and iTerm2, which then draws the same gamma-linear ramp Ghostty does where it used to darken a full-color tint's midtones — measured) and no pixel carries the background; `sips` bakes come back RGBA with the tone in every pixel, which is still the same picture. A palette whose `backdrop` tone or opacity changes is repainted by `sync` (`retint`): the files' PLTE is swapped (a `sips` bake is re-encoded from its alpha), they move to a new stem, the tuning moves with them and an opacity equal to the old default follows the new one. A `blur` that no longer matches the setting, or a picture with no `tone` (drawn before this format), is drawn again from its original by `redrawPictures` (`src/redraw.ts`, a pool of render workers running `redrawOne`, `src/pictures.ts`) — at every `init` after it applies, and through the hidden `ttheme redraw` that `ttheme config` runs when the `TTHEME_BG_BLUR` line changed and preview's alt-c panel runs when its `blur` row is saved; a picture drawn before cuts were kept finds its cut in the find cache or asks Vision again, and one without an original is left as it was. The CLI reads `TTHEME_BG_BLUR` from `config.zsh` itself (`blurOf`), never from the environment `__tt_cli` hands it, since an older shell still holds the old value and would draw every picture back. Tuning belongs to the picture, not the palette; the shell layer takes the file names from the conf's includes (`bgtunef`/`bgofff` in `__tt_bg_load`), falling back to `<palette>.tune.conf` for a conf the user wrote. In preview a picture's state is keyed by the palette for the active one and `<palette>:<key>` for the others (`__tt_bg_load` makes their conf lines from the `# picture` line); the tuning panel's strip (`__tt_pv_bg_strip`, up to five thumbnails of the pictures' fills as kitty placements `p=700001`–`700005` at `z=-1`, drawn by `__tt_pv_flush` after the frame so a resize's `d=A` cannot take them) follows `,` `.`, which only change what preview shows (`tpick`); enter keeps the tuning of every picture touched (`bgedit`) and the choice (`bgview`, `bgswap`), esc puts back every picture's state from when the panel opened (`tsnaps`), and the preview's close writes the tuning first and then shows the kept picture with `ttheme image <palette> show <key>`. `=` puts the field under the cursor back to the conf's defaults and `+` all of them, and a `↺` marks each field off its default. `f` and `D` change what the palette holds, so they write its kept tuning first and read it again after (`__tt_pv_bg_commit`, `__tt_pv_bg_reset`); installing the same post again starts from the defaults (the old stem's files go). A missing `images.json` is built once from the layout before it (`migrate`: the shown conf plus `backgrounds/shelf/<palette>/<key>/`), keeping a picture whose conf has no `# image` line under `picture_<hash>` rather than dropping it, and leaving a conf ttheme did not write alone and out of the store; `sync` opens the store, so an upgrade migrates at its first `init`, add or remove. Every file a terminal or another shell reads — the store, the confs, `palettes.zsh`, `installed.json`, the iTerm2 profiles — is written to a temp file and renamed over (`writeAtomic`, `src/edits.ts`; `__tt_put` in `ttheme.zsh`, which writes through a symlink to its target, ignores `noclobber` and renames with zsh/files' `zf_mv`, so a picture change forks nothing — `config.zsh`, the pins file and the remembered colors go through it too), so a reload never reads half a file. There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which the ghostty block always includes. Wearing a palette — `ttheme use <name>`, preview's enter, `ttheme next`, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: `__tt_precmd` turns focus reporting (mode 1004) on at every prompt, `__tt_preexec` turns it off before each command, and Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd) — so the picture belongs to the tab you are looking at, not to the last tab that switched, and a busy tab catches up at its next prompt. A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is written or reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own.
- A picture can keep its own colors instead of the tone (`Picture.coloring`, `'tone'` when absent; `Coloring` in `src/backdrop.ts`): an 8-bit RGBA PNG of the original's colors and its own alpha (a cut-out's, or none), blurred as premultiplied planes (`blurColors`), placed with the same `fillFrame`, lifted by nothing, and carrying no `tone` — `undrawn` is a picture with neither. Every terminal lays it over its background at `background-image-opacity` exactly as it lays a tone's ramp, and preview's veil and the kitty and WezTerm handlers never read a pixel, so no adapter names the coloring; the only shell code that does is the `# colors <key> original` conf line (`confText`; `bgcolors`, `__tt_bg_coloring`) and the tuning panel's fourth row and its `c` key from any row, which call the hidden `ttheme image <palette> tone|original [<picture>]` (`redrawColoring`, `src/redraw.ts`) and reopens on the same picture (`__tt_pv_bg_recolor`) — the coloring is a redraw from the original, so it is never staged or undone with esc. Its default opacity comes from its `peak`, the color of the brightest 1% of its visible pixels by relative luminance (`peakOf`): `originalOpacity` is the highest opacity at which the palette's text passes the gate on that color and it is no brighter than a tone picture may be (`fade`, shared with `toneFor`), so a picture with white in it opens at about half a tone's opacity. A palette whose text colors change moves it without drawing again (`retint` with a `Paint` per palette, `restrength`); redrawing into the other coloring keeps size and position and drops a tuned opacity, whose scale differs. `TTHEME_BG_COLORS` (`coloringFor`, read from `config.zsh` like the blur) only names what `find` and `add` install from now on; it never redraws.
- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image next|prev|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshPictures`, which runs every wired terminal's `pictures`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`, and `default` while the tab is still on `ttheme · default`, read through `TTHEME_STARTUP` so it follows a default changed elsewhere); it never asks for a reload, and with no focus tracking the layer syncs once at shell start instead. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown` and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band `sips` cut first, into a scratch dir `__tt_pv_bg_close` removes).
- One setup can wire several terminals, and a change made from any reaches all of them. `palettes.zsh` carries the wired terminals as `TTHEME_TERMINALS`; preview's saved pictures go through `__tt_bg_saved` (`_bg.zsh`) to `__tt_pictured` (`_wired.zsh`), which rewrites `ttheme.json` when iTerm2 is wired and reloads Ghostty when `shown.conf` names one of them; `ttheme default` and a catalog change that moves the startup palette (`__tt_catalog`) reload Ghostty too. `__tt_reload` reloads only the wired terminals that have a `__tt_reload_<id>` (Ghostty). Tuning is written for every wired terminal: with iTerm2 wired, a picture that is not centered is baked at the window size even when it is tuned in Ghostty (`__tt_bg_aligns`, and `aligns` on the CLI's side, from the wirings' `bakes`), since iTerm2 cannot place one.
- Every terminal ttheme wires is one module in `src/terminals/` (`WIRINGS` in `index.ts`, ids in `WIRED`) implementing `Wiring` (`types.ts`), and `src/palettes.ts` only orchestrates, naming none: `sync` builds one `Ctx` and runs every wired terminal's `sync` through one `Out` (`write` content-compared and atomic, `wire` through `editUserFile`, `themes` for the emitter's files under its `shelf`, `remove`, and `repaint` when open tabs must repaint), then rewrites `palettes.zsh` with each wiring's `layer` values; `wiringPlan`, `wiringNotes` and `wiringNext` are init's lines, `forget` drops removed palettes' theme files, `refreshPictures` follows a picture change, and `unwire` gives uninstall its edits, removals and touches (every wiring, whatever `installed.json` says). A terminal whose default is a profile (iTerm2, Konsole) has `defaults`: `base` keeps the user's own in `installed.json` (`itermBase`, `konsoleBase`), and `point` moves new tabs to ttheme's profile or gives the user's back, returning whether a running app needs a restart; `commit` runs them (`withBases`, `pointDefaults`) when a startup palette appears or vanishes, when `default`, `on` or init ask (`take`), or when the startup palette changes — without `take`, a terminal whose current default is not ttheme's keeps it. Every external command a wiring runs (`defaults`, `pgrep`, `dbus-send`, `cmd.exe`, `wslpath`) goes through `Host.run` (`systemHost`), which the tests fake. A new terminal is a module, an emitter, a `TRAITS` row and an adapter, and `src/terminals/index.test.ts` holds them together and to the support tables.
- The shell layer names a terminal only in `ttheme.zsh`'s detection block; `_osc.zsh` and `_bg.zsh` name none, and an adapter names only itself (`terminal.test.ts`). Everything a terminal does differently is an adapter hook overriding `_osc.zsh`'s default — the paint and reset (`__tt_osc_apply`, `__tt_osc_reset`, `__tt_pv_paint`, `__tt_reset_reloaded`), what it hears at start (`__tt_hear`, `__tt_heard`), pictures (`__tt_shown`, `__tt_unshown`, `__tt_bg_*`), `__tt_reloaded`, `__tt_worn`, `__tt_keepable`, `__tt_follows_focus` (bind focus reporting: Ghostty, kitty, Windows Terminal — `latency.zsh forks` reads it from the adapters) and `__tt_paints`/`__tt_unpainted`: in a terminal the layer cannot paint (an unwired Konsole, and a Warp that is unwired or has no settings file) the layer stays inactive and refuses the tab verbs (`TTHEME_TAB_VERBS`, from `src/verbs.ts`) and the bare menu with that terminal's own message; `__tt_follows_prompt` has the layer add the adapter's `__tt_prompted` to every prompt (Warp). What a wired terminal needs when another tab changes the state they share lives in `_wired.zsh`, one `__tt_<event>_<id>` per terminal behind `__tt_reload` and `__tt_pictured`.
- WezTerm, Windows Terminal and Warp are wired by `sync` too, each through the one file ttheme may own there. WezTerm's config is Lua, so `sync` writes `~/.config/ttheme/wezterm.lua` (`weztermModule`, `src/emit/wezterm.ts`: the startup `color_scheme`, the colors dir, and a picture handler) and keeps a `-- ttheme begin`/`-- ttheme end` block that `dofile`s it just before the user config's last `return config` (`upsertLuaBlock`; `~/.wezterm.lua` wins over `$XDG_CONFIG_HOME/wezterm/wezterm.lua`, as in WezTerm) — a config with no such line is left alone and init says so; WezTerm reloads the module on its own because it watches it. Its OSC palette is per pane but a `background` is per window: the shell's `__tt_shown` (wezterm adapter) sets the pane's `ttheme_shown` user var, and the module's `user-var-changed` and `update-status` handlers put the active pane's picture on its window through `set_config_overrides`, reading `backgrounds/<palette>.conf` with its `.tune`/`.off` includes itself, so nothing reloads when a picture changes elsewhere; while preview is open it sends `ttheme_view` instead — the frame `__tt_bg_frame` computed over the grid, with the picture, its opacity and position — which the module (`framed`) maps onto the window the way WezTerm draws the saved conf, the grid canvas scaled to cover the window and aligned by the position, so its tuning panel shows what saving writes (measured: the live and the saved picture's edges within 2 px); closing preview clears it and the window goes back to `ttheme_shown`. A tuned picture is written through `_bg.zsh` as in every other terminal, and `__tt_bg_refresh` sends `ttheme_shown` again so the module rereads the confs. Windows Terminal reads fragments but watches only `settings.json`: `sync` writes `%LOCALAPPDATA%/Microsoft/Windows Terminal/Fragments/ttheme/ttheme.json` (every scheme, plus an `updates` of the profile init ran in — `WT_PROFILE_ID`, else `defaultProfile` — wearing the startup palette) and then touches every `settings.json` it finds so the terminal reloads; init resolves `%LOCALAPPDATA%` (from WSL through `cmd.exe` and `wslpath`) and keeps it as `wtHome` in `installed.json`. A settings reload makes Windows Terminal reset every OSC color in every pane (`Terminal::UpdateColorScheme`, read in its source, not measured), so `sync` touches `settings.json` only when the fragment changed, the windows-terminal adapter's `__tt_reloaded` repaints the tab whenever `palettes.zsh` moves (`sync` moves it whenever it touched `settings.json`, even when its content is the same), and the adapter binds focus reporting as Ghostty does, so a tab repaints at its next prompt or focus. Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes` — the released Warp reads no subfolder there) and, when its `settings.toml` exists (a feature-flagged build), the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/terminals/warp.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 0.5 s later if the settings are still unchanged and the theme file is still there (`WARP_LATER`) — a file 0.1 s old is already worn right, one written in the same moment as the settings is not (measured, three runs at each age). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the warp adapter paints a tab through that key: with Warp wired and a `settings.toml` (`__tt_warp_wired`), `__tt_apply` points the `theme` line at the palette's newest theme file (`__tt_warp_value`, the newest hashed one by a zsh glob, so no fork) through `__tt_put`, so a linked dotfile survives, and writes nothing when the line already says it — every write reaches Warp's `Theme` preference, which its settings sync sends to the account (`SyncToCloud::Globally`) — keeping the user's own value in `warp.base` the way `sync` does; `__tt_osc_reset` puts on the default palette, or while ttheme is off the value in `warp.base` (`"dark"` over none) and removes `warp.base` once the user's theme is back (`__tt_warp_want`, `__tt_warp_wear`, which also waits until a theme file is 0.26 s old, since Warp falls back to its default for one it does not know yet). A new tab hears the default palette instead of asking Warp, whose answer is whatever tab is in front (`__tt_hear`; a shell started inside a painted tab hears the palette Warp wears). Warp tells an idle prompt nothing when its tab comes to the front — its `TerminalView` reports focus only while it holds focus itself, and at a prompt its input editor does — but it saves its session to its sqlite database (`~/Library/Group Containers/<team>.dev.warp/Library/Application Support/dev.warp.Warp-Stable/warp.sqlite`, `$XDG_STATE_HOME/warp-terminal/warp.sqlite` on Linux) at every tab activation and window activation (`should_save_app_state_on_action`, `on_active_window_changed`), at once and while `restore_session` is on (its default), and every shell knows its pane as `WARP_TERMINAL_SESSION_UUID`, the hex of `terminal_panes.uuid`. So every tab records what it wears in `$XDG_STATE_HOME/ttheme/warp/<uuid>` — its pid, the default it wore it under, its palette (none for a tab that never painted, which follows the default) and preview's view — from each paint, reset and prompt (`__tt_warp_publish`, `__tt_prompted`), and one follower per user (`__tt_warp_follower`, a `zsh -f` sourcing the layer, kept single by a `zsystem flock` on `warp/.follow` and started by any prompt that finds it gone — one process per Warp session) polls the database's modification time every 0.1 s, reads the front tab with one `sqlite3` query when it moved (`TTHEME_WARP_SQL`: `app.active_window_id`, that window's `active_tab_index`-th tab by id, its focused leaf, `terminal_panes.uuid`; no active window while Warp is in the background, which changes nothing), writes it to `warp/.active`, and puts on that tab's palette when the front tab, its record or `palettes.zsh` moved (`__tt_warp_tick`); a record made before ttheme went off gets the user's theme, as Ghostty's tabs turn off at their next focus, and the follower leaves when no recorded shell is alive (`__tt_warp_live`). A command's `sync` writes the default (or while off the user's theme) over the key, so the warp adapter's `__tt_reloaded`, which `__tt_catalog`, `__tt_switch` and `__tt_fresh` call after `palettes.zsh` is read again, puts the tab's own palette back. A tab behind another writes nothing itself (`__tt_warp_here` reads `.active`, trusted only while the follower holds its lock); without a follower (no `sqlite3`, no session id) `__tt_prompted` runs `__tt_sync`, so a tab puts its palette back at its prompt. Measured on 0.2026.09.16: seven clicked tab switches each reached the database within milliseconds, and switching two sandbox windows through `warp://session/<uuid>` moved the key 0.17–0.21 s after the switch was asked for, four times out of four, before Warp's own 0.5 s settings debounce (`WarpManagedPathsWatcher`). Split panes are not followed, since `FocusPane` saves nothing. Terminal.app (`TERM_PROGRAM=Apple_Terminal`) takes every OSC color but ignores the OSC resets, so its startup answer is all 20 colors rather than the background alone (`__tt_hear`, one batched query): `__tt_heard` keeps them as the base `__tt_osc_reset` puts back, and `__tt_start_bg` takes the startup background from them.
- Warp shows a picture through its theme: a palette whose `backgrounds/<palette>.conf` names one gets `ttheme-<stem>.<hash>.png`, the picture laid whole on the palette's background (`flatten` at 1, `src/png.ts`, written by `encodeRgb` as an RGB PNG at deflate level 1 rather than through pngjs, whose defaults try every filter at level 9; `warpPictureFile` names it by the 32-bit FNV-1a of the picture's path and the lowercased background), and `ttheme-<stem>.<hash>.yaml` beside its plain theme showing that file at the picture's opacity (`warpThemeFile`/`warpTheme`, `src/emit/warp.ts` — the hash is of the laid file and the opacity). Warp draws a theme's picture first and lays the theme's background color over it at 1 − opacity: a picture with transparent parts turns the window see-through by as much (measured: a fully transparent picture at 80 turned `#204060` into `#aeb3b8`), which is why the picture goes out laid on the background, and a picture laid whole at `opacity: 19` shows the same colors as one laid at 0.19 at `opacity: 100` (measured at five points, exact). While Warp loads a picture it has not shown yet it draws only that color layer for a frame, so the window shows through by the opacity: at 100 that frame is the whole window light grey, at 19 a faint lift (measured six times each: `#bdbdbd` against `#3e3634` over `#211513`) — hence the opacity stays Warp's, and a change of opacity alone keeps the same laid file, which Warp already holds. The Warp wiring's `sync` and `pictures` hooks write them (`laidFiles`, `writePictures`, `src/terminals/warp.ts`; `refreshPictures` calls `pictures` whenever a picture changes) — a palette whose picture cannot be read wears its plain theme — move the `theme` key to the new file while Warp wears that palette and it is still installed (`wearWarp` with `keep`, through `WARP_LATER` when the file is new), and delete the palette's other hashed files unless the key still names one — so a stale one goes a sync later — and every laid file no theme names. Warp reads a theme file once — rewriting the one it wears changes nothing on screen, and neither does renaming another file over it, deleting it or writing it again after a delete (measured) — hence a new name for every change. Warp shows any change of the key 0.58–0.77 s after the write — a plain theme, a picture it has shown and a new one alike, PNG or JPEG, whole or half size, a rename or an in-place write (measured over forty switches); an in-place write that leaves the file short for a moment makes it log `Failed to reload settings file` and keep the old state. Warp has no position or size, and draws every picture as cover, so the Warp wiring `bakes`, and with Warp wired `__tt_bg_write` bakes every tuned size up to 100% onto a window canvas — centered ones too, `__tt_bg_covers` in `_wired.zsh` — and `__tt_bg_aligns` is false, as with iTerm2; `__tt_pictured_warp` runs `ttheme image <palette> tuned` unless iTerm2's hook already did. In preview the warp adapter sources `_bg.zsh` but never draws its kitty layers: `__tt_pv_bg_show` does nothing while a picture is untuned — the palette's theme already carries it — and draws nothing either while keys keep coming (the next within 0.15 s, `zselect -r 0`, which reads nothing), so a held key renders once, when it is let go, not four times a second with a grey frame each; otherwise `__tt_warp_view` writes a short-lived `ttheme-<stem>.view-<n>.yaml` (the plain theme plus the picture at its opacity) first and then has the hidden `ttheme flatten` lay the picture whole on the background in one pass — the saved file itself when it exists (`__tt_warp_saved` names the file `__tt_bg_write` would record for this tuning: the base, the fill, the kept bake or the bake to come), else the source in the frame `__tt_bg_frame` gives on the grid's canvas, passed as `<canvas> <place>` geometry, at the picture's own resolution when Warp would enlarge it anyway (`canvasOf`, so a 140% step is 1926×1349 instead of 2912×2040) — into Warp's themes folder under the name a save gives that picture (`__tt_warp_laid`, the same FNV-1a without a fork, which `palettes.test.ts` holds to `warpPictureFile`), so a state seen before is never drawn again, an opacity step draws nothing, and the saved theme shows the very file the view showed, which Warp already holds (measured: no frame changes on applying); the files it made (`TTHEME_WARP_LAID`) that no theme names 10 s after preview closes are removed (`__tt_warp_sweep`), as `sync` removes any other; it points the key at the theme once that is 0.25 s old, setting preview's `applied` and `painted` so its paint does not put the plain theme back, and records the view, so the follower puts it back when the tab returns to the front. A step takes 0.2–0.3 s where five `sips` runs and a second node process took 1.8 s. `__tt_pv_bg_close` wears the palette again and removes the view unless its picture has a kept tuning (`bgedit`) or is the picture chosen to be shown (`bgview`), which the close is about to save: that view stays up while `refreshPictures` moves the key off it to the new pictured theme (`wearWarp` in keep mode, through `WARP_LATER` when that file is new), so the saved picture never flicks back to the old one, and the warp adapter's `__tt_bg_refresh`, which `__tt_bg_saved` calls after the CLI, only removes the view file. The warp adapter bakes a saved tuning with the hidden `ttheme bake` (the picture placed on a transparent canvas of the same size in one pass) instead of five `sips` runs: 0.39 s against 0.89, alpha within 2 of the `sips` bake and the tone exact, so closing preview after a save takes 0.68 s where it took 1.54 (measured in a pty). Nothing is swept sooner, since Warp may fetch a view's picture again until it has moved off it (its log: `Asset fetch failed`). `__tt_bg_cells` divides `CSI 14t` by `CSI 18t` — Warp answers no `CSI 16t` — and doubles it, because Warp reports points and draws at twice that on a Retina Mac. find and the tuning strip draw with kitty graphics, where Warp differs from every other terminal (measured on 0.2026.09.16, `window.zsh --warp`): it refuses `t=f` (`UnsupportedPlatform`), so `TRAITS.warp.files` is false and pictures go out as chunked base64 (`transmit`, `__tt_bg_transmit`, one `base64` fork per picture sent); it ignores a source rectangle, so `bands` is on; it draws every negative `z` above non-default cell backgrounds — so `TRAITS.warp.layers` is false and find draws no cover there, which would hide its loading bar and every colored cell, and preview's `__tt_bg_hide` puts the palette's plain theme on before it runs find; placing an image again under the same `i` and `p` adds a second placement rather than moving the first (`TRAITS.warp.moves`, so find deletes it first; iTerm2 cannot take that, since its `d=i` frees the data), `EL` and `ECH` leave a placement alone, and a relative placement answers OK but is drawn at its parent, ignoring `H`/`V`. `cellReport` reads the window and grid reports when no `CSI 16t` comes back.
- kitty is wired through a watcher `sync` writes to `~/.config/ttheme/kitty.py` (`kittyWatcher`, `src/emit/kitty.ts`), loaded by the kitty block (`watcher`, plus `window_logo_scale 100` and `window_logo_alpha 1` unless kitty.conf sets them itself). The kitty adapter talks to it through user vars (`__tt_kitty_var`, the value base64'd in zsh by `__tt_b64s`, so a paint — every preview hover among them — forks nothing): `ttheme_worn` on every paint and reset (the `__tt_worn` hook in `_osc.zsh`), `ttheme_shown` from `__tt_shown`, and `ttheme_startup` from `__tt_reloaded` after `palettes.zsh` moves. A window's picture is its logo, read from `backgrounds/<palette>.conf` with its includes and re-read on focus; kitty 0.49 draws logos at the global alpha and scale only (`draw_window_logo`), so the watcher fades the PNG's alpha to the opacity itself (`load_png_data`/`png_from_32bit_rgba_data`, about 0.3 s for a 1880×1008 picture, cached). kitty's `auto_reload_config` (on by default) reloads when `kitty.conf` or any file it includes changes, and a reload resets every OSC color (measured): the watcher wraps `boss.load_config_file` and puts each window's `ttheme_worn` palette back right after it, and `ttheme_startup` patches the configured colors (`patch_colors(…, True, ())`, which leaves open windows alone) for a kitty whose auto reload is off. Preview and find reuse `_bg.zsh`: kitty draws below-background placements above the logo, so preview's layers cover it; the adapter places them absolutely (no relative placements, no margins). `sync` writes a file only when its content changed, so an add or remove that leaves kitty's files alone reloads nothing.
- Alacritty takes its startup palette through `general.import`: `upsertAlacrittyImport` (`src/terminals/alacritty.ts`) appends a `[general]` block to a config without that table, or puts the import line inside the config's own `[general]` (TOML defines a table once), and leaves a config that already imports there or defines `general` otherwise alone — init notes it. Alacritty live-reloads the config and its imports and keeps OSC colors through a reload (measured).
- iTerm2 has no config file, so `sync` owns `~/Library/Application Support/iTerm2/DynamicProfiles/ttheme.json` whole: one `ttheme · <palette>` profile per listed palette (`itermProfiles`, `src/emit/iterm2.ts`), rewritten on every add/remove/browse and reloaded by iTerm2 on its own, plus `ttheme · default` (Guid `ttheme-default`), a copy of the startup palette's profile: `ttheme default` rewrites it, and every tab still on it — new ones and ones never painted — follows within about 0.3 s, which is iTerm2's side of Ghostty's `theme =` and reload. It is also iTerm2's default profile, so a new tab or window is created wearing it and never switches after it opens — a shell that moved a new tab onto it would flash the old profile first, which is never acceptable. `init` and `ttheme default`, and an add, remove or browse that makes a startup palette appear or vanish (never any other, so a default the user picked in iTerm2 stays), point `Default Bookmark Guid` at it through `defaults` (iTerm2's `defaults.point`, `src/terminals/iterm2.ts`, run by `pointDefaults`) and write the profile they replace to `installed.json` as `itermBase`, which every ttheme profile names as its `Dynamic Profile Parent GUID` so fonts, keys and the rest keep coming from the user's own profile; `ttheme off` or removing the last palette gives `itermBase` back. A running iTerm2 takes the new default only at its next start — the notes say so. While off, or with no palette installed, there is no startup palette and no `ttheme · default`; `ttheme on` and `ttheme default` turn it back on, and init's "pick a default palette in ttheme preview?" answered no installs off. `TTHEME_ITERM_SUITE` names the preferences domain (`com.googlecode.iterm2` by default); the sandbox sets it to its own suite so nothing reaches the user's iTerm2. `palettes.zsh` carries the startup palette as `TTHEME_STARTUP`, so a shell that opens on `ttheme · default` knows whose picture it shows. Measured on 3.7.2: iTerm2 reads OSC colors as Display P3 (its `p3` default) and reports an sRGB profile color converted, so the profiles and `.itermcolors` are written in P3 or the shell's OSC 11 palette match fails; and a newly added dynamic profile inherits its parent's light/dark split and then ignores unsuffixed color keys, so every profile sets `Use Separate Colors for Light and Dark Mode` false.
- The CLI talks to a terminal through `src/terminal.ts`, the TypeScript side of what the adapters know: `detectTerminal` (the shell's order — `terminal.test.ts` runs the shell's own detection block against it) and `TRAITS`, one row per terminal: whether it opens OSC 8 links (`linkable`; `palettes.zsh` carries the list as `TTHEME_LINKS`), shows pictures (`showsPictures`: the adapters that source `_bg.zsh`, never inside tmux — the palette editor offers `p` only there), draws a kitty source rectangle upside down (`cropsInBands`), loads a kitty picture from a file path (`readsFiles`), moves a placement placed again under the same ids (`movesPlacements`) and draws negative-`z` layers under cell backgrounds (`layersUnderCells` — `terminal.test.ts` holds it to compat's `kitty-under-bg`, as `bands` to `kitty-crop`; the three are false in Warp alone), paints the background an OSC sets (not Warp), and which colors a live repaint sends (iTerm2's background and foreground alone, as its `__tt_pv_paint`; Konsole's too, since it draws no OSC 4 — `schemes` — and it restores them in hex, `hex`). `livePaint` is the one way a TUI repaints the tab while it browses — browse, init's picker and the palette editor: nothing without a TTY, under `NO_COLOR`, inside tmux (where an OSC 11 becomes the pane's own opaque background) or in Warp; `saved` asks only the colors it will paint and `restore` puts back each of them, resetting one the terminal never reported. In Warp `warpLive` (`src/warp-live.ts`) takes its place: a hover points the theme key at the palette's newest theme once the keys have settled for 150 ms, a palette not installed and the editor's draft (`Live.look`, which the editor calls instead of painting slots) go out as a short-lived `ttheme-<stem>.view-<pid>-<n>.yaml` named once it is 0.26 s old, each view goes as soon as the next is up, and closing puts back the line the tab wore; init's picker paints only over an install that already wires Warp, so nothing touches `settings.toml` before the plan is accepted. `CLEAR` is the only screen clear — never ED 2 or `CSI H CSI J`, which iTerm2 answers in the alternate screen by pushing the screen into its scrollback — and `terminal.test.ts` fails on either anywhere in `src/` or `shell/`. A new terminal gets its `TRAITS` row with its adapter; the tests hold the adapters' files to the table.
- The layer's hot paths start no process: a new tab in `off` and `seq` (all but Terminal.app's `seq`, which asks its 20 colors at start), every prompt's hooks, preexec, `line-init`, a focus-in, a `cd`, and a paint or picture change during preview (`__tt_apply`, `__tt_pv_paint`, `__tt_shown`, `__tt_bg_send`, `__tt_bg_dim`, which reads a PNG's size with `sysread`) — save Warp's follower, which a prompt starts once per Warp session when none runs, and whose `sqlite3` reads run in it, never in a tab. A fork costs 1.5–2.5 ms on macOS against microseconds for a builtin, so reach for `$(<file)`, `zstat`, `sysread -t`, `__tt_b64s` and parameter expansion there, never `$(…)`, a pipe or an external command. `tests/forks.tsv` is the ratchet `shell:check` holds every journey to (`mise run forks`), and `shell/check.zsh`'s `forks_of` holds the paint helpers to zero; a change that removes a fork lowers the file with `mise run forks --update`. `__tt_cli` hands node `NODE_COMPILE_CACHE` under the ttheme cache dir, about 4 ms of every CLI call; node keys the cache by the file's path, so an upgrade overwrites it instead of adding one.
- In `off`, a new tab never waits on the terminal to learn what it shows. The answer its shell needs at start — the background, which names the palette the tab wears (`__tt_wearing`, the startup palette first), or Terminal.app's 20 colors — is kept per adapter in `$XDG_STATE_HOME/ttheme/colors.<adapter>` beside the startup palette it was heard under (`__tt_recall`, `__tt_remember`, `__tt_listen`). A shell uses it before its first prompt and asks again from its first `line-init` (`__tt_line_init` → `__tt_recheck`), where zle already holds the tty raw, so no `stty` runs: a different answer rewrites the file and moves the tab's palette — or a pin's base — and its picture to the fresh one, while an announce already printed stays. Only a tab's own colors may be kept, so every paint exports `TTHEME_PAINTED` (`__tt_osc_apply`; a reset unsets it): a shell that inherits it (`exec zsh`, a nested shell) or paints before its first prompt (a pinned directory) neither keeps nor rechecks, and asks at start as before — as does a miss (no file, another startup palette, `seq`, tmux, no zle, nothing installed), which then writes the file. `line-init` is one widget (`__tt_line_init`: the recheck, then `__tt_typed`, then `__tt_focus_on` where focus is bound), since each `add-zle-hook-widget` costs about 0.5 ms of every start. Measured with `mise run bench --against`: a new tab's first prompt went from +7.2 to +2.6 ms over a bare shell in `off` and from +8.2 to +3.2 ms in Terminal.app, and no adapter adds a process to a start, a prompt, a focus change or a `cd` (a `fork`/`execve`-counting `DYLD_INSERT_LIBRARIES` shim on a re-signed copy of zsh — PIDs cannot tell, the Mac forks about 500 times a second on its own).
- Konsole (`KONSOLE_VERSION`, which Konsole's session sets, so Yakuake and the Dolphin and Kate panels too; 23.08.5 measured under Xvfb, its source read up to 26.04) draws the background and foreground an OSC 10/11 sets, about 20 ms later, and no OSC 12 or 17; it never draws an OSC 4 — it keeps the colors only to answer OSC 4 queries, which therefore report what an OSC 4 set rather than what it draws (compat's `wear` fails there, and `wear-ansi` checks the drawn red on a screenshot); its bare OSC 104/110/111/112 resets do nothing (`110;` and `111;` reset from 25.12); and it parses an OSC 10/11 color with Qt's `QColor`, which reads `#rrggbb` and never `rgb:`, so a TUI restores it in hex (`hex`). A palette's 16 colors therefore reach a tab only through a color scheme: `sync` writes `ttheme-<stem>.colorscheme` (`konsoleScheme`, `src/emit/konsole.ts`: all 30 entries, intense from the brights, faint halfway to the background) and a `ttheme-<stem>.profile` for every listed palette and the startup one (the scheme, the cursor, `Name=ttheme · <palette>`, `Parent=` the user's default — `konsoleBase` — or `FALLBACK/`) into `$XDG_DATA_HOME/konsole`, and drops the profiles of palettes no longer installed. The konsole adapter wears an installed palette with one `OSC 50 ColorScheme=ttheme-<stem>;UseCustomCursorColor=true;customCursorColor=<cursor>` (lowercase: Konsole's own `CustomCursorColor=` shortcut sets the cursor only for the moment) and never an OSC 11 in the same burst, paints any other colors through OSC 10/11 alone, and resets to the scheme a new tab opens with: the startup palette's, or while off the user's own (`TTHEME_KONSOLE_BASE`, the `layer` value `baseLook` reads through the base profile's parents). Konsole loads its profiles and `konsolerc` once per process, so `point` sets `[Desktop Entry] DefaultProfile` in `konsolerc` (giving `konsoleBase` back while off, removing the key when there was none) and then calls `setDefaultProfile` on every running Konsole over D-Bus (`dbus-send`: each `org.kde.konsole-<pid>`, its first `/Windows/<n>`), checking `defaultProfile` after — a Konsole started before that profile existed needs a restart, and ttheme says so. It passes compat's kitty graphics cases, but it keeps a scheme's wallpaper cached while any tab shows the scheme, so a picture tuned elsewhere would not reach an open tab: no pictures (`pictures: false`). The sandbox (`--konsole`, Linux) runs it on its own Xvfb display and D-Bus session (`dbus-run-session`), with `XDG_DATA_HOME` scrubbed, so nothing reaches the user's Konsole.

## Gotchas

- The layer runs inside the user's shell, under whatever options their `.zshrc` set, while every test runs it under zsh's defaults — and `no_clobber` (Prezto sets it) made its writes fail, `ksh_arrays` and `sh_word_split` misread its arrays and arguments, and `no_unset` stopped it loading at all. So every function the shell calls on its own — `ttheme`, each hook, zle widget and the completion — and each block that runs while the layer is sourced starts with `emulate -L zsh ${=${options[xtrace]:#off}:+-o xtrace}` (about 3 µs; the xtrace clause keeps `set -x` and the fork counts working, which a bare `emulate` switches off). `terminal.test.ts` holds every function the layer registers to it, and `latency.zsh check` sources the layer under such a `.zshrc` and uses it.
- Every question the layer asks the terminal goes through `__tt_ask` (`_osc.zsh`): it opens the tty as `{ exec {fd}<>/dev/tty } 2>/dev/null`, because an `exec` with no command applies all its redirections to the shell for good — the plain `exec {fd}<>/dev/tty 2>/dev/null` sent every later command's stderr to /dev/null (measured). It sets the tty up in one `stty` subshell (save, raw, then restore: about 5.7 ms of forks against a 0.1 ms answer, measured) only while the tty is still cooked — never inside zle, which holds it raw already (`zle` answers true there), nor inside preview, which holds it `-echo -icanon` for its whole session (`TTHEME_RAW`) because zsh's own `read -s -k` restores the modes between characters: keys arriving while preview drew were echoed into its frame (39 of 60 held arrows at 160×50, measured; `latency.zsh check` types into it). It appends a DSR (`\e[5n`), reads whole chunks with `sysread -t 0.3` until its `\e[0n`, so it ends as soon as the terminal has answered everything, and then splits the bytes with one pattern: a byte outside an escape sequence is a key the user typed ahead: it goes to `TTHEME_TYPED`, which the `__tt_typed` line-init widget hands back to zle (`zle -U`), so a command typed while the shell starts still runs. Preview drops them (`__tt_pv_bg_open`) — those keys were meant for it.

- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- Ghostty, Alacritty and Warp leave OSC 17 (selection) queries unanswered (`mise run compat`'s osc-selection; Ghostty's `stream_handler.zig` logs "reporting dynamic color highlight_background not implemented"), so a query that waits for every color it asked stalls until its deadline — `queryTerminalColors` (`src/osc.ts`, browse and init's picker) ends at a DSR answer instead, which took 120 ms off every browse in those terminals.
- Preview's search hint animates on a timer, and those ticks redraw its first row alone (`tick`, `__tt_pv_draw hint`): a full frame is about 4 KB and 3.6 ms at 160×50, and the hint had been 9 KB a second of redraws while preview sat idle. The row is cleared with ECH over the list's columns, never `\e[K`, which would take the right panel's header on the same row with it.
- Ghostty applies a SIGUSR2 reload asynchronously, an OSC reset returns a surface to the defaults Ghostty holds at that moment, and a reload does not repaint a surface's current colors (measured) — so a reset sent right after the config changes brings back the old `theme =`. `ttheme off` therefore writes everything first, reloads once, and `__tt_reset_reloaded` (ghostty adapter) resets again every 50 ms while the tab still shows the palette's background, for at most a second. Every other open tab turns itself off too (`__tt_off_here`) at its next prompt or focus, when `__tt_fresh` sees `TTHEME_STARTUP` go empty; `ttheme on` wears the default only in the tab that ran it, and new tabs.
- Ghostty answers focus reporting (`\e[?1004h`) with the current focus the moment it goes on (`stream_handler.zig`, `.focus_event`), and until zle takes the tty raw the kernel echoes that answer as `^[[I` above the next prompt. So the layer turns it on from zle's `line-init` hook (`__tt_focus_on`, last in `__tt_line_init`, after the recheck whose read would otherwise take Ghostty's `\e[I` for itself), where the `^[[I` binding reads it, never from precmd; preexec still turns it off.
- BSD `pgrep`/`pkill` skip their own ancestors, so from inside a Ghostty tab `pkill ghostty` misses that Ghostty. `__tt_reload_ghostty` (`_wired.zsh`) therefore walks up to the Ghostty that owns the shell and signals only it, falling back to `pkill` when the shell sits outside one (tmux, or another terminal such as iTerm2 changing a picture Ghostty shows); the walk runs once per shell and its answer is kept in `TTHEME_GHOSTTY_PID`, since a shell never outlives or changes its Ghostty.
- zsh's `read -k` given `-t` puts back the tty modes zsh last saved when it times out (`settyinfo(&shttyinfo)` in `bin_read`), not the ones it found, and zsh saves them only after a foreground command — a `$(stty …)` does not count. So preview runs its `stty -echo -icanon` in the foreground: from `$(…)` it held at a prompt but not under `zsh -i -c` (the sandbox's `sb_drive`), where the first drain's timeout put echo and canonical input back — keys were echoed into the frame and `zselect -r 0` saw no key without a newline (measured).
- `shell/ttheme.zsh` only runs from an installed layer, with `palettes.zsh` beside it — there is no source-from-checkout path. `shell/check.zsh` assembles such a layer in a temp dir.
- The installed layer `zcompile`s the files it sources (`ttheme.zsh`, `palettes.zsh`, the adapters) into `.zwc` beside them at shell start, and zsh's `source` takes a `.zwc` stamped in the same second as a newer source — so whatever rewrites one of those files deletes its `.zwc` (`applyInit`, `sync`).
- iTerm2 3.7 keeps its sessions alive in `iTermServer` across a quit and saves dynamic profiles into its prefs (`New Bookmarks`), so a test run can come back on an old session or an old profile's values; a dynamic profile without `Dynamic Profile Parent Name` merges into the default profile, which can be itself. Like Ghostty, it starts shells through `login`, which resets `HOME`.
- iTerm2 3.7 shares kitty placement ids across images — a second image placed with `p=1` removes the first one's — so every placement takes its own image's id (preview's layers, find's tiles). Its `a=d,d=i` frees the image's data along with its placements (the spec keeps the data for lowercase), so preview takes a picture down with `d=i,i=N,p=N` and places it again later without resending; a picture sent earlier and deleted by id alone came back as nothing. iTerm2 drops the least recently used images past 320 MB (about 42 pictures at 1880×1008; Ghostty's `image-storage-limit` defaults to the same size), so `__tt_bg_send` keeps the most recently shown up to 128 MB decoded (sized with `__tt_bg_dim`; a tuned picture can be a full 25 MP original) and frees the rest itself (`d=I`), resending one when it comes back, and `__tt_bg_forget` frees them all at a resize, `find` and close. It leaves `CSI 16t` unanswered, so cell sizes come from `OSC 1337;ReportCellSize` (points and a scale) first. `SetProfile` raises a permission bar until the user picks Always Allow; any keystroke dismisses it as a denial.
- iTerm2 3.7 turns every OSC color into a profile change: its parser pauses on each one (`addUnmanagedPausedSideEffect`) while the main thread copies the session's profile, logs the change and reloads every setting from it (`setSessionSpecificProfileValues`) — about 6 ms apiece at 80×25 and 9 ms at 160×50 (3.7.3, against a DSR round trip), so a palette's twenty kept iTerm2 busy for 170–200 ms a preview hover and an arrow key held at 30 Hz kept preview moving for 0.8–1.9 s after release, where Ghostty answers such a frame in 0.1 ms. A hover therefore paints through `__tt_pv_paint`: the default paints the whole palette and records it in preview's `painted`; the iterm2 adapter paints the background and foreground alone (OSC 11, 10), and while the terminal does not hold the hovered palette (`applied` ≠ `painted`) the frame spells its ANSI colors out in truecolor — bold blue as bright blue, as iTerm2's default Brighten bold text draws it — which iTerm2 reads in the same space as an OSC color (`p3`), so the frame looks the same, iTerm2 answers a hover in about 35 ms (mostly its 1/30 s report tick) and a held key stops within 25 ms of release. Picking paints the other eighteen once (110–160 ms, paid once) inside the synchronized update that leaves the alternate screen, so the shell's screen comes back in its final colors rather than changing one color at a time; `find` gets the whole palette painted first, since it draws with ANSI colors. `latency.zsh check` fails when a hover in iTerm2 paints an ANSI color again. Timing iTerm2 behind other windows needs its `DisableAppNap` setting: napping, a bare DSR round trip takes about 200 ms instead of 20, and a DSR answer always waits for iTerm2's side-effect tick (1/30 s).
- iTerm2 3.7 keeps its default profile in memory: it reads `Default Bookmark Guid` at launch (and then adopts a dynamic profile it names), and writes its in-memory value back whenever that profile is replaced — a dynamic default is replaced on every dynamic-profile reload, so while the default is dynamic an outside write is undone within a second. No AppleScript command, escape sequence or dynamic-profile key sets the default (it strips `Default Bookmark`, issue 4115), a dynamic profile whose Guid a regular profile has is refused, and the Python API that can is off until the user enables it. A child profile's `Keyboard Map` replaces its parent's whole, so ttheme sets no key bindings.
- iTerm2 3.7's Metal renderer flips the `y` of a kitty source rectangle (asking for the top half draws the bottom one; the legacy renderer, which iTerm2 falls back to on battery, does not — `mise run compat`'s `kitty-crop`, measured again on 3.7.3, and the sandbox keeps Metal on whatever the power source so that a run on battery measures it), and it draws no placement that leaves the grid, relative or not — so there is no way to show part of a picture vertically except cutting it first, which find's band worker does for the tiles its grid cuts and the iterm2 adapter's `__tt_bg_crop` does unless the crop is centered — two `sips` runs, about 100 ms of preview's first hover on each picture when the window is wider than the picture (`sips --cropOffset 0` means centered, so a top band is padded first); each band is sent once and placed after that. Its `ED 2`, and `CSI H CSI J` in the alternate screen, push the whole screen into scrollback, kitty placements included, so preview and find clear with `\e[K\e[2H\e[J` and delete images with `a=d,d=A` instead.
- WezTerm attaches a kitty image to the cells it covers: text written over it and ECH leave it (an image with a placement id survives a print), but EL and ED take it away with the cells they erase, and every negative `z` is drawn above non-default cell backgrounds — there is no tier below them. Preview's layers and find's cover would hide the selection bar and every background-colored cell, and each EL in their frames would punch a hole in the picture, so WezTerm draws no kitty layers and opens no find (`TRAITS.wezterm.pictures`, held by `terminal.test.ts` to compat's `kitty-under-bg` and `kitty-el`); preview shows its pictures and tuning through the window background instead (above), and the tuning panel's strip, the one kitty placement left there, is placed again after every frame (`__tt_bg_lasting`). WezTerm also holds every answer to a query until a synchronized update ends (compat's `sync-query`), so preview asks for its cell size before it begins one, and `latency.zsh check` fails when it does not. The rest works there: a source rectangle keeps its `y`, a placement deleted by id and `p` can be placed again without resending, `t=f` loads, `CSI 16t` answers, and placing a full-window image cost about 0.3 ms at 80×24 (measured on 20260917-114457-b09b56c2).
- tmux keeps an OSC 11 as the pane's own background and then paints every cell with an explicit `48;2;…` (`input_osc_11` → `tty_default_colours`), and Ghostty draws an explicit cell background opaque over `background-image` (and iTerm2's) — so inside tmux the layer never tells tmux its colors: `__tt_tmux` (once, at shell start) turns the pane's `allow-passthrough` on when it is off and the server's `focus-events` on, and sets `TTHEME_TMUX` unless the client is control mode (`tmux -CC`, where iTerm2 reads the pane's raw output itself); then `__tt_out` wraps every color OSC and iTerm2's `SetProfile` in `\ePtmux;…\e\\` for the outer terminal, as tinted-shell does. The colors therefore belong to the terminal tab, not the pane: a pane re-wears its palette when tmux reports focus (`__tt_rewear`), the tab's current bg is kept in the session option `@ttheme_bg` (tmux answers OSC 11 from a bg it cached at attach, so `__tt_query_bg` reads the option first) and iTerm2's shown profile in `@ttheme_shown`, a pane ignores the `TTHEME_SPEC` inherited from the tmux server's environment, a shell outside tmux re-wears itself at the prompt after a `tmux` command (`__tt_mux`/`__tt_unmux`) — one that wears no palette sends iTerm2 an empty `SetProfile`, which iTerm2 reads as its default profile (`screenSetProfileToProfileNamed`), so the tab looks like a new one (`__tt_unshown`) — and `__tt_reload_ghostty` walks up from the tmux client (`#{client_pid}`) instead of the shell. tmux answers `CSI 16t` but turns a kitty APC into the pane title (`input_exit_apc`, `allow-set-title`), so preview skips its picture layers, tuning and find inside tmux (`__tt_pv_bg_open` leaves `bgcw` 0).
- Alacritty's parser (vte) keeps at most 16 OSC parameters and drops an OSC 4 whose count then comes out even, so a palette in one OSC 4 never reached Alacritty's ANSI colors: every OSC 4 carries one color (`__tt_osc_apply`, `paletteOsc`).
- kitty on macOS draws nothing while its window is occluded or the screen is locked (`windowDidChangeOcclusionState`), and `get_window_logo_settings_if_not_default` reads a logo only once it has been drawn — so a kitty screenshot needs the window in front on an unlocked screen, while OSC queries and user vars work either way. `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked` tells.
- `tests/tui.zsh` unsets the terminal-identity variables (`GHOSTTY_RESOURCES_DIR`, `KITTY_WINDOW_ID`, …) before each capture: its tmux server inherits the environment of whatever terminal runs it, so without that the ghostty adapter loads locally but not on CI and the screens diverge.
