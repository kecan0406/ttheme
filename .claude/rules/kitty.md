# kitty

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only kitty does.

## Conventions

- kitty is wired through a watcher `sync` writes to `~/.config/ttheme/kitty.py` (`kittyWatcher`, `src/terminals/emit/kitty.ts`), loaded by ttheme's `~/.config/ttheme/kitty.conf`, which the kitty block includes (`watcher`, plus `window_logo_scale 100` and `window_logo_alpha 1` unless kitty.conf sets them itself, a `# mode <mode>` line and an include of the startup palette's theme file in that mode — every palette's theme is written in both modes, `ttheme-<stem>.dark.conf` and `.light.conf`, and the watcher re-wears a window from the one the `# mode` line names, which the same write that makes kitty reload changes, so a mode switch rewrites this one file). The kitty adapter talks to it through user vars (`__tt_kitty_var`, the value base64'd in zsh by `__tt_b64s`, so a paint — every preview hover among them — forks nothing): `ttheme_worn` on every paint and reset, sent ahead of the colors so a reload landing between the two puts back the new palette, not the old (the `__tt_worn` hook in `_osc.zsh`), `ttheme_shown` from `__tt_shown`, and `ttheme_startup` from `__tt_reloaded` after `palettes.zsh` moves. A window's picture is its logo, read from `backgrounds/<palette>.conf` with its includes and re-read on focus; kitty 0.49 draws logos at the global alpha and scale only (`draw_window_logo`), so the watcher fades the PNG's alpha to the opacity itself (`load_png_data`/`png_from_32bit_rgba_data`, about 0.3 s for a 1880×1008 picture, cached). kitty's `auto_reload_config` (on by default) reloads when `kitty.conf` or any file it includes changes, and a reload resets every OSC color (measured): the watcher wraps `boss.load_config_file` and puts each window's `ttheme_worn` palette back right after it, and `ttheme_startup` patches the configured colors (`patch_colors(…, True, ())`, which leaves open windows alone) for a kitty whose auto reload is off. Preview and find reuse `_bg.zsh`: kitty draws every kitty graphics placement above the logo, below-background ones included, so preview's layers cover it (compat's `logo-over`, measured on 0.49.2 with the window in front: a full-window placement at preview's picture tier and at `z=-1` hid a 64×64 logo whole); the adapter places them absolutely (no relative placements, no margins). kitty samples a stretched picture against a transparent border, so a 1×1 picture stretched over the window fades from about 81% opaque in the middle to less at the edges, and a 64×64 one over its outer 10 px (measured: the logo and the tab's own background showed through preview's fill, darkened toward the edges); every solid layer is therefore a 3×3 of one color placed through its middle pixel (`solid` and `SOLID` in `src/tui/find/screen.ts`, the same in `__tt_pv_bg_show`), which samples nothing but that color in any terminal — iTerm2's Metal renderer, which flips a source rectangle's `y`, leaves the middle pixel where it is. `sync` writes a file only when its content changed, so an add or remove that leaves kitty's files alone reloads nothing.
- Under `TTHEME_MODE=auto` kitty passes the system's appearance on through the watcher (`TRAITS.appears: 'hooks'`): `sync` writes an `# appearance <path>` line into ttheme's `kitty.conf` (the `appearance` file under `$XDG_STATE_HOME/ttheme`) only while the setting is `auto`, and `on_load` wraps `boss.on_system_color_scheme_change` — which kitty's glfw layer calls on every change of the system's scheme, as does its `simulate_color_scheme_preference_change` action — calling kitty's own first, then `appear`: the shade (`dark`, else `light`, so GNOME's `no_preference` reads as light) written over that file when it differs, through a temp file and `os.replace`, and SIGURG to every pid in `shells/`, which each shell's `__tt_appeared` turns into a remode (`terminals.md`). kitty's documented ways do not fit: the `on_color_scheme_preference_change` watcher event fires only when a window's background changes, and a system switch changes it only through `dark-theme.auto.conf` and `light-theme.auto.conf`, whose colors `patch_colors` writes over every window's OSC colors too — a painted tab would show the startup palette until the remode painted it again — and whose names are kitty's own, which a user's `kitten themes` may already hold. Wrapping a `Boss` method leans on internals kitty's docs call not stable; its signature has been `(appearance, is_initial_value)` from 0.38.0 to the 2026-10 tree, and the watcher leaves kitty alone where it has none. kitty hands the scheme it starts in to `Boss` before any watcher loads, so `on_load` also reads it once (`glfw_get_system_color_theme`) and passes it to `appear`, which a change made while kitty was closed needs. A running kitty takes a new watcher only at its next start (`runpy` runs it once per process), while the `# appearance` line is read at every change, so switching `auto` on or off reaches it at once.

## Gotchas

- kitty's `auto_reload_config` watches through a Go kitten (`kitten __watch_conf__`, since 0.47.0) whose config parser expands variables in an include (`ExpandVars`) but not `~`, while kitty's own loader expands both, so an `include ~/…` loads and is never watched (`mise run compat --linux kitty` on 0.49.2: `follow-default` and `follow-belief` fail with a `~` include and pass from `$HOME`). The block therefore names it from `$HOME` (`kittyBlock`), and the parity model watches what the kitten watches (`kittyFiles`: variables expanded, `~` not, a relative include under the file that includes it) while it loads what kitty loads (`kittyColors`).
- kitty on macOS draws nothing while its window is occluded or the screen is locked (`windowDidChangeOcclusionState`), and `get_window_logo_settings_if_not_default` reads a logo only once it has been drawn — so a kitty screenshot needs the window in front on an unlocked screen, while OSC queries and user vars work either way. `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked` tells.
