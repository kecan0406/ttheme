# Rio

The shell layer's, the wiring's and the picture model's general rules are in `terminals.md`; these are what only Rio does.

## Conventions

- Rio (`raphamorim/rio`) reads `$XDG_CONFIG_HOME/rio/config.toml` (`RIO_CONFIG_HOME` before it, which ttheme does not follow), and a top-level `theme = "<name>"` there loads `themes/<name>.toml` beside it in place of the config's own `[colors]` (`Config::load`/`try_load` in `rio-backend/src/config/mod.rs`; a theme that does not load leaves the config's colors and shows an error). Its config has no include, so the startup palette goes through a theme of a fixed name: `sync` puts a block holding `theme = "ttheme"` at the top of the config (`upsertRioTheme`, `src/terminals/rio.ts`: a top-level key must come before the first table) once, and from then on rewrites only `themes/ttheme.toml` — the startup palette's theme in the mode worn (`rioTheme`, the same text as its `ttheme-<stem>.<mode>.toml`), or, with no startup palette, a copy of the config's own `[colors]` table (`ownColors`, cut from the text, so Rio looks as it does without ttheme while ttheme is off). A config that already sets a top-level `theme` is left alone and init says so, as it does for an `[adaptive-theme]`, whose colors Rio puts over the theme's by the system's appearance.
- Rio watches its config folder without recursion (`frontends/rioterm/src/watcher.rs`, `RecursiveMode::NonRecursive`), so a write under `themes/` is never seen: whenever `themes/ttheme.toml` changes, `sync` touches `config.toml`'s times (`utimesSync`), as the Windows Terminal wiring touches `settings.json`. Rio reloads 250 ms after the first event (`PrepareUpdateConfig` schedules `UpdateConfig`, `frontends/rioterm/src/application.rs`), and the reload builds a new `Renderer` from the config and sets the window's background to the config's (`Screen::update_config`, `set_background_color(dynamic_background)`), while each panel keeps the background an OSC 11 set as its state — so a tab that never painted follows a new default, and a painted one goes on answering its palette's background while it draws the new default's until an OSC 11 comes again (measured on 0.5.28's Linux build: compat's `keep-painted`, which now reads the drawn background, failed with asuka answered and rei drawn, and a repaint drew asuka again). So the adapter's `__tt_reloaded`, which every tab runs once `palettes.zsh` moved, paints a painted tab's palette again, first waiting until `config.toml` was touched 0.35 s ago where it was touched less than that ago, so the paint lands after Rio's reload. The parity model holds both: its `delay` is Rio's 250 ms and its `background` the config's for a tab reloaded since its last OSC 11; it watches `config.toml` alone (`rioFiles`), so a sync that forgot the touch shows up there.
- The detection block names Rio by `TERM_PROGRAM=rio` ahead of Ghostty, since a Rio started from a Ghostty tab carries `GHOSTTY_RESOURCES_DIR`. Rio sets and answers OSC 4, 10, 11 and 12 and resets 104 and 110–112 (`rio-vt/src/performer/handler.rs`), reports focus (mode 1004) and carries the kitty graphics protocol, but leaves OSC 17 alone and answers no DSR 996, so `auto` is offered only beside a terminal that reports the appearance. Its one picture is `[window.background-image]` in the config itself, which ttheme would have to rewrite at every switch, so it gets none (`@pictures`). Read in its source at 59203ccd and measured on Rio 0.5.28's Linux build (`mise run compat --linux rio`, 2026-10-27: every OSC, reset, follow, wear, focus, cell-size and kitty graphics case passes, `kitty-under-bg` and `kitty-crop` too, while `osc-selection`, `focus-answer`, `appearance-report` and `reset-baseline` fail, as the model says); compat's macOS `rio` column is unmeasured, since no Rio.app was run.
