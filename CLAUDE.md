# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3, and node 22 — the oldest `engines` allows, so `bin:check` runs the bundle there on CI too, whose runner ships a newer node) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check (which validates the emitted Ghostty files when ghostty is installed) + node-bundle check + TUI screens + the site's typecheck (`ci:checks`) + the parity walk: exactly what CI runs, which runs `ci:checks` as one job and the walk as four beside it, a few terminals and slots each (`.github/workflows/ci.yml`'s matrix — `parity.test.ts` holds it to walk every terminal once — sized so each walked in 24–27 s on a ten-core Mac, where the whole walk took 125 s on one four-core runner: it walks the terminals side by side but each terminal's journeys one after another per slot, and waits on them rather than the processor — the whole walk at one slot used under one core — so slots buy speed), and a `ci` job gathers them, since the `main` ruleset requires a check of that name. Once it passes it marks the tree it checked (`tests/checked.zsh`: the working tree's own git tree, untracked files included, written to `.git/ttheme-checked` only when it is the same before and after the run, so an edit made meanwhile marks nothing)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run slop` — oxlint with anti-slop's rules, vendored in `tools/oxlint/anti-slop` (its `UPSTREAM.md` names the upstream commit and every local deviation; Biome skips the folder, and oxlint's own default rules are off, so Biome stays the one general linter). `lint` runs it after Biome, so ci does, and `format` runs `oxlint --fix` first. `.oxlintrc.json` turns off the type-assertion `SAFETY:` comment rule, since first-party code carries no comments, and the conditional empty-object spread rule, since `...(x ? { k: x } : {})` is how ttheme writes optional keys, and lets the decoder modules its `overrides` lists — the ones that read a file or a response into ttheme's types — take and return `unknown`, hold it in dictionaries and use `typeof`; a new decoder module goes on that list
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build): `shell/check.zsh`, `latency.zsh check`, the fork ratchet and, where a `ghostty` binary exists, `ghostty +validate-config` on every emitted theme file
- `mise run forks [--update]` — the fork ratchet (`tests/latency.zsh forks`, part of `shell:check`): starts a warm shell per terminal and mode with `xtrace` on and `PS4` printing `$sysparams[pid]`, counts the distinct PIDs each journey leaves in the trace (a new tab in `off` and `seq`, an empty command, a focus-in, a `cd`, a command that resets a painted tab's cursor, and in Ghostty a prompt under `auto`, which waits until the widget has written the appearance the harness answered to DSR 996) beyond a bare zsh, and compares them with `tests/forks.tsv`: more fails as a regression, fewer fails until `--update` locks the lower count in, so a hot path only ever loses processes. The counts are a proxy (a subshell whose only work is forking children hides itself) that agreed with an exact `fork`/`execve` interposer everywhere but `base64` pipes, where it still counted more than none, and a zle widget's own processes never reach the trace at all (line-init, focus, the appearance widget), so `shell/check.zsh` counts the appearance widget's functions with `forks_of`, while line-init's mend and recheck and the focus widget are guarded by no count
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run look <scenario | browse | hub | pins | pin | edit:<palette>> <cols>x<rows> [keys…] [--state empty|few|marketplace|pinned] [--rows a-b] [--cols a-b] [--emit png,txt,styles] [--against <ref>]` — how a TUI screen draws, without a window: the screen runs in a private tmux in `tests/tui.zsh`'s fixture with colors on (a scenario brings its state, screen and keys; keys given after it are pressed next), and `tests/look.ts` replays the capture through `@xterm/headless` into `$TMPDIR/ttheme-look/<name>.png` (the screen in the fixture's default palette — open it with the Read tool; about 650 tokens at 130×38, and a `--rows`/`--cols` crop draws twice the size) and `.txt` (its text, row numbers on the left and a column ruler on top, for exact positions); `styles` lists every styled run's fg, bg and attributes — a palette slot, a truecolor hex or `-` for the default — and is long, so crop it. `--against <ref>` draws the same screen from that commit too (its tree unpacked and built aside, the working tree untouched) and prints only the rows that differ, with the styled runs that went or came — a change's before and after in one call, so never put a file back from git to compare. Look at a screen before reading the code that draws it, and check a change to it with `--against HEAD`. Pictures drawn with kitty graphics (preview's layers, find's tiles, the editor's picture picker) are not drawn; they need the sandbox
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust] | --wezterm | --kitty | --alacritty | --warp | --terminal-app | --konsole] [--pictured] [--zshenv FILE] [--empty | --mine | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing Browse), or the user's own with `--mine` (`bring`: `~/.config/ttheme`'s `config.zsh`, `tone.json`, pins, `kept.json`, marketplace caches and pictures cloned in (APFS `cp -c`, so the pictures cost nothing), every local marketplace folder the install lists cloned under the sandbox's `marketplace/` and renamed in `installed.json`, the pins' `~` made the real home and the confs' paths the sandbox's, `installed.json` taken whole but for the terminals and the profile bases the sandbox's own `init` chose, then `init --yes` again — the update path, which keeps it all; the real install is only read, and `--warp` and `--terminal-app`, which wire the user's own apps, refuse it). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--wezterm` starts a separate WezTerm on the sandbox's `wezterm.lua` (`TTHEME_WEZTERM_APP` names a WezTerm.app outside /Applications); `--warp` opens a Warp tab through `~/.warp/launch_configurations/ttheme-sandbox.yaml` (`warp://launch/<name>` matches the YAML's `name`, not its file name) and `--terminal-app` a Terminal.app window through a `.command` file — both run in the user's own app, since neither can be pointed at another home (`--terminal-app` wires Terminal.app into the user's own settings, which `tests/terminal-prefs.zsh` saves first and puts back when the run ends), and both are opened from `env -i`, since an app `open` starts keeps the caller's environment in every tab until it quits; `--konsole` (Linux) starts a separate Konsole on a D-Bus session of its own (`dbus-run-session`), and with `--behind` on a private Xvfb display (`TTHEME_KONSOLE_SCREEN`, `:77`), so neither the user's Konsole nor its default profile is touched; `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME` and `ZDOTDIR` scrubbed, and D-Bus cut off). `--pictured` puts a test picture on the last palette named before the terminal starts (compat's Terminal.app picture cases need one in a profile Terminal loads at launch). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run compat [--update] [ghostty iterm2 wezterm kitty alacritty warp terminal-app konsole…]` — the terminal compatibility suite: runs `tests/compat/cases.zsh` in each installed terminal through the sandbox (`--behind`), answers its screenshot requests (the window is found by pid and a per-run title, the pixel read by `tests/compat/sample.js`; Konsole's on its Xvfb display through `xdotool` and ImageMagick's `import`, read by `tests/compat/sample-png.ts`) and compares the results with `tests/compat/expect.tsv`; an expected pass that fails is a regression. Not part of ci — it opens GUI windows. Add a case there before claiming a terminal supports a feature. A `drawn` control (a truecolor fill the screenshot must show) runs before the screenshot cases, and in a window that does not redraw while covered the control and every screenshot case skip rather than fail, since that measures where the window sits, not the terminal, a DECRQM case skips in a terminal that answers no DECRQM at all (Konsole, Terminal.app), and `--update` never writes a skip over a pass or a fail. iTerm2 opens with `--trust`, on `ttheme · default` as a user's new tab does. Its capability cases (`painted`, `fg-painted`, `ansi-painted`, the `osc-*` round trips, `osc-reset`, `cell-size`, `cell-points`, `kitty-graphics`, `logo-over`, which no terminal passes — kitty draws its window logo under every kitty graphics placement, measured with its window in front, since kitty draws nothing while covered —, `sync-query`, `keyboard-query`, `keyboard-stack`, `focus-report`, `focus-event`, `focus-answer`, `front-tty`, `appearance-report`, the `scheme-*` cases, which only Konsole passes — a scheme's wallpaper drawn, held while a tab shows it, read again once none does —, the `profile-picture` and `picture-*` cases, which only Terminal.app passes — a profile's picture drawn over a background an OSC set, held per path, read again once its file is renamed, gone with its file — and `prompt-trap`, which runs last: the cases leave the shell at its prompt, signal it and hang it up) are what the parity model's `BEHAVIOR` may claim — `focus-event` moves focus away and back, which the harness does only on Konsole's Xvfb display and skips wherever it would take focus from the user — and its journey cases (`follow-default`, `follow-belief`, `keep-painted`, `on-follow`, `on-belief`, `reset-worn`) must end as the parity model's `default-here`, `default-keeps`, `on` and `program-reset` do — `tests/parity/parity.test.ts` holds both wherever compat measured a pass or a fail
- `mise run compat konsole [--update]` — the same suite in Konsole from macOS, where `compat` finds none and no other terminal is named: builds `tests/compat/konsole.Dockerfile` (Ubuntu 24.04, Konsole 23.08, Xvfb with `xcompmgr`, which Konsole 23.08 needs to draw a color scheme's wallpaper, `xdotool`, ImageMagick, node, bun) and runs `tests/compat.zsh` in it on this checkout, where every other terminal counts as not installed; needs Docker running
- `mise run parity [--update] [--only <terminal,…>] [--journey <id,…>] [--show <journey.label>] [-v] [--slots N]` — coverage held to one spec in every terminal (`tests/parity/`, part of ci): every journey in `journeys.ts` (a new tab, `use`, the menu, `default`, `off`, `on`, focus, a busy tab brought to the front, a command ending in a tab behind, preview's hover, keep, Default, tuning and settings panels, a picture dropped or tuned in another tab, pins and a pin set in another tab, an ssh host's pin, browse, a palette added elsewhere, an unwired terminal, a program resetting a painted tab's colors, a shell in an editor's terminal, a default or tuned picture reaching Ghostty, a mode set in preview, and `auto` following the appearance a Ghostty tab hears) is walked in every terminal against a model of it: real zsh tabs on Bun PTYs running the installed layer and the real CLI, an xterm-headless screen, and a synchronous protocol parser per tab (`model.ts`) that answers queries and applies each terminal's colors, resets, profiles, schemes, user vars, reloads and pictures from what it would read (`looks.ts` parses each terminal's own config files, never the emitters) — then each look's facts (the front tab's colors as a palette name, the picture the user sees and its opacity, what the shell believes it wears, and optionally the screen text) are held to the look's spec in every terminal, Ghostty included: the palette `journeys.ts` says the front tab shows (`want`, with `picture`, `opacity` and `repaints` where the look names them), an `issue` of `-` (the shell's belief disagreeing with what the tab shows, or an echoed escape, is one), and for a screen the one Ghostty drew, approved with `--update`. `facts.tsv` holds the spec in its `spec` column and every terminal's cell as `=` or its own value, and every cell that misses the spec needs a row in `gaps.tsv` (terminal, fact glob with `{a,b}` alternatives, `cannot` / `layer` / `deferred`, reason) — or, where the model says the terminal lacks a capability (`CAPABILITIES` in `terms.ts`: `pictures`, `wired`), its one `@capability` row, which explains every fact that needs it (a look's picture and opacity need `pictures`, and so does its screen where the look says so — `text: 'pictures'` for the tuning panel's picture rows; the colors, wears, picture and screen of a look marked `unpainted` need `wired`). A changed fact, the spec's included, fails until `--update` records it, an unexplained cell fails until it is fixed or given a reason, a gap row that covers a fact it does not explain fails until it is narrowed, and one that explains nothing fails once every fact it covers was walked; a journey whose facts moved, or missed the spec with no reason, is walked again one at a time up to twice before it counts, so a loaded machine does not fail it or get recorded by `--update`. Each terminal's fixture home is built once per slot (three from eight cores, one below) by the real `init --yes`, `add`, `default` and `installBackdrop`, snapshotted and restored before every journey, and `ci` starts the walk only once its other tasks are done (`wait_for`), since walked beside them it moved more journeys — 3–18 a run on CI's four cores, and on a ten-core Mac one to three against none to two after them (measured), each walked again; shims (`ps`, `pkill`, `defaults`, `dbus-send`) keep every process off the user's real terminals and fake iTerm2's preferences and Konsole's D-Bus, and a Warp session database drives its follower. While it walks, a terminal shows one progress line (the phase, the count, the journey that finished last, and what is still running once three are left) and a pipe gets a line per phase and every 10 s; the report is a table fitted to the window (short names when it is narrow) marking each journey ✓ (meets the spec), ○ (meets it but for a capability the terminal lacks), · (explained in `gaps.tsv`), ! or ✗, a `meets` row counting ✓ and ○, the facts each missing capability and each gap kind explains, how many journeys meet the spec in every terminal, and the changed facts, unexplained cells, loose gaps and stale gaps each in their own list with what to do about them. The report ends by naming, per terminal, the compat cases the model leans on (`MEASURED` and the journey `BRIDGES` in `facts.ts`) that `tests/compat/expect.tsv` leaves undecided (`?` or `skip`) — the model's standing assumptions — and every terminal compat has no column for
- `mise run bench [--against <ref>] [runs]` — shell latency through a pty (`tests/latency.zsh`, zsh's own `zpty`, answering the layer's terminal queries): zsh-bench's four metrics (first prompt, first command, command, input) for a bare shell and for ttheme off, seq and Terminal.app, interleaved, printed as each one's median difference from the bare shell and its share of zsh-bench's thresholds (50/150/10/20 ms). `--against <ref>` adds the same three shells on `<ref>`'s `shell/` (with this build's `palettes.zsh`) and prints the working tree minus `<ref>`, paired run by run, as a median with its p25–p75 — seq is the control when a change leaves it alone, so a range straddling 0 there is the noise floor; a layer that loses the keys typed ahead shows "typed keys lost" for first command. The harness never idles between shells: a second of waiting lets the CPU clock down and the next shell starts about 1.5× slower (measured), so a lost command is detected with a follow-up command, not a timeout. Not part of ci — wall time on a shared runner is noise; `shell:check` runs the same harness as `latency.zsh check`, which asserts no times, only orders: a command typed before the first prompt runs and stderr still reaches the terminal (on a first tab and on a second one, which remembers the terminal's colors), a second tab asks the terminal nothing before its first prompt, keys typed into preview while it draws are never echoed into it, while preview sits idle its search hint redraws its search row only, and a preview hover in iTerm2 paints no ANSI color (each OSC color is a profile change there), and none of it breaks under a `.zshrc` that sets `no_clobber`, `ksh_arrays`, `sh_word_split`, `no_unset` and the like before it sources the layer. The harness sets `err_return`, so a `(( x++ ))` that starts at 0 returns from the function — count with `(( ++x ))`. A session ends through `stop`, which hangs the shell up while the pty's master is still open and answers it until it is gone, never through a bare `zpty -d`: closing the master while the shell sat in `zle-line-init`, where `__tt_ask` opens /dev/tty, left the shell in that open and zpty's child in its exit for good, each holding a pty (411 of macOS's 511 had piled up, about five from every `forks`). Never measure with `time zsh -lic exit`
- `mise run site:dev` / `mise run site:build` — the showcase site (`site/`, Elysia 2 on Bun, deployed to Vercel): `site:dev` serves it on :3000 and reloads the page on every change, `site:build` builds what Vercel runs (`site/build.ts`: the assets into `site/public/assets`, then the Build Output API directory Vercel deploys as it stands, `site/.vercel/output`: the assets and every page a deployment fixes — the marketplaces read from GitHub once, at build — as static files, and the server, Elysia bundled in, as its one Bun function) and typechecks the server and browser code and runs `xss-scan` over both; not part of ci, but its typecheck is: `mise run site:check` (`site/check.ts`) runs the same two `tsc` programs without building, the two files the build writes (`assets.json`, `marketplaces.json`) typed from stand-ins in a temp dir through a `paths` override, so it needs no network and writes nothing into `site/` — a lockfile that installs two copies of postcss failed `site:build` on a Dependabot bump that ci passed; the two share `site/public` and `site/assets.json`, so stop the dev server before a build
- `mise run pages` — gather what GitHub Pages serves into `pages/`: `dist/manifest.json`, which installs from before the official palettes shipped with ttheme still fetch every day as their catalog, the README's pictures (`site/readme.ts`), and `marketplaces.json`, the marketplace index (below); `pages.yml` runs it on every push to main and every 30 minutes
- `mise run release <x.y.z | patch | minor | major>` — the only way to release: it refuses a working tree that differs from HEAD (`tests/checked.zsh clean`) and a version npm ever had (`npm view … time` keeps the unpublished ones, and npm never takes a version twice), runs `mise run ci` unless that already passed on HEAD's tree (`tests/checked.zsh fresh`), then `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`: the ci workflow, called whole but for the gathering `ci` job, which the release's `needs` does without (`workflow_call`; the workflow's own run for that push skips the `Bump version to` commit, which the release run checks), beside a read-only `pack` job that runs `bin:check` and packs the npm tarball, the archives and the notes, and a `publish` job in the `npm` environment (deployable from `v*.*.*` tags only), the one job with `id-token: write`, publishes that tarball on npm through trusted publishing (`npm publish`, OIDC — no token exists, the trusted publisher accepts only this workflow in that environment, and only an admin may create a `v*` tag under the `release tags` ruleset, so pushing the tag is the approval) and cuts the GitHub release with `gh release create` (releases are immutable, so it uploads to a draft and publishes after; a deleted release's tag can never be reused) with the per-terminal archives and the commit subjects since the last tag as notes; started by hand (`workflow_dispatch`), the workflow runs all of it but `publish`, a dry run of a release. The task then watches the run and waits until npm serves the version (`npm view … --prefer-online`, up to five minutes), so the next `npx …@<version>` finds it. Actions are pinned to full SHAs (the repository requires it) and Dependabot moves the pins
- `bun install` for dependencies

## Conventions

The terminal wiring, the picture model and the shell layer (`.claude/rules/terminals.md`, and what only one terminal does in its own file beside it — `ghostty.md`, `iterm2.md`, `warp.md`, `terminal-app.md`, `konsole.md`, `kitty.md`, `wezterm.md`, `alacritty.md`, `windows-terminal.md`, each loaded with that terminal's adapter, wiring, emitter and tests, and Read by hand from the shared harness — parity, compat, the sandbox —, which loads `terminals.md` alone), the colors and marks every screen draws (`.claude/rules/tui.md`), `find` (`.claude/rules/find.md`) and `site/` (`.claude/rules/site.md`) have their own rules, which load only when a file they cover is opened with the Read tool — `cat` or `sed` in Bash does not load them, so open one with Read before reasoning about that area.

- Source is layered by folder, each layer importing only those before it: `src/core` (the pure model — palettes and their text, colors, the gate, the mirror, share codes, slots, the booru sites, the image codecs — doing no I/O), `src/store` (what ttheme keeps on disk and fetches into it: `installed.json`, the marketplaces, tones, pins, settings, caches), `src/pictures` (decoding, drawing and fetching pictures), `src/terminals` (each terminal's wiring, emitter and live paint, `TRAITS`, the OSC helpers), `src/tui` (the runtime and every screen) and `src/cli` (the verbs and what orchestrates them: `sync`, `init`, `refresh`, …), with `src/bin.ts` above them all and two leaves outside them: `src/root.ts` and `src/embed.ts`, the Bun macro through which core's JPEG decoder inlines its WebAssembly at bundle time. `.oxlintrc.json`'s overrides hold every layer to it and core to `node:crypto`, `node:path` and `node:zlib` alone, with `process`, `fetch` and `Bun` kept out of it but for `booru.ts`, which reads `TTHEME_FIND_HOSTS` and `TTHEME_FIND_CUTOUTS` into `SITES` (Biome's `useNodejsImportProtocol` and `noCommonJs` leave no other way to name a module), while the tests reach across layers freely; the site renders from core, store and pictures alone (`site/build.ts`, which runs the showcase, aside). A module that mixes layers is split: its pure part goes down, and whatever reads files, fetches or draws stays up.
- First-party code carries **no comments** — a deliberate choice; do not add any.
- Every screen and message follows the text rules in CONTRIBUTING.md's "Writing the text": sentence case, with values, names, commands and keys as typed, key hints and `ttheme:` errors lowercase.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/` is the official marketplace and the single source of truth for it, laid out as any marketplace is — `themes/ttheme-marketplace.toml` and `themes/palettes/<catalog>/<palette>.toml`, read by `loadThemes` (`src/cli/build.ts`), which refuses a palette outside a catalog folder, a folder with no `[[catalog]]` table, a catalog without a lead, and tables out of the order `meta.order` gives their palettes; `dist/` is generated, never committed. Everyone else's palettes live in marketplaces (`src/store/sources.ts`, `src/cli/marketplaces.ts`): a GitHub repository or a local folder holding `palettes/*.toml` and `palettes/<catalog>/*.toml` beside a hand-written `ttheme-marketplace.toml` whose fields follow Claude Code's `marketplace.json`, in snake_case (`MARKETPLACE_KEYS`, `readMarketplaceInfo`, `marketplaceToml`): `name`, an `[owner]` table (`name` the GitHub handle, which names a local marketplace, `email`, `url`), `description` (browse's detail panel, the site), `[[catalog]]` tables (`readCatalogs`, `CATALOG_KEYS`: `name` the folder, `native` the title shown dim beside it, `lead` the palette whose colors stand for it — their order is the catalogs' order, a folder no table names follows in name order, and a catalog without a lead is led by its first palette), `[renames]` (old slug → new slug, or `false` once gone), `force_remove_deleted_palettes` and a free `[metadata]`, with an editor-only `"$schema"` (`MARKETPLACE_SCHEMA_URL`; palette files carry `PALETTE_SCHEMA_URL`, which `paletteToml` writes and every official palette file starts with). The JSON Schemas live in `schemas/` and are served by SchemaStore, which matches `ttheme-marketplace.toml` by name; `schemas.test.ts` ties their keys and enums to `MARKETPLACE_KEYS`, `OWNER_KEYS`, `CATALOG_KEYS`, `PALETTE_KEYS`, `SITES`, `POSITIONS` and `RULES`, and a change to them goes to SchemaStore as a PR (`src/schemas/json/ttheme-*.json` there, with TOML tests under `src/test/` and `src/negative_test/`, checked by `node ./cli.js check` and the advisory `coverage`; kecan0406 owns those files through SchemaStore's CODEOWNERS, so their own "LGTM" comment merges it). Enums there keep a string fallback (`anyOf` with `type: string`) wherever ttheme adds values over time — find sites, positions, gate rules — so an older copy never flags a newer file. An unknown key is ignored on read and named by `ttheme marketplace check [dir]` (`checkMarketplace`), which also reads every palette as an install would, checks the renames (`renameProblems`) and the `[[catalog]]` tables (a table with no folder, a lead outside its folder) and prints the gate. `followMarketplaces` (`src/cli/refresh.ts`, run by `update` and `applyRefreshed`) applies every marketplace's renames and removals to what is installed (`plan`, `src/cli/renames.ts`): the installed list and startup palette, the pins (`movePins`), `tone.json` (`moveTone`) and the pictures (`moveRacks`). Nothing is built or committed for it — a generated index tied every marketplace to the ttheme that built it: a repository is fetched as its codeload archive (`archiveUrl` in `src/store/sources.ts`, `fetchArchive` in `src/cli/refresh.ts`, `untar` in `src/core/tarball.ts`, with the ETag so an unchanged one answers 304) and a folder is read in place, both through one reader (`readMarketplaceFiles` in `src/core/own.ts`, over `marketplaceLayout`'s paths), so every gate value, signature color and backdrop is derived by the reader, never stored. `installed.json`'s `marketplaces` lists the sources (`official`, `owner/repo`, an absolute path; absent means `official` alone), and a marketplace is `<owner>@<name>` (`marketplaceId`): the repository's owner and its `ttheme-marketplace.toml`'s `name` (a local one's file gives both), so its palettes are `<owner>@<name>/<slug>` (`nameProblem`, `marketplaceOf`, `slugOf`, `src/core/theme.ts`). Every tier is marketplace → catalog → palette, the official one's included: a folder under a marketplace's `palettes/` is a catalog (`marketplaceLayout`, the `Shelf` `readOwnText` takes, the entry's `catalog`, never part of the name — a slug is used once in a marketplace, `marketplaceFileProblem`; `shelfOf` names a palette's marketplace and catalog wherever one line says where it sits), so `preview` (`__tt_pv_rows`, from `TTHEME_CATALOG` and `TTHEME_MARKETPLACE` in `palettes.zsh`; its `cat` rows only under a marketplace), init's picker (`PaletteList`'s `catalogs` layout, whose `top` rows are the official catalogs and the marketplaces, `topOf`, with `rule` and `catalog` rows) and the bare `ttheme` menu show the official catalogs first and the marketplaces after a `── Marketplaces` line, while `browse` lists marketplaces alone (`PaletteList`'s `marketplaces` layout, `PLACES`: the official catalogs under one `official` row, as any marketplace's catalogs, and no Select all row) — each marketplace as marketplace → catalog → palette with every row naming only its own part (`shownName`; - The `<palette>.conf` a picture's terminal reads has one grammar, and `src/pictures/conf.ts` owns it: the keys it names (`CONF_KEYS`), the include it follows (`CONF_INCLUDE`, `CONF_OPTIONAL`) and how deep (`CONF_DEPTH`) — which `readConf` reads, `confText` writes, and the kitty watcher and the wezterm module read through readers generated from the same constants (`confReaderPython`, `confReaderLua`), so the three readers cannot disagree on what a conf says; `src/pictures/conf.test.ts` holds the format and the shell layer's copy of it, and `src/terminals/conf-readers.test.ts` holds the Python and the Lua to the TypeScript one under their interpreters where they are installed. The shell layer reads the same keys and its own metadata lines (`# picture`, `# credit`, `# source`, `# profile`), which no other reader takes. A palette's file stem is one rule too (`STEM_RULES` in `src/core/theme.ts`, `stem`), rendered into Python, Lua and zsh from it (`src/terminals/emit/stem.ts`), and `src/terminals/stem.test.ts` fails on a mangling anywhere in `shell/` that is not the canonical form — the way `style.test.ts` fails on an SGR written outside `style.ts`.
- The official palettes ship inside ttheme: `init` writes the bundled `dist/manifest.json` (`loadManifest`) to `~/.config/ttheme/official.json` (`writeOfficial`), and nothing else ever writes it — `official` is a marketplace source whose `fetchMarketplace` reads that file, `autoUpdates` is never on for it, and a palette change reaches users only as a release (which is why every palette change is a patch release). `parseManifest` checks the document and its entries but no longer judges a schema, since every reader reads the copy its own `init` wrote. The manifest still carries `schema` (`SCHEMA`, `emptyManifest`) and Pages still publishes it (`.github/workflows/pages.yml`) for installs from before this change, which fetch it daily and learn of a newer release from its `version` — in the schema 1 shape they read (`mise run pages` writes it through `src/cli/pages.ts` and `schemaOne`, which gives each entry its catalog as `group`, the field those installs require) — keep all of it until those installs can go, and keep what `emit/manifest.test.ts` pins (the required fields of that shape, tied to `Manifest` and `SchemaOneEntry`, and the gate's rule order, since a stored `gate[i]` is read against the reader's own `GATE_RULES` — a new rule goes on the end). A share code is one format, `tt4:`, and a change to its layout goes under another prefix; an older prefix is refused, never read. A marketplace carries no format number, as Claude Code's marketplaces carry none: its reader ignores a key it does not know and drops a value it does not know, so a breaking change to a marketplace's files is never made in place — it goes under another file name. A palette file another ttheme wrote — a fetched marketplace's (`readArchive`) or a share code's (`adopt`) — is read with `Place.foreign`, which drops a `meta.booru_sites` site, a `[[picture]]` site or a `position` the reader does not know instead of refusing the palette, while the official marketplace and the user's own local marketplaces still refuse them as typos. A cache in a shape this ttheme does not read is skipped, so `init`'s upgrade never depends on one: `currentPalettes` lays the bundled official marketplace (`readMarketplaces`' `official`) over the marketplace caches that still parse, and what is installed survives through `kept.json`, local marketplaces and the bundle (`init.test.ts` holds it).
- `ttheme update [marketplace…]` (`runUpdate`, `src/cli/installs.ts`) updates ttheme first: `newerRelease` (`src/cli/release.ts`) asks npm's registry for the `latest` dist-tag, and when it is newer and this is the installed CLI (`runsInstalled`: `~/.config/ttheme/ttheme.js`), `upgradeTo` runs `npx --yes @kecan0406/ttheme@<x.y.z> init --yes` (`npm_config_prefer_online`, an exact version, so a stale npx cache cannot serve the old one) — `init`'s update path, which keeps everything — checks the installed copy's `--version`, then hands the rest of the run to the new CLI with `TTHEME_UPDATED` set, so the old process never syncs over what the new one wrote. Run from npx or a checkout it only says how to update. Then it refreshes the marketplaces (all but `official`, or the ones named). A palette installed from a marketplace is pinned: `untuned` (`src/store/available.ts`) lays the `kept.json` copy over a marketplace entry of the same name (an official one follows `official.json`, a local marketplace's is read live), so a refreshed marketplace never changes what a tab wears; `updatesOf` lists the installed ones whose colors or pictures differ, `update` and `autoRefresh` name them (`updatesLine`), browse marks them `⇡` (`MARKS.update`, `PaletteList`'s `note`), `ctrl+r` on a palette or a catalog stages them (`renew`, `BrowseResult.renew`), and `applyBrowse` takes them through `takeUpdates` (the fresh entries into `kept.json`, `sync`, newly listed pictures). Once a day any verb but the hidden ones, `update`, `init` and `uninstall` starts the hidden `latest` verb detached (`startReleaseCheck`, stamped in `$XDG_STATE_HOME/ttheme/release.json`, a failure retried after an hour) and says once a day on stderr when a newer ttheme is known (`tellRelease`), and the shell layer does the same without a verb (`__tt_release`, last in `__tt_prompt`: one `zstat` of `release.json` per prompt and no process; when the stamp is a day old it takes a `zsystem flock` on `release.lock`, writes `checked` itself and starts `ttheme latest` detached — the one process a hot path may start, once a day — and when the stamp names a newer release it prints `TTHEME_OUTDATED`, the CLI's own wording emitted into `palettes.zsh` from `src/tui/notice.ts`, on stderr once a day, recording `told` in the file the CLI reads, so a verb and a prompt never tell twice; never in a shell with no tty on stderr or an inactive layer). The bare `ttheme` checks on a period of its own: opening the hub runs `__tt_release hub`, the same claim under the same lock with an hour in place of a day and nothing told on stderr (a failure waits an hour too: `failed`), and draws what the stamp says at the right end of the plain Preview and Browse key bars — dim, `ttheme 1.2.30` alone while updates are off or nothing is known, then two spaces and `checking…` while a claim is under way, `✓ up to date`, `⇡ 1.2.31 available` in the warn color for a newer release, `✗ check failed` (the marks are `MARKS.ok`, `MARKS.update` and `MARKS.miss`) — dropped first when the bar is too narrow (`STANDING_LINES`/`standingLine` in `src/tui/notice.ts` are the wording, emitted into `palettes.zsh` as `TTHEME_STANDING`; `releaseLine`/`standingOf` in `src/cli/release.ts` and `__tt_pv_standing` in `shell/preview.zsh` read it). The stamp carries two fields for it: `trying`, the milliseconds of a claim, which `ttheme latest` clears when it ends and which reads as checking for 30 s whatever became of the process, and `failed`, when the last check failed, cleared by the next one that succeeds; preview polls the stamp every 0.2 s and Browse every beat while a check is under way, so the line flips the moment `latest` writes. `TTHEME_AUTO_UPDATE=off` (`config.zsh`) or a `CI` environment stops all of that and `autoRefresh` (`autoWanted`), never `ttheme update`, and the tui, parity, bin:check, latency and sandbox harnesses set it (`latency.zsh check` turns it on for one shell per terminal, whose stub `node` records the check). What `autoRefresh` adds beside another verb is advice, not that verb's output: it goes through `advise` (`src/tui/notice.ts`) to stderr, and only when stderr is a terminal — the shell layer captures stdout (`__tt_keep` runs `$(__tt_cli default …)`) while stderr stays the person's terminal; `ttheme update` and browse's closing report are the verbs' own output and stay on stdout. A refresh is one `Outcome` (`attempt`: what was refreshed, or the failure it ended in), `failureLine` is how a failure reads everywhere, and `applyRefreshed` follows the marketplaces' renames and returns its `left its marketplace` lines for the caller to print.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/images.json` owns the pictures each palette keeps and which one is up, and only the CLI writes it — every `<palette>.conf` is a view regenerated from it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the include in ttheme's `ghostty.conf` never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends), each default spelled out on a commented line and only a value that differs from it left live (`settingLine`, `__tt_config_line`; the layer's own `: ${X:=…}` fallbacks are held to `CONFIG_SETTINGS` by `wiring.test.ts`), so a default a later version changes reaches every setup that never touched it: while `TTHEME_TAB_PALETTE` is not `off`, ttheme's Ghostty file routes new tabs through `launch-tab.zsh` (unless a Ghostty config sets its own `command`, and then the layer rotates at shell start), which reads the setting when the tab opens — `ttheme config` and preview's settings panel run the hidden `sync` when that line changes, so the file follows it — and open shells keep theirs until they restart. `palettes.zsh` does not wait: every open shell re-reads it at its next prompt once its modification time moves (`__tt_fresh`, nanoseconds through `zstat -F %s.%N` — whole seconds miss two writes in one second), and at once where it sits idle at its prompt when a `ttheme` verb moved it, since `ttheme()` then signals every other shell (`__tt_wake`, the terminals rule's wake), so a palette added or a default changed in one tab reaches every other tab, in any terminal (the pins file is watched the same way, so a pin set or dropped in one tab repaints the tabs already under it at once where they sit idle, else at their next prompt or focus) — which is why `sync` rewrites it (and drops its `.zwc`) only when its content changed, like every other file it writes, or after it touched Windows Terminal's `settings.json`.
- `installed.json` is read field by field through `OPTIONAL` (`src/store/installed.ts`), a table whose type makes it cover every optional key of `Installed`, and each change spreads the state it read (`{ ...state, … }`); init's `planAgain` sets only what it asks again — the terminals, the palettes, `off`, the startup palette and Windows Terminal's paths — and carries the rest, so a field added later survives a rerun without being named anywhere (`sync.test.ts` and `init.test.ts` hold both to a `Required<Installed>`).
- `src/cli/verbs.ts` is the one list of commands: the CLI's parser and help read it (`cli.ts` adds the runs), and `palettes.zsh` carries every verb but the setup ones (`TTHEME_VERBS`, `TTHEME_VERB_ARGS`, `TTHEME_VERB_ABOUT`, `TTHEME_SHELL_VERBS`) for the shell's completion and argument checks, plus the help text itself (`TTHEME_HELP`, `TTHEME_HELP_ALL`, from `helpText`), so both helps say the same without node. There is no `preview` or `browse` command: a bare `ttheme` is the one way into both (the hub, `__tt_preview hub`, which opens on Preview; with no palette installed it runs `__tt_installs browse` alone, since Preview has nothing to show), and `browse` stays in `VERB_SPECS` as a `hidden` verb only because the hub's Browse tab runs `__tt_cli browse` — a hidden verb is not in `palettes.zsh`, so typing it in the shell is an unknown command. Preview hands the tab to Browse, as to every screen it opens, in the tab's own look and takes it back assuming nothing (`__tt_pv_leave`, `__tt_pv_back`, the contract in `.claude/rules/terminals.md`): Browse is told that look as `TTHEME_HUB_LOOK` and its `live.restore` gives exactly that back when the hub closes from it (`runBrowse`; a tab switch skips `restore`, since Preview repaints, and runs only `live.stop`, which in Terminal.app still lays the palette's picture file back), while the host forgets what it believed the tab showed (`__tt_pv_lost`: `painted=?` and the adapter hook `__tt_pv_forget`, because it never saw what Browse painted), then repaints the palette and picture it showed when Browse switches back, or gives the tab its own look through its teardown when the hub closes — parity's `hub-back` and `browse-back`. Help follows ffmpeg's: a version, description and usage line, `Getting help:` (the three tiers) and `Global options:` (`-h`, `-v`), then every section (`SECTIONS`: This tab, New tabs, Palettes, Your own, Setup, Support) listing each verb as its name and args beside its `about` up to the first ` — ` (`headOf`), so that head is a short phrase that fits one line; `ttheme help` leaves out the verbs marked `more` (`check`, `info`), and `ttheme help all` lists every verb and adds each one's actions and flags indented under it, with their heads, and `Examples:`; `ttheme help <command>` (`commandHelp`) prints the whole `about`, the actions and the flags; the bare CLI with no arguments prints only the banner and a hint (`briefText`), on stderr with status 1. A palette is never a command — `ttheme use <palette>` paints a tab. `ttheme info` (`src/cli/info.ts`, Support) is what a bug report carries — `.github/ISSUE_TEMPLATE/bug.yml` asks for its output instead of a version and a terminal typed by hand, so a row added to it is added to that field's description too; the shell case in `ttheme()` hands it `TTHEME_ZSH` (`ZSH_VERSION` cannot take a prefix assignment) and answers before the empty-install check, and `runCli` points a crash (`isCrash`: `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, or an error with a `code`) to it, never a message written for the user. `palettes.zsh` also names the marketplaces the install holds (`TTHEME_MARKETPLACES`, written by `sync`: each source's id through `nameOf`, else the source itself — the names `ttheme marketplace remove` and `ttheme update` take, which the completion offers without a fork) and the `config.zsh` settings (`TTHEME_SETTINGS`, from `CONFIG_SETTINGS`), and `__tt_cli` hands every one that is set to the CLI, since `config.zsh` assigns without exporting.
- Every official palette must pass the contrast gate (src/core/contrast.ts), which checks readability (WCAG ratios: text 7:1, accents and ANSI 0 on ANSI 1–6 4.5:1, ANSI 8 and ANSI 7 on it 3:1, ANSI 0's luminance only in a dark palette — one whose background is darker than its foreground; a light palette mirrors 0, 7 and 15) and function (OKLCH: each accent's hue inside its ANSI role's band, a bright within 25° of its normal; CIELAB at text size, `apart`: no two accents in a row that read as one color, red and green, normal and bright, apart for a deuteranope; ANSI slots in `meta.signature` and their twins are exempt from the band, and a pair of exempt slots from the comparisons). A new rule goes on the end of `GATE_RULES`, and a rule that does not apply to a palette measures `NaN`, which every reader skips. Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin. A run whose tasks go side by side prefixes every line and takes the TTY off stdout too, while a chain keeps it — which is why `bin:build` depends on `build`: `mise run parity` then keeps the terminal for its progress line, and `interactive` would have made `ci` wait for everything else before starting it (measured on mise 2026.8).
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- The package root is `ROOT` (`src/root.ts`), the one file that reaches it through `import.meta.dirname` and so sits directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` resolves to the package root only at that depth; every other file under `src/`, its tests included, joins from `ROOT`, while `tests/` and `site/`, which no bundle moves, keep their own `import.meta.dirname`.
- `build` needs bun (`Bun.write`); TOML is read with `smol-toml` everywhere, so the CLI parses palette files under node too; `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json`, the only dist file the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- The bundle runs on node 22 and up (`engines`), and `bun build --target=node` lowers `using` and decorators but passes regular expressions and built-ins through as written: a regex with modifiers (`(?i:…)`) or a repeated group name is a SyntaxError that stops the whole bundle loading on node 22, and `Promise.try`, `RegExp.escape`, `Error.isError`, `Iterator.concat`, `Map#getOrInsert`, `Uint8Array.fromBase64` and `Math.sumPrecise` are missing there — while tsc (lib `esnext`, plus `bun-types`, which declares several of them) and `bun test` (JSC) accept them all, so only `bin:check` catches one, and only on the paths it walks. Iterator helpers and the Set methods are there, but iterator helpers measured 2.5–9× slower than the array methods on V8 12.4, V8 13.6 and JSC alike (`for…of` with `push` fastest of all), so they earn a place by laziness or by feeding `new Set`, `new Map` or `Object.fromEntries` directly, never by speed; and Biome breaks a chain of three or more calls one call to a line, so a one-line spread and method stays one.
- Preview's key loop (`__tt_pv_getch`) leaves when five reads in a row come back at once, which only a hung-up tty does (a timed-out `read -k` takes its whole timeout, `EPOCHREALTIME` from `zsh/datetime` tells them apart): a shell that is not the session leader — under a task runner such as `mise run` — never gets the SIGHUP, and the loop spun at 20% CPU on the dead tty, stty forks and all. Checking `[[ -t 0 ]]` or `stty size` does not catch it; both still succeed.
- JPEG pictures are decoded by mozjpeg compiled to WebAssembly (`src/core/jpeg.ts`, `@jsquash/jpeg`), which the bundle carries inside itself: `src/embed.ts` is a Bun macro that reads the `.wasm` at transpile time and inlines it deflated and base64-encoded, so `src/` runs under bun (the tests, `bun src/bin.ts`) and the bundle under node, but `src/` does not run under plain node. The decoder does not read arithmetic-coded JPEGs (it throws `not a JPEG image this decoder can read`), and it turns a picture by its EXIF orientation — `decode(bytes, true)` is jsquash's `preserveOrientation`, which keeps the orientation the picture is shown in, not the raster's — as the PNG reader does with an `eXIf` chunk and Vision does when `src/pictures/cutout.ts` opens the picture, so a cut-out's mask fits the picture as decoded (`jpegSize` and `pngHead` give that size too).
- `bin/` is generated by `mise run bin:build`, never committed. The bundle ships a linked source map without `sourcesContent` (`bin/ttheme.js.map`, copied beside the installed CLI): `TTHEME_DEBUG=1` makes `bin.ts` relaunch node with `--enable-source-maps`, and the CLI prints the error's stack in `src/` lines instead of its message alone.
