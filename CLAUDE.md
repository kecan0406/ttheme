# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check + node-bundle check (exactly what CI runs)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build): `shell/check.zsh`, `latency.zsh check` and the fork ratchet
- `mise run forks [--update]` — the fork ratchet (`tests/latency.zsh forks`, part of `shell:check`): starts a warm shell per terminal and mode with `xtrace` on and `PS4` printing `$sysparams[pid]`, counts the distinct PIDs each journey leaves in the trace (a new tab in `off` and `seq`, an empty command, a focus-in, a `cd`) beyond a bare zsh, and compares them with `tests/forks.tsv`: more fails as a regression, fewer fails until `--update` locks the lower count in, so a hot path only ever loses processes. The counts are a proxy (a subshell whose only work is forking children hides itself) that agreed with an exact `fork`/`execve` interposer everywhere but `base64` pipes, where it still counted more than none
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust] | --wezterm | --kitty | --alacritty | --warp | --terminal-app] [--zshenv FILE] [--empty | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing `browse`). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--wezterm` starts a separate WezTerm on the sandbox's `wezterm.lua` (`TTHEME_WEZTERM_APP` names a WezTerm.app outside /Applications); `--warp` opens a Warp tab through `~/.warp/launch_configurations/ttheme-sandbox.yaml` (`warp://launch/<name>` matches the YAML's `name`, not its file name) and `--terminal-app` a Terminal.app window through a `.command` file — both run in the user's own app, since neither can be pointed at another home; `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `ZDOTDIR` scrubbed). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run compat [--update] [ghostty iterm2 wezterm kitty alacritty warp terminal-app…]` — the terminal compatibility suite: runs `tests/compat/cases.zsh` in each installed terminal through the sandbox (`--behind`), answers its screenshot requests (the window is found by pid and a per-run title, the pixel read by `tests/compat/sample.js`) and compares the results with `tests/compat/expect.tsv`; an expected pass that fails is a regression. Not part of ci — it opens GUI windows. Add a case there before claiming a terminal supports a feature
- `mise run bench [--against <ref>] [runs]` — shell latency through a pty (`tests/latency.zsh`, zsh's own `zpty`, answering the layer's terminal queries): zsh-bench's four metrics (first prompt, first command, command, input) for a bare shell and for ttheme off, seq and Terminal.app, interleaved, printed as each one's median difference from the bare shell and its share of zsh-bench's thresholds (50/150/10/20 ms). `--against <ref>` adds the same three shells on `<ref>`'s `shell/` (with this build's `palettes.zsh`) and prints the working tree minus `<ref>`, paired run by run, as a median with its p25–p75 — seq is the control when a change leaves it alone, so a range straddling 0 there is the noise floor; a layer that loses the keys typed ahead shows "typed keys lost" for first command. The harness never idles between shells: a second of waiting lets the CPU clock down and the next shell starts about 1.5× slower (measured), so a lost command is detected with a follow-up command, not a timeout. Not part of ci — wall time on a shared runner is noise; `shell:check` runs the same harness as `latency.zsh check`, which asserts no times, only orders: a command typed before the first prompt runs and stderr still reaches the terminal (on a first tab and on a second one, which remembers the terminal's colors), a second tab asks the terminal nothing before its first prompt, keys typed into preview while it draws are never echoed into it, and while preview sits idle its search hint redraws its first row only. The harness sets `err_return`, so a `(( x++ ))` that starts at 0 returns from the function — count with `(( ++x ))`. Never measure with `time zsh -lic exit`
- `mise run site:dev` / `mise run site:build` — the showcase site; not part of ci, and `next build` is where site/ gets typechecked (root `tsc` only covers `src/`)
- `mise run release <x.y.z>` — the only way to release: runs ci, `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`, which runs ci again, publishes to npm through trusted publishing (OIDC, with provenance — no token exists, so nothing is ever published from a machine) and cuts the GitHub release with the per-terminal archives and the commit subjects since the last tag as notes
- `bun install` for dependencies

## Conventions

The terminal wiring, the picture model and the shell layer (`.claude/rules/terminals.md`), `find` (`.claude/rules/find.md`) and `site/` (`.claude/rules/site.md`) have their own rules, which load only when a file they cover is opened with the Read tool — `cat` or `sed` in Bash does not load them, so open one with Read before reasoning about that area.

- First-party code carries **no comments** — a deliberate choice; do not add any.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/*.toml` is the single source of truth for the official catalog; `dist/` is generated, never committed. Everyone else's palettes live in markets (`src/sources.ts`, `src/markets.ts`): a GitHub repository whose `ttheme-market.json` (`MarketIndex`, `parseIndex` — the manifest shape plus `owner` and `name`, entries named bare) its reusable action `market/action.yml` rebuilds from `palettes/*.toml` on every push (`ttheme market build`), or a local folder read in place. `installed.json`'s `markets` lists the sources (`official`, `owner/repo`, an absolute path; absent means `official` alone), and a market is `<owner>@<name>` (`marketId`): the repository's owner and its index `name` (a local one's index gives both), so its palettes are `<owner>@<name>/<slug>` (`nameProblem`, `marketOf`, `slugOf`, `src/theme.ts`). The market is their group (`readOwnText`, `marketEntries` set it; `meta.group` is not read), so every list — `browse` (`PalettePrompt`'s `rule` row), `preview` (`__tt_pv_rows`) and the bare `ttheme` menu — shows the series first and the markets after a `── markets` line, `alphabetical` included; no `order` or `role` (a `Place` with `open` reads a file as a market palette), and `meta.base` only names the official palette whose ANSI colors it took. `readCatalog` lays the cached official catalog (`catalog.json`) and every remote market's cached index (`markets/<owner>--<repo>.json`, refreshed by `update`) together; there is no review — nothing but the official catalog's CI enforces the contrast gate. Anywhere a name becomes a file it goes through `stem` (`@` and `/` → `--`, which a slug never contains) — `owned`, the background files and confs, the iTerm2 Guid, and the zsh and watcher lookups (`${${name/@/--}/\//--}`, `palette.replace('@', '--', 1).replace('/', '--', 1)`, the same two `gsub`s in Lua). The `v1` tag, which market repositories' workflows use, is moved to each release by `release.yml`.
- A user's own palettes live in a local market — `~/.config/ttheme/market/<name>` unless `ttheme market init` was given a folder (`ensureLocal`: one is used, several need `--in <name>`, none asks for a name and makes it) — as `palettes/<slug>.toml`, read with the same parser (`readLocal`/`readMarketDir`, `src/own.ts`, with an open `Place`: an unknown base or series is only a label there) and laid over the catalog by `available` (`src/catalog.ts`), which also adds back, from `kept.json` (the entries the last `sync` resolved), any installed palette no market carries — so every reader of palettes goes through `available`/`readAvailable`, never the bare catalog. `new`, `edit`, `check` and `share` (`src/craft.ts`) make, change, measure (`fixGate`, `src/fix.ts`, which the palette skill's role fixer shares; the gate only advises here) and hand them on; a share code (`tt1:`, `shareCode`/`fromCode`) is decoded, written as TOML and parsed like any file, and the entry goes straight into `kept.json` (`adopt`). Anything a palette's `[[picture]]` lists is fetched only when the palette is newly installed or the list gained it (`since`), so a picture the user dropped stays dropped.
- ttheme writes colors only — no font, font size, codepoint map or shader in any terminal, since a theme tool that sets those overrides the user's own (Ghostty loads a `config-file` after the whole file, so its keys win wherever the include sits). A Ghostty theme file also carries the dock-icon colors, which `theme =` loads before the user's config, so the user's own keys still win.
- A user's config is edited only through `editUserFile` (`src/edits.ts`): a copy to `<file>.ttheme.bak` before the first edit (never overwritten), then a temp file renamed over the symlink's target, so a dotfiles link survives. A key the user sets outside the block stays theirs (`userSets`, `src/wiring.ts`): the Ghostty block drops `command` (and with it `shell-integration`) when the config has its own, and the kitty block drops `window_logo_scale`/`window_logo_alpha` the same way; `launch-tab.zsh` execs `$SHELL`, not `/bin/zsh`. Every file ttheme adds to a terminal's own folders, and every scheme name there (WezTerm, Windows Terminal, `.itermcolors`), is `owned(<palette>)` = `ttheme-<stem>`, which is also how `uninstall` finds them. init lists every file it will edit and the keys its block sets (`wiringPlan`), notes what the user's config overrides (`wiringNotes` — an Alacritty config's own `[colors]` win over its import), and refuses to run without a TTY unless given `--yes`. Run over an existing install (a readable `installed.json`), init is the update path — `npx …@latest init` is the only way a new version reaches `~/.config/ttheme` — so it first offers to update and keep everything (`planUpgrade`: the same terminals, palettes, default and `off`, only the layer replaced; the installed copy's `--version` names what is replaced; default yes), and `--yes` does that without asking instead of starting over; "set it up again" starts from the current terminals, the per-palette picker with the current palettes checked, and the default that was in effect.
- `uninstall` (`src/uninstall.ts`, a setup verb run through npx like init) lists and then reverses everything: each block comes out (`removeBlock`, `removeLuaBlock`; a config ttheme created is deleted), Warp's theme comes back from `warp.base`, iTerm2's default from `itermBase`, and the `ttheme-*` files, `~/.config/ttheme`, the cache and state dirs, the dynamic profile and the WT fragment go. A config equal to its backup loses the backup; one edited since keeps it. An open shell whose `~/.config/ttheme` is gone drops out at its next prompt (`__tt_gone`, from `__tt_fresh`): reload, reset, focus reporting off, hooks and the `ttheme` function removed.
- Series metadata lives once, in `themes/_groups.toml`: every `meta.group` needs a `[[group]]` table there, which owns the `native` title and names the `lead` palette whose signature colors the group. A theme file never repeats them.
- `meta.signature` names three palette slots (`cursor`, `foreground`, `background`, `selection`, `ansi0`-`ansi15`) — the colors that identify the character on a card. They must resolve to three different colors.
- `dist/manifest.json` is the data contract for everything outside the build: `init` and `site/` read it instead of re-parsing `themes/` (site tasks depend on `build`). Every dist artifact goes through an `Emitter` in `src/emit/` — terminals emit per theme, `shell`/`meta` emit shared files.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/images.json` owns the pictures each palette keeps and which one is up, and only the CLI writes it — every `<palette>.conf` is a view regenerated from it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the block's include never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends), each default spelled out on a commented line and only a value that differs from it left live (`settingLine`, `__tt_config_line`), so a default a later version changes reaches every setup that never touched it: the Ghostty block routes new tabs through `launch-tab.zsh` (unless the user's config sets its own `command`, and then the layer rotates at shell start), which reads the setting when the tab opens, and open shells keep theirs until they restart. `palettes.zsh` does not wait: every open shell re-reads it at its next prompt once its modification time moves (`__tt_fresh`, nanoseconds through `zstat -F %s.%N` — whole seconds miss two writes in one second), so a palette added or a default changed in one tab reaches every other tab, in any terminal — which is why `sync` rewrites it (and drops its `.zwc`) only when its content changed, like every other file it writes, or after it touched Windows Terminal's `settings.json`.
- `src/verbs.ts` is the one list of commands: the CLI's parser and help read it (`cli.ts` adds the runs), and `palettes.zsh` carries every verb but the setup ones (`TTHEME_VERBS`, `TTHEME_VERB_ARGS`, `TTHEME_VERB_ABOUT`, `TTHEME_SHELL_VERBS`) for the shell's completion and argument checks, plus the help text itself (`TTHEME_HELP`, `TTHEME_HELP_ALL`, from `helpText`), so both helps say the same without node. Help is tiered: `ttheme help` shows the verbs with a `start` line ("Start here") and every section (`SECTIONS`: This tab, New tabs, Palettes, Your own, Setup) as one line of names; `ttheme help all` lists each with its `about`. A palette is never a command — `ttheme use <palette>` paints a tab. `palettes.zsh` also names the `config.zsh` settings (`TTHEME_SETTINGS`, from `CONFIG_SETTINGS`), and `__tt_cli` hands every one that is set to the CLI, since `config.zsh` assigns without exporting.
- Every official palette must pass the contrast gate (src/contrast.ts), which checks readability (WCAG ratios) and function (OKLCH: each accent's hue inside its ANSI role's band, a bright within 25° of its normal, no two accents that read as one color; ANSI slots in `meta.signature` and their twins are exempt from the band). Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin and its output is line-prefixed.
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- Any source file using `import.meta.dirname` to reach the repo root must sit directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` only resolves to the package root when the depth matches.
- `build` needs bun (`Bun.write`); TOML is read with `smol-toml` everywhere, so the CLI parses palette files under node too; `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json`, the only dist file the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- `bin/` is generated by `mise run bin:build`, never committed. The bundle ships a linked source map without `sourcesContent` (`bin/ttheme.js.map`, copied beside the installed CLI): `TTHEME_DEBUG=1` makes `bin.ts` relaunch node with `--enable-source-maps`, and the CLI prints the error's stack in `src/` lines instead of its message alone.
