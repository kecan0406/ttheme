# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check + node-bundle check + TUI screens + the parity walk (exactly what CI runs)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build): `shell/check.zsh`, `latency.zsh check` and the fork ratchet
- `mise run forks [--update]` — the fork ratchet (`tests/latency.zsh forks`, part of `shell:check`): starts a warm shell per terminal and mode with `xtrace` on and `PS4` printing `$sysparams[pid]`, counts the distinct PIDs each journey leaves in the trace (a new tab in `off` and `seq`, an empty command, a focus-in, a `cd`, and a command that resets a painted tab's cursor) beyond a bare zsh, and compares them with `tests/forks.tsv`: more fails as a regression, fewer fails until `--update` locks the lower count in, so a hot path only ever loses processes. The counts are a proxy (a subshell whose only work is forking children hides itself) that agreed with an exact `fork`/`execve` interposer everywhere but `base64` pipes, where it still counted more than none
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust] | --wezterm | --kitty | --alacritty | --warp | --terminal-app | --konsole] [--pictured] [--zshenv FILE] [--empty | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing Browse). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--wezterm` starts a separate WezTerm on the sandbox's `wezterm.lua` (`TTHEME_WEZTERM_APP` names a WezTerm.app outside /Applications); `--warp` opens a Warp tab through `~/.warp/launch_configurations/ttheme-sandbox.yaml` (`warp://launch/<name>` matches the YAML's `name`, not its file name) and `--terminal-app` a Terminal.app window through a `.command` file — both run in the user's own app, since neither can be pointed at another home (`--terminal-app` wires Terminal.app into the user's own settings, which `tests/terminal-prefs.zsh` saves first and puts back when the run ends), and both are opened from `env -i`, since an app `open` starts keeps the caller's environment in every tab until it quits; `--konsole` (Linux) starts a separate Konsole on a D-Bus session of its own (`dbus-run-session`), and with `--behind` on a private Xvfb display (`TTHEME_KONSOLE_SCREEN`, `:77`), so neither the user's Konsole nor its default profile is touched; `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME` and `ZDOTDIR` scrubbed, and D-Bus cut off). `--pictured` puts a test picture on the last palette named before the terminal starts (compat's Terminal.app picture cases need one in a profile Terminal loads at launch). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run compat [--update] [ghostty iterm2 wezterm kitty alacritty warp terminal-app konsole…]` — the terminal compatibility suite: runs `tests/compat/cases.zsh` in each installed terminal through the sandbox (`--behind`), answers its screenshot requests (the window is found by pid and a per-run title, the pixel read by `tests/compat/sample.js`; Konsole's on its Xvfb display through `xdotool` and ImageMagick's `import`, read by `tests/compat/sample-png.ts`) and compares the results with `tests/compat/expect.tsv`; an expected pass that fails is a regression. Not part of ci — it opens GUI windows. Add a case there before claiming a terminal supports a feature. A `drawn` control (a truecolor fill the screenshot must show) runs before the screenshot cases, and in a window that does not redraw while covered the control and every screenshot case skip rather than fail, since that measures where the window sits, not the terminal, a DECRQM case skips in a terminal that answers no DECRQM at all (Konsole, Terminal.app), and `--update` never writes a skip over a pass or a fail. iTerm2 opens with `--trust`, on `ttheme · default` as a user's new tab does. Its capability cases (`painted`, `fg-painted`, `ansi-painted`, the `osc-*` round trips, `osc-reset`, `cell-size`, `cell-points`, `kitty-graphics`, `sync-query`, `focus-report`, `focus-event`, `focus-answer`, `front-tty`, the `scheme-*` cases, which only Konsole passes — a scheme's wallpaper drawn, held while a tab shows it, read again once none does —, the `profile-picture` and `picture-*` cases, which only Terminal.app passes — a profile's picture drawn over a background an OSC set, held per path, read again once its file is renamed, gone with its file — and `prompt-trap`, which runs last: the cases leave the shell at its prompt, signal it and hang it up) are what the parity model's `BEHAVIOR` may claim — `focus-event` moves focus away and back, which the harness does only on Konsole's Xvfb display and skips wherever it would take focus from the user — and its journey cases (`follow-default`, `follow-belief`, `keep-painted`, `on-follow`, `on-belief`, `reset-worn`) must end as the parity model's `default-here`, `default-keeps`, `on` and `program-reset` do — `tests/parity/parity.test.ts` holds both wherever compat measured a pass or a fail
- `mise run compat:konsole [--update]` — the same suite in Konsole from macOS: builds `tests/compat/konsole.Dockerfile` (Ubuntu 24.04, Konsole 23.08, Xvfb with `xcompmgr`, which Konsole 23.08 needs to draw a color scheme's wallpaper, `xdotool`, ImageMagick, node, bun) and runs `tests/compat.zsh` in it on this checkout, where every other terminal counts as not installed; needs Docker running
- `mise run parity [--update] [--only <terminal,…>] [--journey <id,…>] [--show <journey.label>] [-v] [--slots N]` — coverage held to one spec in every terminal (`tests/parity/`, part of ci): every journey in `journeys.ts` (a new tab, `use`, the menu, `default`, `off`, `on`, focus, a busy tab brought to the front, a command ending in a tab behind, preview's hover, keep, Default, tuning and settings panels, a picture dropped or tuned in another tab, pins and a pin set in another tab, an ssh host's pin, browse, a palette added elsewhere, an unwired terminal, a program resetting a painted tab's colors, a shell in an editor's terminal, and a default or tuned picture reaching Ghostty) is walked in every terminal against a model of it: real zsh tabs on Bun PTYs running the installed layer and the real CLI, an xterm-headless screen, and a synchronous protocol parser per tab (`model.ts`) that answers queries and applies each terminal's colors, resets, profiles, schemes, user vars, reloads and pictures from what it would read (`looks.ts` parses each terminal's own config files, never the emitters) — then each look's facts (the front tab's colors as a palette name, the picture the user sees and its opacity, what the shell believes it wears, and optionally the screen text) are held to the look's spec in every terminal, Ghostty included: the palette `journeys.ts` says the front tab shows (`want`, with `picture`, `opacity` and `repaints` where the look names them), an `issue` of `-` (the shell's belief disagreeing with what the tab shows, or an echoed escape, is one), and for a screen the one Ghostty drew, approved with `--update`. `facts.tsv` holds the spec in its `spec` column and every terminal's cell as `=` or its own value, and every cell that misses the spec needs a row in `gaps.tsv` (terminal, fact glob with `{a,b}` alternatives, `cannot` / `layer` / `deferred`, reason) — or, where the model says the terminal lacks a capability (`CAPABILITIES` in `terms.ts`: `pictures`, `wired`), its one `@capability` row, which explains every fact that needs it (a look's picture and opacity need `pictures`, and so does its screen where the look says so — `text: 'pictures'` for the tuning panel's picture rows; the colors, wears, picture and screen of a look marked `unpainted` need `wired`). A changed fact, the spec's included, fails until `--update` records it, an unexplained cell fails until it is fixed or given a reason, a gap row that covers a fact it does not explain fails until it is narrowed, and one that explains nothing fails once every fact it covers was walked; a journey whose facts moved, or missed the spec with no reason, is walked again one at a time up to twice before it counts, so a loaded machine does not fail it or get recorded by `--update`. Each terminal's fixture home is built once per slot (three from eight cores, one below) by the real `init --yes`, `add`, `default` and `installBackdrop`, snapshotted and restored before every journey, and `ci` starts the walk only once its other tasks are done (`wait_for`), since walked beside them on CI's four cores it moved 3–18 journeys a run; shims (`ps`, `pkill`, `defaults`, `dbus-send`) keep every process off the user's real terminals and fake iTerm2's preferences and Konsole's D-Bus, and a Warp session database drives its follower. While it walks, a terminal shows one progress line (the phase, the count, the journey that finished last, and what is still running once three are left) and a pipe gets a line per phase and every 10 s; the report is a table fitted to the window (short names when it is narrow) marking each journey ✓ (meets the spec), ○ (meets it but for a capability the terminal lacks), · (explained in `gaps.tsv`), ! or ✗, a `meets` row counting ✓ and ○, the facts each missing capability and each gap kind explains, how many journeys meet the spec in every terminal, and the changed facts, unexplained cells, loose gaps and stale gaps each in their own list with what to do about them. The report ends by naming, per terminal, the compat cases the model leans on (`MEASURED` and the journey `BRIDGES` in `facts.ts`) that `tests/compat/expect.tsv` leaves undecided (`?` or `skip`) — the model's standing assumptions — and every terminal compat has no column for
- `mise run bench [--against <ref>] [runs]` — shell latency through a pty (`tests/latency.zsh`, zsh's own `zpty`, answering the layer's terminal queries): zsh-bench's four metrics (first prompt, first command, command, input) for a bare shell and for ttheme off, seq and Terminal.app, interleaved, printed as each one's median difference from the bare shell and its share of zsh-bench's thresholds (50/150/10/20 ms). `--against <ref>` adds the same three shells on `<ref>`'s `shell/` (with this build's `palettes.zsh`) and prints the working tree minus `<ref>`, paired run by run, as a median with its p25–p75 — seq is the control when a change leaves it alone, so a range straddling 0 there is the noise floor; a layer that loses the keys typed ahead shows "typed keys lost" for first command. The harness never idles between shells: a second of waiting lets the CPU clock down and the next shell starts about 1.5× slower (measured), so a lost command is detected with a follow-up command, not a timeout. Not part of ci — wall time on a shared runner is noise; `shell:check` runs the same harness as `latency.zsh check`, which asserts no times, only orders: a command typed before the first prompt runs and stderr still reaches the terminal (on a first tab and on a second one, which remembers the terminal's colors), a second tab asks the terminal nothing before its first prompt, keys typed into preview while it draws are never echoed into it, while preview sits idle its search hint redraws its first row only, and a preview hover in iTerm2 paints no ANSI color (each OSC color is a profile change there), and none of it breaks under a `.zshrc` that sets `no_clobber`, `ksh_arrays`, `sh_word_split`, `no_unset` and the like before it sources the layer. The harness sets `err_return`, so a `(( x++ ))` that starts at 0 returns from the function — count with `(( ++x ))`. A session ends through `stop`, which hangs the shell up while the pty's master is still open and answers it until it is gone, never through a bare `zpty -d`: closing the master while the shell sat in `zle-line-init`, where `__tt_ask` opens /dev/tty, left the shell in that open and zpty's child in its exit for good, each holding a pty (411 of macOS's 511 had piled up, about five from every `forks`). Never measure with `time zsh -lic exit`
- `mise run site:dev` / `mise run site:build` — the showcase site (`site/`, Elysia 2 on Bun, deployed to Vercel): `site:dev` serves it on :3000 and reloads the page on every change, `site:build` builds what Vercel runs (`site/build.ts`: the assets into `site/public/assets`, then the Build Output API directory Vercel deploys as it stands, `site/.vercel/output`: the assets as static files and the server, Elysia bundled in, as its one Bun function) and typechecks the server and browser code and runs `xss-scan` over both; not part of ci (root `tsc` only covers `src/`), and the two share `site/public` and `site/assets.json`, so stop the dev server before a build
- `mise run pages` — gather what GitHub Pages serves into `pages/`: `dist/manifest.json`, which installs from before the official palettes shipped with ttheme still fetch every day as their catalog, and the README's pictures (`site/readme.ts`); `pages.yml` runs it on every push to main
- `mise run release <x.y.z>` — the only way to release: runs ci, `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`, which runs ci again, publishes to npm through trusted publishing (OIDC, with provenance — no token exists, so nothing is ever published from a machine) and cuts the GitHub release with the per-terminal archives and the commit subjects since the last tag as notes
- `bun install` for dependencies

## Conventions

The terminal wiring, the picture model and the shell layer (`.claude/rules/terminals.md`), the colors and marks every screen draws (`.claude/rules/tui.md`), `find` (`.claude/rules/find.md`) and `site/` (`.claude/rules/site.md`) have their own rules, which load only when a file they cover is opened with the Read tool — `cat` or `sed` in Bash does not load them, so open one with Read before reasoning about that area.

- First-party code carries **no comments** — a deliberate choice; do not add any.
- Every screen and message follows the text rules in CONTRIBUTING.md's "Writing the text": sentence case, with values, names, commands and keys as typed, key hints and `ttheme:` errors lowercase.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/*.toml` is the single source of truth for the official catalog; `dist/` is generated, never committed. Everyone else's palettes live in markets (`src/sources.ts`, `src/markets.ts`): a GitHub repository or a local folder holding `palettes/*.toml` and `palettes/<catalog>/*.toml` beside a hand-written `ttheme-market.toml` whose fields follow Claude Code's `marketplace.json`, in snake_case (`MARKET_KEYS`, `readMarketInfo`, `marketToml`): `name`, an `[owner]` table (`name` the GitHub handle, which names a local market, `email`, `url`), `description` (browse's detail panel, `ttheme market`, the site), `[renames]` (old slug → new slug, or `false` once gone), `force_remove_deleted_palettes` and a free `[metadata]`, with an editor-only `"$schema"` (`MARKET_SCHEMA_URL`; palette files carry `PALETTE_SCHEMA_URL`, which `paletteToml` writes and every `themes/*.toml` starts with). The JSON Schemas live in `schemas/` and are served by SchemaStore, which matches `ttheme-market.toml` by name; `schemas.test.ts` ties their keys and enums to `MARKET_KEYS`, `OWNER_KEYS`, `PALETTE_KEYS`, `SITES`, `POSITIONS` and `RULES`, and a change to them goes to SchemaStore as a PR (`src/schemas/json/ttheme-*.json` there, with TOML tests under `src/test/` and `src/negative_test/`, checked by `node ./cli.js check` and the advisory `coverage`; kecan0406 owns those files through SchemaStore's CODEOWNERS, so their own "LGTM" comment merges it). Enums there keep a string fallback (`anyOf` with `type: string`) wherever ttheme adds values over time — find sites, positions, gate rules — so an older copy never flags a newer file. An unknown key is ignored on read and named by `ttheme market check [dir]` (`checkMarket`), which also reads every palette as an install would, checks the renames (`renameProblems`) and prints the gate. `followMarkets` (`src/refresh.ts`, run by `update` and `applyRefreshed`) applies every market's renames and removals to what is installed (`plan`, `src/renames.ts`): the installed list and startup palette, the pins (`movePins`), `tone.json` (`moveTone`) and the pictures (`moveRacks`). Nothing is built or committed for it — a generated index tied every market to the ttheme that built it: a repository is fetched as its codeload archive (`archiveUrl`, `fetchArchive`, `untar` in `src/tarball.ts`, with the ETag so an unchanged one answers 304) and a folder is read in place, both through one reader (`readMarketFiles` in `src/own.ts`, over `marketLayout`'s paths), so every gate value, signature color and backdrop is derived by the reader, never stored. `installed.json`'s `markets` lists the sources (`official`, `owner/repo`, an absolute path; absent means `official` alone), and a market is `<owner>@<name>` (`marketId`): the repository's owner and its `ttheme-market.toml`'s `name` (a local one's file gives both), so its palettes are `<owner>@<name>/<slug>` (`nameProblem`, `marketOf`, `slugOf`, `src/theme.ts`). The market is their group (`readOwnText` sets it; `meta.group` is not read), and a folder under the market's `palettes/` is a catalog (`marketFiles`, the entry's `catalog`, never part of the name — a slug is used once in a market, `marketFileProblem`), so every list — `browse` (`PaletteList`'s `rule` and `catalog` rows), `preview` (`__tt_pv_rows`'s `cat` rows, from `TTHEME_CATALOG` in `palettes.zsh`) and the bare `ttheme` menu — shows the series first and the markets after a `── Markets` line, each market as market → catalog → palette with every row naming only its own part (`shownName`; a palette outside every catalog follows the catalogs), `alphabetical` included, while a place that names one palette — browse's right panel, preview's status line, `list` — keeps the whole name; no `order` or `role` (a `Place` with `open` reads a file as a market palette), and `meta.base` only names the official palette whose ANSI colors it took. `readCatalog` lays the official catalog `init` wrote (`catalog.json`) and every remote market's cached archive (`markets/<owner>--<repo>.json`: `{ etag, files }`, the fetched `ttheme-market.toml` and `palettes/` texts as they came — `Archive`, `parseArchive`, `readArchive` — refreshed by `update` and auto-update) together, a remote palette file that does not parse skipped silently there and listed under browse's Errors; there is no review — nothing but the official catalog's CI enforces the contrast gate. Anywhere a name becomes a file it goes through `stem` (`@` and `/` → `--`, which a slug never contains) — `owned`, the background files and confs, the iTerm2 Guid, and the zsh and watcher lookups (`${${name/@/--}/\//--}`, `palette.replace('@', '--', 1).replace('/', '--', 1)`, the same two `gsub`s in Lua).
- Markets behave like Claude Code's plugin marketplaces. A repository source may pin a ref (`owner/repo#v1`: `repoOf`/`refOf`, `archiveUrl` fetches that ref, the cache file ignores it, and adding the same repository with another ref moves it in place). `autoUpdates` is off for a repository until it is switched on, and never on for `official` or a folder; `installed.json`'s `updates` holds only the switches that differ from that default (`withMarkets`), and `market add` and `add --market` ask for a repository's (off without a TTY). `autoRefresh` (`src/refresh.ts`) runs in `runCli` before `add`, `remove`, `market`, `default`, `on` and `off`: each source with auto-update on whose cached copy is a day old (`dueSources` reads the cache's mtime; a failed try, kept in `$XDG_STATE_HOME/ttheme/markets.json`, waits an hour) is fetched within 5 s, a change is printed (`updateNote`) with the installed palettes that now have an update, and the markets' renames are followed (`applyRefreshed`) — never from the shell layer, whose hot paths start no process. `browse` (`src/browse.ts`, its UI `src/browse-panel.ts`) is a four-tab `BrowsePanel` — Catalog, Installed, Markets, Errors — over two `PaletteList`s sharing one picked set: it refreshes due markets in the background, stages market adds, removals, auto-update switches and palette updates along with the picks, and applies them all on enter (`applyBrowse`) from any row but a series, which enter opens and closes as in preview — through a review first (`phase`: `browse`, `review`, `applying`, `done`; `reviewLines`), then inside the panel itself: `BrowseIo.apply` runs `applyBrowse` under `into` (`src/pending.ts`), the one sink the apply path writes to (`say` for a line, the ones `applyRefreshed` returns included, and `pending` for the step in hand, which `bringPictures` already uses), so the panel shows the lines and a spinner while it works and a result until enter closes it; `runBrowse` prints the same lines to the scrollback after the screen leaves, and rethrows a failure. Its screen follows Claude Code's plugin screen: a pill on the tab, a heading with its counts, a boxed search (one line with the counts when the window has fewer than 22 rows), and — over Catalog and Installed, once there are two markets — a strip counting each (`chips`) that `ctrl+s` walks (`scope`, `scoped`: one market's palettes into the list, the counts and the heading following), `↑ n more` and `↓ n more` around the window, and two-line rows in Markets and Errors (`windowOf` counts lines). Markets looks GitHub up by itself unless `TTHEME_MARKET_LOOKUP` is `off`: the topic search when the tab opens and, a moment after typing stops, for the query (`lookup`, `search`, a counter drops stale answers), the archive of a typed `owner/repo` and of the repository the cursor rests on (`watch`, `load`, kept in `peeked` — `space` then stages it without fetching again, `arrive`), failures as a row `space` retries or in the detail panel, never in Errors; the tui harness turns it off. Its right-hand detail panel needs 94 columns (a narrower window gets one line under the list); every width goes through `fast-string-width`, so a line never wraps. init's picker is the same `PaletteList` inside `PalettePrompt`, without tabs.
- A user's own palettes live in a local market — `~/.config/ttheme/market/<name>` unless `ttheme market init` was given a folder (`ensureLocal`: one is used, several need `--in <name>`, none asks for a name and makes it) — as `palettes/<slug>.toml` (or `palettes/<catalog>/<slug>.toml` on a catalog's shelf; `new` files it loose), read with the same parser (`readLocal`/`readMarketDir`, `src/own.ts`, with an open `Place`: an unknown base or series is only a label there) and laid over the catalog by `available` (`src/catalog.ts`), which also adds back, from `kept.json` (the entries the last `sync` resolved), any installed palette no market carries — so every reader of palettes goes through `available`/`readAvailable`, never the bare catalog. `new` and `edit` open the palette editor full screen (`PaletteEditor`, a key-driven model in `src/palette-editor.ts`; `renderEditor` and the alt-screen session `runEditor` in `src/editor-screen.ts`, on the TUI runtime below): `new` starts on the seeds (`grow`, `src/seeds.ts` — background and foreground lightness, a hue and tint for the neutrals and the cursor, one lightness and chroma the accents share on `ROLE_HUES`' centers, which pass the gate at every seed) unless `--from` names a palette, and leaves them for good on enter (`edit` and `--from` never show them); then the slots, each shown and tuned in OKLCH (the grid lists L C H, the hex only in the slot's details) with one keymap on every screen (enter or `tab` tunes — `↑↓` move lightness, `←→` chroma, `⇧←→` hue by 5 (`,` `.` by 1), and `channel` is the one moved last, which `0`-`9` and `home`/`end` act on —, enter keeps, esc undoes every slot the tune moved, `s` saves, `r`/`R` put back the colors it opened with, `g` swaps the slots for their relations — lightness, chroma and hue of all sixteen ANSI colors, `relations` —, `n`/`N` walk the misses; while tuning `tab` moves to `◐`, a fourth channel that solves lightness for a contrast against the slot's partner, `partnerOf`, `home` its floor, `1`-`9` that ratio, and `a` cycles the scope, `SCOPES`/`scopeSlots`, whose slots move by the same step, `held` per slot; chroma stops at the sRGB edge, `edgeChroma`, and what lightness or hue took away comes back only while the tune lasts, `held`, drawn as `○`; a grey hex borrows the background's hue, `neutralHue`), with the gate measured per slot (`slotChecks`, `gateRows`; ✗ marks every slot whose own checks miss, `misses`) and saved only when the parser reads it (`check`, which also takes the signature `*` marks, `resign`); while it is open the terminal's own colors are never changed: only the mock terminal is drawn in the draft, in explicit colors, and the editor's own rows keep the terminal's — asked once before the first frame (the slots' OSC queries ahead of a DA1, read as `color` events; Ghostty leaves OSC 17 unanswered, so a missing selection is the terminal's background mixed with its foreground), which the sidebar's rows and the picker's panel draw with; the palette's own picture lies behind the window as preview lays it, tinted to the draft, its cover and veil placed over the window alone (`Backdrop`, `src/editor-backdrop.ts`: kitty layers, or WezTerm's view, which sets the whole window's background, and none in Terminal.app or Warp); `p`, a drop or a paste hands the terminal to `find` on the draft (`findFor`) and takes it back after. `new`, `edit`, `check`, `share` and the hidden `tone` (`src/craft.ts`) make, change, measure (`fixGate`, `src/fix.ts`, which the palette skill's role fixer shares; the gate only advises here) and hand them on; a share code (`tt2:`, `shareCode`/`fromCode`, its last four bytes the first four of a SHA-256 over the rest, so a mistyped one is refused) travels as a link, `https://ttheme.vercel.app/p/<code>` (`shareLink`, `SHARE_URL`), which `share` prints with its QR code under it when stdout is a terminal (`qrLines`, `src/qr.ts`, on `uqr`, black on white through 256-color indices 16 and 231, which no palette sets); `add` and the editor's paste take the link or the bare code (`codeOf`), which is decoded, written as TOML and parsed like any file (`readCode`, which the site's `/p/<code>` page reads too), and `adopt` puts the entry straight into `kept.json` — unless a palette of that name is already there, which it installs when the colors match its untuned ones (the code carries no `order`, `native` or `booru_sites`, so whole entries never match) with the code's pictures, and refuses when they differ. Anything a palette's `[[picture]]` lists is fetched only when the palette is newly installed or the list gained it (`since`), so a picture the user dropped stays dropped.
- The palette editor draws as a builder from 96×28 (`layoutOf`, `src/builder-layout.ts`: the geometry, the mock terminal window, its tabs and the scene lines each shows (`paneLines`), its frame (`joints`), the spots and which slots a scene role draws with; `renderBuilder`, `src/builder-screen.ts`; the drawing helpers it shares with the older screen are in `src/editor-paint.ts`, and `renderEditor` keeps that older slots-beside-detail screen below the size, for the seeds and for the keys and open overlays, calling `viewport` so the model knows the layout). A refresh is one `Outcome` (`attempt`: what was refreshed, or the failure it ended in), `failureLine` is how a failure reads everywhere, and `applyRefreshed` follows the markets' renames and returns its `left its market` lines for the caller to print.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/images.json` owns the pictures each palette keeps and which one is up, and only the CLI writes it — every `<palette>.conf` is a view regenerated from it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the block's include never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends), each default spelled out on a commented line and only a value that differs from it left live (`settingLine`, `__tt_config_line`; the layer's own `: ${X:=…}` fallbacks are held to `CONFIG_SETTINGS` by `wiring.test.ts`), so a default a later version changes reaches every setup that never touched it: the Ghostty block routes new tabs through `launch-tab.zsh` (unless the user's config sets its own `command`, and then the layer rotates at shell start), which reads the setting when the tab opens, and open shells keep theirs until they restart. `palettes.zsh` does not wait: every open shell re-reads it at its next prompt once its modification time moves (`__tt_fresh`, nanoseconds through `zstat -F %s.%N` — whole seconds miss two writes in one second), so a palette added or a default changed in one tab reaches every other tab, in any terminal (the pins file is watched the same way, so a pin set or dropped in one tab repaints the tabs already under it at their next prompt or focus) — which is why `sync` rewrites it (and drops its `.zwc`) only when its content changed, like every other file it writes, or after it touched Windows Terminal's `settings.json`.
- `installed.json` is read field by field through `OPTIONAL` (`src/palettes.ts`), a table whose type makes it cover every optional key of `Installed`, and each change spreads the state it read (`{ ...state, … }`); init's `planAgain` sets only what it asks again — the terminals, the palettes, `off`, the startup palette and Windows Terminal's paths — and carries the rest, so a field added later survives a rerun without being named anywhere (`palettes.test.ts` and `init.test.ts` hold both to a `Required<Installed>`).
- `src/verbs.ts` is the one list of commands: the CLI's parser and help read it (`cli.ts` adds the runs), and `palettes.zsh` carries every verb but the setup ones (`TTHEME_VERBS`, `TTHEME_VERB_ARGS`, `TTHEME_VERB_ABOUT`, `TTHEME_SHELL_VERBS`) for the shell's completion and argument checks, plus the help text itself (`TTHEME_HELP`, `TTHEME_HELP_ALL`, from `helpText`), so both helps say the same without node. There is no `preview` or `browse` command: a bare `ttheme` is the one way into both (the hub, `__tt_preview hub`, which opens on Preview; with no palette installed it runs `__tt_catalog browse` alone, since Preview has nothing to show), and `browse` stays in `VERB_SPECS` as a `hidden` verb only because the hub's Browse tab runs `__tt_cli browse` — a hidden verb is not in `palettes.zsh`, so typing it in the shell is an unknown command. When the hub closes from Browse, the tab's colors are put back by Browse's own `live.restore` (`runBrowse`, which a tab switch skips since Preview repaints) and by the host (`__tt_pv_screen` marks `painted=?` and calls the adapter hook `__tt_pv_forget`, because the host never saw what Browse painted). Help follows ffmpeg's: a version, description and usage line, `Getting help:` (the three tiers) and `Global options:` (`-h`, `-v`), then every section (`SECTIONS`: This tab, New tabs, Palettes, Your own, Setup, Support) listing each verb as its name and args beside its `about` up to the first ` — ` (`headOf`), so that head is a short phrase that fits one line; `ttheme help all` adds each verb's actions and flags indented under it, with their heads, and `Examples:`; `ttheme help <command>` (`commandHelp`) prints the whole `about`, the actions and the flags; the bare CLI with no arguments prints only the banner and a hint (`briefText`), on stderr with status 1. A palette is never a command — `ttheme use <palette>` paints a tab. `ttheme info` (`src/info.ts`, Support) is what a bug report carries — `.github/ISSUE_TEMPLATE/bug.yml` asks for its output instead of a version and a terminal typed by hand, so a row added to it is added to that field's description too; the shell case in `ttheme()` hands it `TTHEME_ZSH` (`ZSH_VERSION` cannot take a prefix assignment) and answers before the empty-install check, and `runCli` points a crash (`isCrash`: `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, or an error with a `code`) to it, never a message written for the user. `palettes.zsh` also names the `config.zsh` settings (`TTHEME_SETTINGS`, from `CONFIG_SETTINGS`), and `__tt_cli` hands every one that is set to the CLI, since `config.zsh` assigns without exporting.
- Every official palette must pass the contrast gate (src/contrast.ts), which checks readability (WCAG ratios) and function (OKLCH: each accent's hue inside its ANSI role's band, a bright within 25° of its normal, no two accents that read as one color; ANSI slots in `meta.signature` and their twins are exempt from the band). Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin. A run whose tasks go side by side prefixes every line and takes the TTY off stdout too, while a chain keeps it — which is why `bin:build` depends on `build`: `mise run parity` then keeps the terminal for its progress line, and `interactive` would have made `ci` wait for everything else before starting it (measured on mise 2026.8).
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- Any source file using `import.meta.dirname` to reach the repo root must sit directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` only resolves to the package root when the depth matches.
- `build` needs bun (`Bun.write`); TOML is read with `smol-toml` everywhere, so the CLI parses palette files under node too; `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json`, the only dist file the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- Preview's key loop (`__tt_pv_getch`) leaves when five reads in a row come back at once, which only a hung-up tty does (a timed-out `read -k` takes its whole timeout, `EPOCHREALTIME` from `zsh/datetime` tells them apart): a shell that is not the session leader — under a task runner such as `mise run` — never gets the SIGHUP, and the loop spun at 20% CPU on the dead tty, stty forks and all. Checking `[[ -t 0 ]]` or `stty size` does not catch it; both still succeed.
- JPEG pictures are decoded by mozjpeg compiled to WebAssembly (`src/jpeg.ts`, `@jsquash/jpeg`), which the bundle carries inside itself: `src/embed.ts` is a Bun macro that reads the `.wasm` at transpile time and inlines it deflated and base64-encoded, so `src/` runs under bun (the tests, `bun src/bin.ts`) and the bundle under node, but `src/` does not run under plain node. The decoder does not read arithmetic-coded JPEGs (it throws `not a JPEG image this decoder can read`), and it leaves EXIF orientation alone (a cut-out's mask has the raster's own size).
- `bin/` is generated by `mise run bin:build`, never committed. The bundle ships a linked source map without `sourcesContent` (`bin/ttheme.js.map`, copied beside the installed CLI): `TTHEME_DEBUG=1` makes `bin.ts` relaunch node with `--enable-source-maps`, and the CLI prints the error's stack in `src/` lines instead of its message alone.
