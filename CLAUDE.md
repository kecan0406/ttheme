# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check + node-bundle check + TUI screens + the parity walk (exactly what CI runs)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build): `shell/check.zsh`, `latency.zsh check` and the fork ratchet
- `mise run forks [--update]` — the fork ratchet (`tests/latency.zsh forks`, part of `shell:check`): starts a warm shell per terminal and mode with `xtrace` on and `PS4` printing `$sysparams[pid]`, counts the distinct PIDs each journey leaves in the trace (a new tab in `off` and `seq`, an empty command, a focus-in, a `cd`, and a command that resets a painted tab's cursor) beyond a bare zsh, and compares them with `tests/forks.tsv`: more fails as a regression, fewer fails until `--update` locks the lower count in, so a hot path only ever loses processes. The counts are a proxy (a subshell whose only work is forking children hides itself) that agreed with an exact `fork`/`execve` interposer everywhere but `base64` pipes, where it still counted more than none
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust] | --wezterm | --kitty | --alacritty | --warp | --terminal-app | --konsole] [--pictured] [--zshenv FILE] [--empty | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing `browse`). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--wezterm` starts a separate WezTerm on the sandbox's `wezterm.lua` (`TTHEME_WEZTERM_APP` names a WezTerm.app outside /Applications); `--warp` opens a Warp tab through `~/.warp/launch_configurations/ttheme-sandbox.yaml` (`warp://launch/<name>` matches the YAML's `name`, not its file name) and `--terminal-app` a Terminal.app window through a `.command` file — both run in the user's own app, since neither can be pointed at another home (`--terminal-app` wires Terminal.app into the user's own settings, which `tests/terminal-prefs.zsh` saves first and puts back when the run ends), and both are opened from `env -i`, since an app `open` starts keeps the caller's environment in every tab until it quits; `--konsole` (Linux) starts a separate Konsole on a D-Bus session of its own (`dbus-run-session`), and with `--behind` on a private Xvfb display (`TTHEME_KONSOLE_SCREEN`, `:77`), so neither the user's Konsole nor its default profile is touched; `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME` and `ZDOTDIR` scrubbed, and D-Bus cut off). `--pictured` puts a test picture on the last palette named before the terminal starts (compat's Terminal.app picture cases need one in a profile Terminal loads at launch). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run compat [--update] [ghostty iterm2 wezterm kitty alacritty warp terminal-app konsole…]` — the terminal compatibility suite: runs `tests/compat/cases.zsh` in each installed terminal through the sandbox (`--behind`), answers its screenshot requests (the window is found by pid and a per-run title, the pixel read by `tests/compat/sample.js`; Konsole's on its Xvfb display through `xdotool` and ImageMagick's `import`, read by `tests/compat/sample-png.ts`) and compares the results with `tests/compat/expect.tsv`; an expected pass that fails is a regression. Not part of ci — it opens GUI windows. Add a case there before claiming a terminal supports a feature. A `drawn` control (a truecolor fill the screenshot must show) runs before the screenshot cases, and in a window that does not redraw while covered the control and every screenshot case skip rather than fail, since that measures where the window sits, not the terminal, a DECRQM case skips in a terminal that answers no DECRQM at all (Konsole, Terminal.app), and `--update` never writes a skip over a pass or a fail. iTerm2 opens with `--trust`, on `ttheme · default` as a user's new tab does. Its capability cases (`painted`, `fg-painted`, `ansi-painted`, the `osc-*` round trips, `osc-reset`, `cell-size`, `cell-points`, `kitty-graphics`, `sync-query`, `focus-report`, `focus-event`, `focus-answer`, `front-tty`, the `scheme-*` cases, which only Konsole passes — a scheme's wallpaper drawn, held while a tab shows it, read again once none does —, the `profile-picture` and `picture-*` cases, which only Terminal.app passes — a profile's picture drawn over a background an OSC set, held per path, read again once its file is renamed, gone with its file — and `prompt-trap`, which runs last: the cases leave the shell at its prompt, signal it and hang it up) are what the parity model's `BEHAVIOR` may claim — `focus-event` moves focus away and back, which the harness does only on Konsole's Xvfb display and skips wherever it would take focus from the user — and its journey cases (`follow-default`, `follow-belief`, `keep-painted`, `on-follow`, `on-belief`, `reset-worn`) must end as the parity model's `default-here`, `default-keeps`, `on` and `program-reset` do — `tests/parity/parity.test.ts` holds both wherever compat measured a pass or a fail
- `mise run compat:konsole [--update]` — the same suite in Konsole from macOS: builds `tests/compat/konsole.Dockerfile` (Ubuntu 24.04, Konsole 23.08, Xvfb with `xcompmgr`, which Konsole 23.08 needs to draw a color scheme's wallpaper, `xdotool`, ImageMagick, node, bun) and runs `tests/compat.zsh` in it on this checkout, where every other terminal counts as not installed; needs Docker running
- `mise run parity [--update] [--only <terminal,…>] [--journey <id,…>] [--show <journey.label>] [-v] [--slots N]` — coverage held to one spec in every terminal (`tests/parity/`, part of ci): every journey in `journeys.ts` (a new tab, `use`, `next`, the menu, `default`, `off`, `on`, focus, a busy tab brought to the front, a command ending in a tab behind, preview's hover, keep, Default, tuning and settings panels, a picture dropped or tuned in another tab, pins and a pin set in another tab, an ssh host's pin, browse, a palette added elsewhere, an unwired terminal, a program resetting a painted tab's colors, a shell in an editor's terminal, and a default or tuned picture reaching Ghostty) is walked in every terminal against a model of it: real zsh tabs on Bun PTYs running the installed layer and the real CLI, an xterm-headless screen, and a synchronous protocol parser per tab (`model.ts`) that answers queries and applies each terminal's colors, resets, profiles, schemes, user vars, reloads and pictures from what it would read (`looks.ts` parses each terminal's own config files, never the emitters) — then each look's facts (the front tab's colors as a palette name, the picture the user sees and its opacity, what the shell believes it wears, and optionally the screen text) are held to the look's spec in every terminal, Ghostty included: the palette `journeys.ts` says the front tab shows (`want`, with `picture`, `opacity` and `repaints` where the look names them), an `issue` of `-` (the shell's belief disagreeing with what the tab shows, or an echoed escape, is one), and for a screen the one Ghostty drew, approved with `--update`. `facts.tsv` holds the spec in its `spec` column and every terminal's cell as `=` or its own value, and every cell that misses the spec needs a row in `gaps.tsv` (terminal, fact glob with `{a,b}` alternatives, `cannot` / `layer` / `deferred`, reason) — or, where the model says the terminal lacks a capability (`CAPABILITIES` in `terms.ts`: `pictures`, `wired`), its one `@capability` row, which explains every fact that needs it (a look's picture and opacity need `pictures`, and so does its screen where the look says so — `text: 'pictures'` for the tuning panel's picture rows; the colors, wears, picture and screen of a look marked `unpainted` need `wired`). A changed fact, the spec's included, fails until `--update` records it, an unexplained cell fails until it is fixed or given a reason, a gap row that covers a fact it does not explain fails until it is narrowed, and one that explains nothing fails once every fact it covers was walked; a journey whose facts moved, or missed the spec with no reason, is walked again one at a time up to twice before it counts, so a loaded machine does not fail it or get recorded by `--update`. Each terminal's fixture home is built once per slot by the real `init --yes`, `add`, `default` and `installBackdrop`, snapshotted and restored before every journey; shims (`ps`, `pkill`, `defaults`, `dbus-send`) keep every process off the user's real terminals and fake iTerm2's preferences and Konsole's D-Bus, and a Warp session database drives its follower. While it walks, a terminal shows one progress line (the phase, the count, the journey that finished last, and what is still running once three are left) and a pipe gets a line per phase and every 10 s; the report is a table fitted to the window (short names when it is narrow) marking each journey ✓ (meets the spec), ○ (meets it but for a capability the terminal lacks), · (explained in `gaps.tsv`), ! or ✗, a `meets` row counting ✓ and ○, the facts each missing capability and each gap kind explains, how many journeys meet the spec in every terminal, and the changed facts, unexplained cells, loose gaps and stale gaps each in their own list with what to do about them. The report ends by naming, per terminal, the compat cases the model leans on (`MEASURED` and the journey `BRIDGES` in `facts.ts`) that `tests/compat/expect.tsv` leaves undecided (`?` or `skip`) — the model's standing assumptions — and every terminal compat has no column for
- `mise run bench [--against <ref>] [runs]` — shell latency through a pty (`tests/latency.zsh`, zsh's own `zpty`, answering the layer's terminal queries): zsh-bench's four metrics (first prompt, first command, command, input) for a bare shell and for ttheme off, seq and Terminal.app, interleaved, printed as each one's median difference from the bare shell and its share of zsh-bench's thresholds (50/150/10/20 ms). `--against <ref>` adds the same three shells on `<ref>`'s `shell/` (with this build's `palettes.zsh`) and prints the working tree minus `<ref>`, paired run by run, as a median with its p25–p75 — seq is the control when a change leaves it alone, so a range straddling 0 there is the noise floor; a layer that loses the keys typed ahead shows "typed keys lost" for first command. The harness never idles between shells: a second of waiting lets the CPU clock down and the next shell starts about 1.5× slower (measured), so a lost command is detected with a follow-up command, not a timeout. Not part of ci — wall time on a shared runner is noise; `shell:check` runs the same harness as `latency.zsh check`, which asserts no times, only orders: a command typed before the first prompt runs and stderr still reaches the terminal (on a first tab and on a second one, which remembers the terminal's colors), a second tab asks the terminal nothing before its first prompt, keys typed into preview while it draws are never echoed into it, while preview sits idle its search hint redraws its first row only, and a preview hover in iTerm2 paints no ANSI color (each OSC color is a profile change there), and none of it breaks under a `.zshrc` that sets `no_clobber`, `ksh_arrays`, `sh_word_split`, `no_unset` and the like before it sources the layer. The harness sets `err_return`, so a `(( x++ ))` that starts at 0 returns from the function — count with `(( ++x ))`. Never measure with `time zsh -lic exit`
- `mise run site:dev` / `mise run site:build` — the showcase site; not part of ci, and `next build` is where site/ gets typechecked (root `tsc` only covers `src/`)
- `mise run release <x.y.z>` — the only way to release: runs ci, `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`, which runs ci again, publishes to npm through trusted publishing (OIDC, with provenance — no token exists, so nothing is ever published from a machine) and cuts the GitHub release with the per-terminal archives and the commit subjects since the last tag as notes
- `bun install` for dependencies

## Conventions

The terminal wiring, the picture model and the shell layer (`.claude/rules/terminals.md`), `find` (`.claude/rules/find.md`) and `site/` (`.claude/rules/site.md`) have their own rules, which load only when a file they cover is opened with the Read tool — `cat` or `sed` in Bash does not load them, so open one with Read before reasoning about that area.

- First-party code carries **no comments** — a deliberate choice; do not add any.
- Every screen and message follows the text rules in CONTRIBUTING.md's "Writing the text": sentence case, with values, names, commands and keys as typed, key hints and `ttheme:` errors lowercase.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/*.toml` is the single source of truth for the official catalog; `dist/` is generated, never committed. Everyone else's palettes live in markets (`src/sources.ts`, `src/markets.ts`): a GitHub repository whose `ttheme-market.json` (`MarketIndex`, `parseIndex` — the manifest shape plus `owner` and `name`, entries named bare) its reusable action `market/action.yml` rebuilds from `palettes/*.toml` and `palettes/<catalog>/*.toml` on every push (`ttheme market build`), or a local folder read in place. `installed.json`'s `markets` lists the sources (`official`, `owner/repo`, an absolute path; absent means `official` alone), and a market is `<owner>@<name>` (`marketId`): the repository's owner and its index `name` (a local one's index gives both), so its palettes are `<owner>@<name>/<slug>` (`nameProblem`, `marketOf`, `slugOf`, `src/theme.ts`). The market is their group (`readOwnText`, `marketEntries` set it; `meta.group` is not read), and a folder under the market's `palettes/` is a catalog (`marketFiles`, the entry's `catalog`, never part of the name — a slug is used once in a market, `marketFileProblem`), so every list — `browse` (`PaletteList`'s `rule` and `catalog` rows), `preview` (`__tt_pv_rows`'s `cat` rows, from `TTHEME_CATALOG` in `palettes.zsh`) and the bare `ttheme` menu — shows the series first and the markets after a `── Markets` line, each market as market → catalog → palette with every row naming only its own part (`shownName`; a palette outside every catalog follows the catalogs), `alphabetical` included, while a place that names one palette — browse's right panel, preview's status line, `list` — keeps the whole name; no `order` or `role` (a `Place` with `open` reads a file as a market palette), and `meta.base` only names the official palette whose ANSI colors it took. `readCatalog` lays the cached official catalog (`catalog.json`) and every remote market's cached index (`markets/<owner>--<repo>.json`, refreshed by `update` and auto-update) together; there is no review — nothing but the official catalog's CI enforces the contrast gate. Anywhere a name becomes a file it goes through `stem` (`@` and `/` → `--`, which a slug never contains) — `owned`, the background files and confs, the iTerm2 Guid, and the zsh and watcher lookups (`${${name/@/--}/\//--}`, `palette.replace('@', '--', 1).replace('/', '--', 1)`, the same two `gsub`s in Lua). The `v1` tag, which market repositories' workflows use, is moved to each release by `release.yml`.
- Markets behave like Claude Code's plugin marketplaces. A repository source may pin a ref (`owner/repo#v1`: `repoOf`/`refOf`, `rawUrl` fetches that ref, the cache file ignores it, and adding the same repository with another ref moves it in place). `autoUpdates` is on for `official` and off for a repository; `installed.json`'s `updates` holds only the switches that differ from that default (`withMarkets`), and `market add` and `add --market` ask for a repository's (off without a TTY). `autoRefresh` (`src/refresh.ts`) runs in `runCli` before `add`, `remove`, `market`, `default`, `on` and `off`: each source with auto-update on whose cached copy is a day old (`dueSources` reads the cache's mtime; a failed try, kept in `$XDG_STATE_HOME/ttheme/markets.json`, waits an hour) is fetched within 5 s, a change is printed (`updateNote`), and the installed palettes it changed are synced and their newly listed pictures fetched (`applyRefreshed`) — never from the shell layer, whose hot paths start no process. `browse` (`src/browse.ts`, its UI `src/browse-panel.ts`) is a four-tab `BrowsePanel` — Catalog, Installed, Markets, Errors — over two `PaletteList`s sharing one picked set: it refreshes due markets in the background, stages market adds, removals and auto-update switches along with the picks, and applies them all on enter (`applyBrowse`) from any row but a series, which enter opens and closes as in preview — through a review first (`phase`: `browse`, `review`, `applying`, `done`; `reviewLines`), then inside the panel itself: `BrowseIo.apply` runs `applyBrowse` under `into` (`src/pending.ts`), the one sink the apply path writes to (`say` for a line, `pending` for the step in hand, which `bringPictures` and `applyRefreshed` already use), so the panel shows the lines and a spinner while it works and a result until enter closes it; `runBrowse` prints the same lines to the scrollback after the screen leaves, and rethrows a failure. Its screen follows Claude Code's plugin screen: a pill on the tab, a heading with its counts, a boxed search (one line with the counts when the window has fewer than 22 rows), and — over Catalog and Installed, once there are two markets — a strip counting each (`chips`) that `ctrl+s` walks (`scope`, `scoped`: one market's palettes into the list, the counts and the heading following), `↑ n more` and `↓ n more` around the window, and two-line rows in Markets and Errors (`windowOf` counts lines). Markets looks GitHub up by itself unless `TTHEME_MARKET_LOOKUP` is `off`: the topic search when the tab opens and, a moment after typing stops, for the query (`lookup`, `search`, a counter drops stale answers), the index of a typed `owner/repo` and of the repository the cursor rests on (`watch`, `load`, kept in `peeked` — `space` then stages it without fetching again, `arrive`), failures as a row `space` retries or in the detail panel, never in Errors; the tui harness turns it off. Its right-hand detail panel needs 94 columns (a narrower window gets one line under the list); every width goes through `fast-string-width`, so a line never wraps. init's picker is the same `PaletteList` inside `PalettePrompt`, without tabs.
- A user's own palettes live in a local market — `~/.config/ttheme/market/<name>` unless `ttheme market init` was given a folder (`ensureLocal`: one is used, several need `--in <name>`, none asks for a name and makes it) — as `palettes/<slug>.toml` (or `palettes/<catalog>/<slug>.toml` on a catalog's shelf; `new` files it loose), read with the same parser (`readLocal`/`readMarketDir`, `src/own.ts`, with an open `Place`: an unknown base or series is only a label there) and laid over the catalog by `available` (`src/catalog.ts`), which also adds back, from `kept.json` (the entries the last `sync` resolved), any installed palette no market carries — so every reader of palettes goes through `available`/`readAvailable`, never the bare catalog. `new` and `edit` open the palette editor full screen (`PaletteEditor`, a key-driven model in `src/palette-editor.ts`; `renderEditor` and the alt-screen session `runEditor` in `src/editor-screen.ts`, on the TUI runtime below): `new` starts on the seeds (`grow`, `src/seeds.ts` — background and foreground lightness, a hue and tint for the neutrals and the cursor, one lightness and chroma the accents share on `ROLE_HUES`' centers, which pass the gate at every seed) unless `--from` names a palette, and leaves them for good on enter (`edit` and `--from` never show them); then the slots, each shown and tuned in OKLCH (the grid lists L C H, the hex only in the slot's details) with the keys of preview's panel, both screens one keymap (enter or `tab` tunes, enter keeps, esc undoes every slot the tune moved, `s` saves, `r`/`R` put back the colors it opened with, `g` swaps the slots for their relations — lightness, chroma and hue of all sixteen ANSI colors, `relations` —, `n`/`N` walk the misses; while tuning `◐` is a fourth channel that solves lightness for a contrast against the slot's partner, `partnerOf`, `home` its floor, `1`-`9` that ratio, and `a` cycles the scope, `SCOPES`/`scopeSlots`, whose slots move by the same step, `held` per slot; chroma stops at the sRGB edge, `edgeChroma`, and what lightness or hue took away comes back only while the tune lasts, `held`, drawn as `○`; a grey hex borrows the background's hue, `neutralHue`), with the gate measured per slot (`slotChecks`, `gateRows`; ✗ marks every slot whose own checks miss, `misses`) and saved only when the parser reads it (`check`, which also takes the signature `*` marks, `resign`); while it is open the terminal is painted only the slots that changed, coalesced to 30 Hz, only OSC 10/11 in iTerm2, and gets `queryTerminalColors`' answer back when it closes, and the palette's own picture lies behind it as preview lays it, tinted to the draft (`Backdrop`, `src/editor-backdrop.ts`: kitty layers, or WezTerm's view, and none in Terminal.app or Warp); `p`, a drop or a paste hands the terminal to `find` on the draft (`findFor`) and takes it back after. `new`, `edit`, `check` and `share` (`src/craft.ts`) make, change, measure (`fixGate`, `src/fix.ts`, which the palette skill's role fixer shares; the gate only advises here) and hand them on; a share code (`tt1:`, `shareCode`/`fromCode`) is decoded, written as TOML and parsed like any file, and the entry goes straight into `kept.json` (`adopt`). Anything a palette's `[[picture]]` lists is fetched only when the palette is newly installed or the list gained it (`since`), so a picture the user dropped stays dropped.
- A character's names in every language come from aninames (`kecan0406/aninames`, its own repository and license layers), which ttheme only reads, from `$XDG_CACHE_HOME/ttheme/aninames/ttheme-<layer>.json` (core, kowiki, unlicensed; `namesDir`, `src/names.ts`): nothing ships them, and without them — or with a layer that does not parse, which is skipped — nothing changes. `sync` writes each installed palette's aliases — its tag's names in Korean, Japanese, English and Chinese, at most 16, less its `native_names` and any `name (work)` whose bare name is there — to `aliases.zsh` beside `palettes.zsh` as `TTHEME_ALIASES`, which preview sources into a local when it opens (so no shell start pays for it) and whose names its search matches and names beside a row; browse, init's picker and `ttheme list` match them and `native_names` through `aliasesFor`, once `knowAliases` has asked for every palette they list. Both go through `aliases.json` beside the layers, keyed by their sizes and times, so a sync reads the layers only when they or the palettes' tags change. find suggests a character's danbooru tag for a name typed in any language (`nameHits`) from `index.bin`, the index built beside the layers — about 1.4 s and 570 MB once per change of the layers, then opened in about 4 ms: the search keys sorted in one buffer with their owners as typed arrays, a card decoded only for a hit. A hit scores its character's danbooru posts (`log1p` against the most tagged, which the slices carry as `posts`), 0.25 per level — the whole query a whole name, a word of one, a prefix; a generated Hangul spelling one level lower — and 0.1 for a character a catalog palette has, whose own tag it then returns (`prefer`), so a palette whose tag is an older danbooru name still gets its `booru_sites`. Picking one replaces the whole query, and a query with Hangul, kana or Han starts with the first name picked, so enter searches it. The palette skill's `natives.ts` lists a tag's Japanese, Korean and other names for `meta.native_names`.
- A palette's tone is tuned in preview's panel (`tab`, `→` or `ctrl+e` on a palette — `tab` switches screens of the bare `ttheme` only off a palette, `shift+tab` everywhere — `__tt_te_*` in `shell/preview.zsh`) and kept as an override, never as a new palette: `~/.config/ttheme/tone.json` (`src/tone.ts`, written only by `ToneSession.save` in `src/tone-server.ts`) maps a palette to the slots that differ from the colors its market gives, and `available` lays it over every entry (`tonedEntry` recomputes the signature, the gate and the backdrop tint; `untuned` is the same view without it) — so every reader, `sync` and the pictures' retint follow it, while `sync` writes `kept.json` from the untuned entries, since a tone must always be able to go back to what the market gave. The panel takes the sample's place beside preview's list (the whole screen when the window has no room for the sample, `__tt_pv_te_draw`) and is one list under one EDIT badge — the picture's rows (Images, its thumbnails or an empty frame whose enter opens find, then colors, size, position and opacity, dimmed with no picture), the palette's slots, then an Apply button — scrolled by `__tt_pv_te_panel` to keep the cursor in view: the palette half is the node palette editor (`PaletteEditor` with `variant: 'theme'`, `renderTone`) run as a coprocess (`ttheme tone <palette>`, a hidden verb: one request line in — `key <name>`, `ch <code>`, `mouse <action> <line> <col> <n>`, `size`, `focus`, `save`, `quit` — and one frame line out, fields split on `\x1f`: status, the host signal `save`/`cancel`, or `above`/`below` when `↑`/`↓` leave the first or last slot instead of wrapping, mode, dirt, the 20 colors shown, key hints, a note, the cursor's line, then the panel's lines), and the image half is the zsh tuning code (`__tt_pv_tune*`, `__tt_pv_bg_panel`) unchanged. The tone server also takes `show <path>`, the picture preview draws, and answers every frame with a copy of it tinted to the draft and the opacity saving would give it (`Tints`, `drafted`, `src/tints.ts`; a retone swaps only the PNG's `PLTE`), so the layers behind the panel — the background, the picture and its opacity, which follows the draft unless the user set it — move with every key (`__tt_pv_bg_draft`); where that cannot be drawn live (`__tt_bg_tints` fails: Terminal.app, Warp) the picture's title line says `recolors on save`. Preview, browse and init's picker filter as you type, so `j`/`k` move like `↓`/`↑` only where nothing filters — the panel, preview's settings, the palette editor and find's grid — and enter on a palette in preview's list applies it at once, asking where. Nothing is kept before `s` (`__tt_te_save`: the picture through `__tt_pv_bg_save`, the tone through the server, then `__tt_palettes_load` and `__tt_reload`); `esc` drops what changed since and goes back to the list; enter on a slot tunes it, and enter on Apply saves and then asks where to apply (`Default` first), through the same `pick` panel `pin` and `init` use. `ttheme share` offers the tuned palette (named `<name>-tuned`, since the name belongs to the original wherever it is installed) or the original (`--tone`).
- Every Node screen — browse, init's picker, the palette editor, find — runs on one runtime in `src/tui/`, and a screen is a model whose `view` returns its rows. `Terminal` (`terminal.ts`, opened through `within`) owns the terminal while a screen is up: raw mode and the modes the screen sets (`ALT_SCREEN`, `HIDE_CURSOR`, `NO_WRAP`, `PASTES`, `FOCUS`; `hold` adds one later, as find does focus reporting once its probes are answered), counted across screens nested in one process (find inside the editor), so the inner one puts back only what it set, and put back in reverse on every way out — the screen's own `finally`, a signal (SIGTERM, SIGHUP, SIGINT, SIGQUIT end every open screen with `Signalled`, which `runCli` exits with as 128+n, silently), an error thrown anywhere while a screen is up (every open screen fails with it through `until`, so each cleanup runs and the CLI prints it on the main screen) and process exit; SIGCONT sets them again. Modes a program around it already set — preview around find or around browse in the hub — are `assume`d: set, never put back. `Keys` (`keys.ts`) is the one input decoder: bytes to named keys (`up`, `shift-left`, `ctrl-r`, `alt-v`, a character), pastes, focus, OSC and DECRQM, DA1 and size replies, in stream order, holding a sequence split across reads (a lone ESC 30 ms, a partial CSI 50 ms, a paste or an OSC until it ends, appended without rescanning) — so no screen reads `esc` out of half an arrow; `loop` hands a screen its events until it returns a result, and `ask` sends a query and takes its answer, holding other input meanwhile (`CELL_QUERY`, `CellProbe`). `Screen` (`screen.ts`) writes a frame as the rows that changed since the last one, in one write inside a synchronized update; a frame that changes nothing writes nothing, input paints on the next turn (`soon`), anything else at most every 16 ms (`request`), and the 80 ms beat runs only while the frame on screen moves (`ticking`); `Inline` does the same below the cursor for a prompt in clack's flow (init's picker). `edit` (`field.ts`, and `Field` around it) is the one line editing every text input shares — the filters, find's search and settings, the editor's typed color: backspace takes a whole grapheme, ctrl+u clears, ctrl+w drops a word. clack stays for the inline questions only (`p.confirm`, `p.text`, …): no screen subclasses its `Prompt`.
- Every full-window screen takes the mouse as well as the keys — preview and the bare `ttheme`'s tabs, browse, the palette editor, the panel preview opens beside a palette, find — and every mouse action has a key that does the same; init's picker (`Inline`) takes none, since it draws below the prompt with no row of its own to map a click to and the wheel must keep scrolling the terminal. The modes are `MOUSE` (1000, 1002 and 1006, put back in reverse; 1003, 1015 and 1016 never), which `pointing()` gives unless `TTHEME_MOUSE=off` (`config.zsh`, preview's alt-c `Mouse`, which lets go at once); every Node screen claims it itself, never `assume`s it, so it goes off when that screen does, and preview, which sets and clears its own in `__tt_pv_pointer` alone (`pvmouse` holds what it wrote), turns it back on when browse or find hands the terminal back. `Keys` reads SGR reports (`Mouse`: press, release, drag, wheel, zero-based `row`/`col`, modifiers) and a legacy X10 report, rewritten to SGR from the raw bytes (`legacy`) because the UTF-8 decoder turns a coordinate byte past 95 into U+FFFD — tmux sends X10 to a pane that asked for SGR when the outer terminal does not speak it — so its three bytes never land as keys; a press and its release carry `count` (500 ms and the same cell, ±1 column, as fzf and Textual), and a same-direction wheel event within 5 ms of the last is dropped, so the three Ghostty sends per notch move one row. A view marks what it can be clicked on with `zone(target, text)` (`src/tui/zones.ts`; `keyZone(word, text)` for a key hint, whose first word names the key it presses): zero-width marks (`CSI ? n y`, which `fast-string-width` and `fit` skip) that exist only while `Screen` paints, so a view drawn elsewhere — the tests, `Inline` — gets plain text, lifted out with the columns they wrapped (`lift`, following CHA) before the frame is diffed; find hands its `Line` parts and its tiles as rectangles in `Frame.zones` instead. `Screen.point` answers from the frame on screen, the smallest zone under the pointer, and a left press captures its zone (`Pointer`), so a drag and the release are measured against it even off it. A press selects — a row, a tab, a chip, a tile, a slot, a slider's value (the L, C, H and ◐ bars and the seeds jump to the point and follow a drag; a press on a bar in the list starts tuning that channel) — and only a release over the zone pressed acts — a key hint, a ○ or ▸, a link, the second release of a double click, which does what enter does — so a screen that closes on a click has read the release first and nothing leaks into the shell; the wheel moves the cursor a row without wrapping (find's grid a row of tiles, its try-on the next picture). Preview does the same in zsh with no fork: `__tt_pv_sgr` decodes, `__tt_pv_draw` and the panels append `"row from to action args"` to `pvz` on every full draw (a hint-only redraw keeps them), `__tt_pv_spot` finds the last zone under the pointer, `__tt_pv_press`/`__tt_pv_release` act (`mzone` holds the pressed one), and the tone panel's lines forward to the tone server as `mouse …` with the line and column inside the panel, where `pointEditor` (`src/editor-screen.ts`) acts on the same zones `renderTone` drew. A link is the terminal's to open, except in find, which opens a clicked post or source itself (`visit`: a plain click, not over SSH, http(s) or file) — the three terminals find draws in never also open it: Ghostty reports a Cmd-click as a plain click, iTerm2 keeps its Cmd-click, kitty's Shift-click bypasses reporting.
- A CLI verb that waits on the network says what it waits on through `pending` (`src/pending.ts`): one dim spinner line on stdout that shows only after 300 ms and only when stdout is a TTY (the shell layer's `$(__tt_cli …)` captures stdout, so preview never sees it), with the stage, the thing and `n/m` (`Downloading kita · danbooru 1234 · 3.1/8.4 MB · 1/2`, `Updating official, owner/repo · 1/2`), result lines printed above it through `say`, and gone on `done` — find's loader in one line, never a line per item.
- ttheme writes colors only — no font, font size, codepoint map or shader in any terminal, since a theme tool that sets those overrides the user's own (Ghostty loads a `config-file` after the whole file, so its keys win wherever the include sits). Of the colors it sets a palette's 16 ANSI colors and never the 256-color extension (Ghostty's `palette-generate`, iTerm2's `Harmonize 256 Colors`): colorschemes written for the 256-color palette, Vim's without `termguicolors` among them, read indices 16–255 as xterm's. A Ghostty theme file also carries the dock-icon colors, which `theme =` loads before the user's config, so the user's own keys still win.
- A user's config is edited only through `editUserFile` (`src/edits.ts`): a copy to `<file>.ttheme.bak` before the first edit (never overwritten), then a temp file renamed over the symlink's target, so a dotfiles link survives. A key the user sets outside the block stays theirs (`userSets`, `src/wiring.ts`): the Ghostty block drops `command` (and with it `shell-integration`) when the config has its own, and the kitty block drops `window_logo_scale`/`window_logo_alpha` the same way; `launch-tab.zsh` execs `$SHELL`, not `/bin/zsh`. Every file ttheme adds to a terminal's own folders, and every scheme name there (WezTerm, Windows Terminal, `.itermcolors`), is `owned(<palette>)` = `ttheme-<stem>` (Konsole's schemes and profiles too), which is also how `uninstall` finds them. init lists every file it will edit and the keys its block sets (`wiringPlan`), notes what the user's config overrides (`wiringNotes` — an Alacritty config's own `[colors]` win over its import), and refuses to run without a TTY unless given `--yes`. Run over an existing install (a readable `installed.json`), init is the update path — `npx …@latest init` is the only way a new version reaches `~/.config/ttheme` — so it first offers to update and keep everything (`planUpgrade`: the same terminals, palettes, default and `off`, only the layer replaced; the installed copy's `--version` names what is replaced; default yes), and `--yes` does that without asking instead of starting over; "set it up again" starts from the current terminals, the per-palette picker with the current palettes checked — offering every market the install has (`againCatalog`: the bundled official catalog while `official` is among them, the other markets' palettes and the installed ones kept) — and the default that was in effect, and keeps the markets, their auto-update switches and the handle (`planAgain`).
- `uninstall` (`src/uninstall.ts`, a setup verb run through npx like init) lists and then reverses everything: each block comes out (`removeBlock`, `removeLuaBlock`; a config ttheme created is deleted), Warp's theme comes back from `warp.base`, iTerm2's and Konsole's default profiles from `itermBase` and `konsoleBase`, and the `ttheme-*` files, `~/.config/ttheme`, the cache and state dirs, the dynamic profile and the WT fragment go. A config equal to its backup loses the backup; one edited since keeps it. An open shell whose `~/.config/ttheme` is gone drops out at its next prompt (`__tt_gone`, from `__tt_fresh`): reload, reset, focus reporting off, hooks and the `ttheme` function removed.
- Series metadata lives once, in `themes/_groups.toml`: every `meta.group` needs a `[[group]]` table there, which owns the `native` title and names the `lead` palette whose signature colors the group. A theme file never repeats them.
- `meta.signature` names three palette slots (`cursor`, `foreground`, `background`, `selection`, `ansi0`-`ansi15`) — the colors that identify the character on a card. They must resolve to three different colors.
- `dist/manifest.json` is the data contract for everything outside the build: `init` and `site/` read it instead of re-parsing `themes/` (site tasks depend on `build`). Every dist artifact goes through an `Emitter` in `src/emit/` — terminals emit per theme, `shell`/`meta` emit shared files.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/images.json` owns the pictures each palette keeps and which one is up, and only the CLI writes it — every `<palette>.conf` is a view regenerated from it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the block's include never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends), each default spelled out on a commented line and only a value that differs from it left live (`settingLine`, `__tt_config_line`; the layer's own `: ${X:=…}` fallbacks are held to `CONFIG_SETTINGS` by `wiring.test.ts`), so a default a later version changes reaches every setup that never touched it: the Ghostty block routes new tabs through `launch-tab.zsh` (unless the user's config sets its own `command`, and then the layer rotates at shell start), which reads the setting when the tab opens, and open shells keep theirs until they restart. `palettes.zsh` does not wait: every open shell re-reads it at its next prompt once its modification time moves (`__tt_fresh`, nanoseconds through `zstat -F %s.%N` — whole seconds miss two writes in one second), so a palette added or a default changed in one tab reaches every other tab, in any terminal (the pins file is watched the same way, so a pin set or dropped in one tab repaints the tabs already under it at their next prompt or focus) — which is why `sync` rewrites it (and drops its `.zwc`) only when its content changed, like every other file it writes, or after it touched Windows Terminal's `settings.json`.
- `installed.json` is read field by field through `OPTIONAL` (`src/palettes.ts`), a table whose type makes it cover every optional key of `Installed`, and each change spreads the state it read (`{ ...state, … }`); init's `planAgain` sets only what it asks again — the terminals, the palettes, `off`, the startup palette and Windows Terminal's paths — and carries the rest, so a field added later survives a rerun without being named anywhere (`palettes.test.ts` and `init.test.ts` hold both to a `Required<Installed>`).
- `src/verbs.ts` is the one list of commands: the CLI's parser and help read it (`cli.ts` adds the runs), and `palettes.zsh` carries every verb but the setup ones (`TTHEME_VERBS`, `TTHEME_VERB_ARGS`, `TTHEME_VERB_ABOUT`, `TTHEME_SHELL_VERBS`) for the shell's completion and argument checks, plus the help text itself (`TTHEME_HELP`, `TTHEME_HELP_ALL`, from `helpText`), so both helps say the same without node. Help is tiered: `ttheme help` shows the verbs with a `start` line ("Start here") and every section (`SECTIONS`: This tab, New tabs, Palettes, Your own, Setup, Support) as one line of names; `ttheme help all` lists each with its `about`. A palette is never a command — `ttheme use <palette>` paints a tab. `ttheme info` (`src/info.ts`, Support) is what a bug report carries — `.github/ISSUE_TEMPLATE/bug.yml` asks for its output instead of a version and a terminal typed by hand, so a row added to it is added to that field's description too; the shell case in `ttheme()` hands it `TTHEME_ZSH` (`ZSH_VERSION` cannot take a prefix assignment) and answers before the empty-install check, and `runCli` points a crash (`isCrash`: `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, or an error with a `code`) to it, never a message written for the user. `palettes.zsh` also names the `config.zsh` settings (`TTHEME_SETTINGS`, from `CONFIG_SETTINGS`), and `__tt_cli` hands every one that is set to the CLI, since `config.zsh` assigns without exporting.
- Every official palette must pass the contrast gate (src/contrast.ts), which checks readability (WCAG ratios) and function (OKLCH: each accent's hue inside its ANSI role's band, a bright within 25° of its normal, no two accents that read as one color; ANSI slots in `meta.signature` and their twins are exempt from the band). Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin. A run whose tasks go side by side prefixes every line and takes the TTY off stdout too, while a chain keeps it — which is why `bin:build` depends on `build`: `mise run parity` then keeps the terminal for its progress line, and `interactive` would have made `ci` wait for everything else before starting it (measured on mise 2026.8).
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- Any source file using `import.meta.dirname` to reach the repo root must sit directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` only resolves to the package root when the depth matches.
- `build` needs bun (`Bun.write`); TOML is read with `smol-toml` everywhere, so the CLI parses palette files under node too; `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json`, the only dist file the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- Preview's key loop (`__tt_pv_getch`) leaves when five reads in a row come back at once, which only a hung-up tty does (a timed-out `read -k` takes its whole timeout, `EPOCHREALTIME` from `zsh/datetime` tells them apart): a shell that is not the session leader — under a task runner such as `mise run` — never gets the SIGHUP, and the loop spun at 20% CPU on the dead tty, stty forks and all. Checking `[[ -t 0 ]]` or `stty size` does not catch it; both still succeed.
- JPEG pictures are decoded by mozjpeg compiled to WebAssembly (`src/jpeg.ts`, `@jsquash/jpeg`), which the bundle carries inside itself: `src/embed.ts` is a Bun macro that reads the `.wasm` at transpile time and inlines it deflated and base64-encoded, so `src/` runs under bun (the tests, `bun src/bin.ts`) and the bundle under node, but `src/` does not run under plain node. The decoder does not read arithmetic-coded JPEGs (it throws `not a JPEG image this decoder can read`), and it leaves EXIF orientation alone (a cut-out's mask has the raster's own size).
- `bin/` is generated by `mise run bin:build`, never committed. The bundle ships a linked source map without `sourcesContent` (`bin/ttheme.js.map`, copied beside the installed CLI): `TTHEME_DEBUG=1` makes `bin.ts` relaunch node with `--enable-source-maps`, and the CLI prints the error's stack in `src/` lines instead of its message alone.
