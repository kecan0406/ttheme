# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check + node-bundle check (exactly what CI runs)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build)
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust]] [--zshenv FILE] [--empty | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing `browse`). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `ZDOTDIR` scrubbed). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run site:dev` / `mise run site:build` — the showcase site; not part of ci, and `next build` is where site/ gets typechecked (root `tsc` only covers `src/`)
- `mise run release <x.y.z>` — the only way to release: runs ci, `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`, which runs ci again, publishes to npm through trusted publishing (OIDC, with provenance — no token exists, so nothing is ever published from a machine) and cuts the GitHub release with the per-terminal archives and the commit subjects since the last tag as notes
- `bun install` for dependencies

## Conventions

- First-party code carries **no comments** — a deliberate choice; do not add any. `ghostty/shaders/*.glsl` is third-party (MIT) and keeps its headers.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/*.toml` is the single source of truth; `dist/` is generated, never committed. `[font]` and `[ghostty]` sections inherit from `themes/_defaults.toml`.
- Series metadata lives once, in `themes/_groups.toml`: every `meta.group` needs a `[[group]]` table there, which owns the `native` title and names the `lead` palette whose signature colors the group. A theme file never repeats them.
- `meta.booru` is the character's booru tag and the only thing ttheme knows about finding its art: `preview`'s tab opens `find` (`src/find.ts`, a hidden CLI verb), which searches that tag live on the sites in `SITES` (`src/booru.ts` — safebooru, yande.re, konachan and danbooru through the `safebooru.donmai.us` mirror), each read at the ratings `TTHEME_FIND_RATING` lists — `safe` by default, where the Moebooru ones carry `rating:s` — with the tag groups `TTHEME_FIND_BLOCK` names (nudity, underwear; both by default) dropped, and installs through `src/backdrop.ts`. Never add post ids, image URLs or curated picks to the repo; palettes that are not one character carry no tag.
- A palette keeps every picture installed on it. The one shown is `backgrounds/<palette>.conf` with its figure `<palette>.<hash>.png` and crop `<palette>.<hash>@fill-N.png` — the shell layer reads it, and the bakes it makes carry the same stem — and its conf names it with `# image <site>_<id>`. The hash is of the images' content (`installBackdrop`), because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name; the others sit whole under `backgrounds/shelf/<palette>/<key>/` with the palette name cut off their file names, and a conf without the line is not kept: the next install replaces it, as installs always did. Installing (`retire` in `src/backdrop.ts`) shelves the shown picture, `ttheme image <palette> next|prev|drop` (hidden verb, `src/images.ts`; preview's tune keys `,` `.` `D`) swaps or removes the shown one, and a switch touches its original so `origins` keeps naming the shown picture. Tuning belongs to the picture, not the palette: the shelf holds each picture's whole set — its conf, the figure and the `@fill` crop, the bakes, `.tune.conf` and `.off.conf`, all with the palette name cut off (`belongs`, `src/backdrop.ts`) — so a switch puts a picture back the way it was left and `drop` takes its tuning with it. Preview writes tuning that has not been confirmed to the picture before `,` `.` move off it; installing the same post again still starts from the defaults (`retire` clears them). There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which the ghostty block always includes. Wearing a palette — `ttheme <name>`, preview's enter, `ttheme next`, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: `__tt_precmd` turns focus reporting (mode 1004) on at every prompt, `__tt_preexec` turns it off before each command, and Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd) — so the picture belongs to the tab you are looking at, not to the last tab that switched, and a busy tab catches up at its next prompt. A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is written or reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own.
- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image next|prev|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshProfiles`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`); it never asks for a reload, and with no focus tracking the layer syncs once at shell start instead. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown`, `__tt_bg_saved`, `__tt_bg_aligns` (whether the terminal places a background by its position) and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band `sips` cut first, into a scratch dir `__tt_pv_bg_close` removes).
- `find` never decodes or encodes an image on its own thread: every decode, resize, tint and PNG write goes through `src/render.ts`, one worker for tiles and one for the try view. The worker entry is `import.meta.filename`, which is `src/render.ts` in dev and `bin/ttheme.js` in the bundle, so `src/bin.ts` guards `runCli` behind `isMainThread` and `bin:check` asserts the bundle answers a render message.
- `~/.cache/ttheme/<site>/` keeps what a `find` session paid for — `orig` (the downloaded post), `tile` (the grid thumbnail at the terminal's cell size), `thumb` (the booru preview), `cut` (the Vision cut-out) — plus `probes.json` and `owners.json`. Only the palette-tinted try images are session-temporary. `sweepCache` trims the four image directories to `CACHE_BYTES`, oldest first, when find exits.
- The `@fill` background crop has two shapes (`fillFrame`, `src/backdrop.ts`, shared by `find`'s try screen and install). A figure wide enough keeps the old crop: full alpha-box width, a band of the frame's aspect slid to the anchor. A **transparent** figure too narrow for that band (`0.61 × w/h` of the figure would fall under `KEEP` 55 %) is instead stood in the frame — 55 % of the figure, scaled down and placed at `PLACE` 0.65 of the leftover width with the headroom above — because the area outside a cut-out is transparent and composites to the palette background for free. Both shapes take the same anchored band, and the shrink and the headroom are scaled by how far under the floor the figure falls, so the two meet with no jump at the switch (`w/h ≈ 0.909`) and a wider figure always fills more of the frame; the anchor stops moving the crop once it is high enough to clamp, which is every genuinely narrow figure. An opaque picture (under 3 % transparent) is a wallpaper and is always covered. Never widen the crop box past the image to make room — `resample` clamps out-of-range samples and streaks the edge pixels; the frame blits instead.
- `find` removes an opaque picture's background with the operating system's own segmentation — Vision through `osascript -l JavaScript` (`src/cutout.ts`, macOS 14+), nothing bundled. Measured on six anime pictures, small general models (u2netp, silueta) cut anime badly, the anime one (isnet-anime) is 176 MB, and every in-process runtime is 145–300 MB against a 0.4 MB bundle, so never add an ONNX runtime, model or `rembg` dependency; other systems keep the opaque picture.
- `meta.signature` names three palette slots (`cursor`, `foreground`, `background`, `selection`, `ansi0`-`ansi15`) — the colors that identify the character on a card. They must resolve to three different colors.
- `dist/manifest.json` is the data contract for everything outside the build: `init` and `site/` read it instead of re-parsing `themes/` (site tasks depend on `build`). Every dist artifact goes through an `Emitter` in `src/emit/` — terminals emit per theme, `shell`/`meta` emit shared files.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the block's include never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends): the Ghostty block always routes new tabs through `launch-tab.zsh`, which reads the setting when the tab opens.
- iTerm2 has no config file, so `sync` owns `~/Library/Application Support/iTerm2/DynamicProfiles/ttheme.json` whole: one `ttheme · <palette>` profile per listed palette (`itermProfiles`, `src/emit/iterm2.ts`), rewritten on every add/remove/browse and reloaded by iTerm2 on its own, plus `ttheme · default` (Guid `ttheme-default`), a copy of the startup palette's profile that the user sets as Default once: `ttheme default` rewrites it, and every tab still on it — new ones and ones never painted — follows within about 0.3 s, which is iTerm2's side of Ghostty's `theme =` and reload. Under keep there is no startup palette and no `ttheme · default`. `palettes.zsh` carries the startup palette as `TTHEME_STARTUP`, so a shell that opens on `ttheme · default` knows whose picture it shows. Measured on 3.7.2: iTerm2 reads OSC colors as Display P3 (its `p3` default) and reports an sRGB profile color converted, so the profiles and `.itermcolors` are written in P3 or the shell's OSC 11 palette match fails; and a newly added dynamic profile inherits its parent's light/dark split and then ignores unsuffixed color keys, so every profile sets `Use Separate Colors for Light and Dark Mode` false.
- Every palette must pass the contrast gate (src/contrast.ts). Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.
- `site/` consumes `@base-ui/react` only through `site/components/ui/*`, managed by the shadcn CLI (`site/components.json`, style `base-nova`): add parts with `bunx shadcn@latest add <name>` from `site/`, then adapt them in place — feature components never import `@base-ui/react` directly (biome enforces it). Color tokens use shadcn's vocabulary in a dark-only `:root`. The landing root wears the current palette: its inline style sets the raw slots (`--bg`, `--fg`, `--cu`, `--se`, `--a0`–`--a15`) and the `.wear` class in `globals.css` remaps the shadcn tokens onto them, so every part on the page — ui primitives included — wears that palette.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin and its output is line-prefixed.
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- BSD `pgrep`/`pkill` skip their own ancestors, so from inside a Ghostty tab `pkill ghostty` misses that Ghostty. `__tt_reload` therefore walks up to the Ghostty that owns the shell and signals only it, falling back to `pkill` when the shell sits outside one (tmux); the walk runs once per shell and its answer is kept in `TTHEME_GHOSTTY_PID`, since a shell never outlives or changes its Ghostty.
- `shell/ttheme.zsh` only runs from an installed layer, with `palettes.zsh` beside it — there is no source-from-checkout path. `shell/check.zsh` assembles such a layer in a temp dir.
- The installed layer `zcompile`s the files it sources (`ttheme.zsh`, `palettes.zsh`, the adapters) into `.zwc` beside them at shell start, and zsh's `source` takes a `.zwc` stamped in the same second as a newer source — so whatever rewrites one of those files deletes its `.zwc` (`applyInit`, `sync`).
- Any source file using `import.meta.dirname` to reach the repo root must sit directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` only resolves to the package root when the depth matches.
- `build` needs bun (`Bun.write`, `Bun.TOML.parse`); `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json` and `dist/ghostty/ttheme.conf`, the only dist files the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- `bin/` is generated by `mise run bin:build`, never committed.
- iTerm2 3.7 keeps its sessions alive in `iTermServer` across a quit and saves dynamic profiles into its prefs (`New Bookmarks`), so a test run can come back on an old session or an old profile's values; a dynamic profile without `Dynamic Profile Parent Name` merges into the default profile, which can be itself. Like Ghostty, it starts shells through `login`, which resets `HOME`.
- iTerm2 3.7 shares kitty placement ids across images — a second image placed with `p=1` removes the first one's — so every placement takes its own image's id (preview's layers, find's tiles). It leaves `CSI 16t` unanswered, so cell sizes come from `OSC 1337;ReportCellSize` (points and a scale) first. `SetProfile` raises a permission bar until the user picks Always Allow; any keystroke dismisses it as a denial.
- iTerm2 3.7's Metal renderer flips the `y` of a kitty source rectangle (asking for the top half draws the bottom one; the legacy renderer, which iTerm2 falls back to on battery, does not), and it draws no placement that leaves the grid, relative or not — so there is no way to show part of a picture vertically except cutting it first, which the iterm2 adapter's `__tt_bg_crop` does unless the crop is centered. Its `ED 2`, and `CSI H CSI J` in the alternate screen, push the whole screen into scrollback, kitty placements included, so preview and find clear with `\e[K\e[2H\e[J` and delete images with `a=d,d=A` instead.
- `tests/tui.zsh` unsets the terminal-identity variables (`GHOSTTY_RESOURCES_DIR`, `KITTY_WINDOW_ID`, …) before each capture: its tmux server inherits the environment of whatever terminal runs it, so without that the ghostty adapter loads locally but not on CI and the screens diverge.
- `bunx shadcn@latest add` can emit `import { cn } from "cn"` and add the unrelated `cn` npm package to site/package.json — point the import at `@/lib/utils` and `bun remove cn`.
- The shadcn parts carry `dark:` variants and `<html>` always has `.dark`, so a plain `hover:`/`data-*:` override loses to them on specificity — adapt the part in place or use a plain element.
