# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All dev commands are mise tasks. package.json deliberately has **no scripts** — do not add any; the toolchain (bun 1.3) and tasks live in mise.toml.

- `mise run ci` — lint + typecheck + tests + build + shell check + node-bundle check (exactly what CI runs)
- `mise run build` (or `--only <terminal>`) — regenerate dist/; fails on contrast violations
- `mise run test` / `mise run check` / `mise run lint` / `mise run format`
- `mise run shell:check` — zsh syntax + runtime check of shell/ (depends on build)
- `mise run bin:check` — bundle bin/ttheme.js and smoke-test it under node (help, `init --yes`, idempotency)
- `mise run sandbox [--here | --behind] [--iterm [--legacy] [--trust] | --wezterm | --warp | --terminal-app] [--zshenv FILE] [--empty | palette…]` — try ttheme by hand as a user of this checkout: a throwaway home at `$TMPDIR/ttheme-sandbox`, wiped on every run and kept after exit for inspection, with every catalog palette installed — or only the ones named, or none with `--empty` (the new-user state `init` leaves, for testing `browse`). It opens a separate Ghostty instance on it, the only way to test `keep`, new tabs and config reloads; `--iterm` wires it for iTerm2 instead and opens an iTerm2 on its own settings suite (`-suite ttheme-sandbox`), which never touches the user's iTerm2 preferences or sessions (`--legacy` turns Metal off, `--trust` pre-allows the escape-sequence permission prompts); `--wezterm` starts a separate WezTerm on the sandbox's `wezterm.lua` (`TTHEME_WEZTERM_APP` names a WezTerm.app outside /Applications); `--warp` opens a Warp tab through `~/.warp/launch_configurations/ttheme-sandbox.yaml` (`warp://launch/<name>` matches the YAML's `name`, not its file name) and `--terminal-app` a Terminal.app window through a `.command` file — both run in the user's own app, since neither can be pointed at another home; `--here` drops into a zsh in this tab instead (`HOME` moved; `TTHEME_*`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `ZDOTDIR` scrubbed). `--behind` and `--zshenv` exist for Claude: `--behind` hands focus back once the window exists, `--zshenv` seeds a hook every sandbox shell sources first. Claude drives it through the `sandbox` skill (`.claude/skills/sandbox/`), never bare — a bare run puts a window in front of the user
- `mise run compat [--update] [ghostty iterm2 wezterm warp terminal-app…]` — the terminal compatibility suite: runs `tests/compat/cases.zsh` in each installed terminal through the sandbox (`--behind`), answers its screenshot requests (the window is found by pid and a per-run title, the pixel read by `tests/compat/sample.js`) and compares the results with `tests/compat/expect.tsv`; an expected pass that fails is a regression. Not part of ci — it opens GUI windows. Add a case there before claiming a terminal supports a feature
- `mise run site:dev` / `mise run site:build` — the showcase site; not part of ci, and `next build` is where site/ gets typechecked (root `tsc` only covers `src/`)
- `mise run release <x.y.z>` — the only way to release: runs ci, `npm version` makes the `Bump version to x.y.z` commit and its `v` tag, and pushing the tag runs `.github/workflows/release.yml`, which runs ci again, publishes to npm through trusted publishing (OIDC, with provenance — no token exists, so nothing is ever published from a machine) and cuts the GitHub release with the per-terminal archives and the commit subjects since the last tag as notes
- `bun install` for dependencies

## Conventions

- First-party code carries **no comments** — a deliberate choice; do not add any.
- No backwards-compat shims, deprecated aliases, or legacy fallbacks.
- `themes/*.toml` is the single source of truth; `dist/` is generated, never committed.
- ttheme writes colors only — no font, font size, codepoint map or shader in any terminal, since a theme tool that sets those overrides the user's own (Ghostty loads a `config-file` after the whole file, so its keys win wherever the include sits). A Ghostty theme file also carries the dock-icon colors, which `theme =` loads before the user's config, so the user's own keys still win.
- A user's config is edited only through `editUserFile` (`src/edits.ts`): a copy to `<file>.ttheme.bak` before the first edit (never overwritten), then a temp file renamed over the symlink's target, so a dotfiles link survives. A key the user sets outside the block stays theirs (`userSets`, `src/wiring.ts`): the Ghostty block drops `command` (and with it `shell-integration`) when the config has its own, and the kitty block drops `window_logo_scale`/`window_logo_alpha` the same way; `launch-tab.zsh` execs `$SHELL`, not `/bin/zsh`. Every file ttheme adds to a terminal's own folders, and every scheme name there (WezTerm, Windows Terminal, `.itermcolors`), is `owned(<palette>)` = `ttheme-<palette>`, which is also how `uninstall` finds them. init lists every file it will edit and the keys its block sets (`wiringPlan`), notes what the user's config overrides (`wiringNotes` — an Alacritty config's own `[colors]` win over its import), and refuses to run without a TTY unless given `--yes`.
- `uninstall` (`src/uninstall.ts`, a setup verb run through npx like init) lists and then reverses everything: each block comes out (`removeBlock`, `removeLuaBlock`; a config ttheme created is deleted), Warp's theme comes back from `warp.base`, iTerm2's default from `itermBase`, and the `ttheme-*` files, `~/.config/ttheme`, the cache and state dirs, the dynamic profile and the WT fragment go. A config equal to its backup loses the backup; one edited since keeps it. An open shell whose `~/.config/ttheme` is gone drops out at its next prompt (`__tt_gone`, from `__tt_fresh`): reload, reset, focus reporting off, hooks and the `ttheme` function removed.
- Series metadata lives once, in `themes/_groups.toml`: every `meta.group` needs a `[[group]]` table there, which owns the `native` title and names the `lead` palette whose signature colors the group. A theme file never repeats them.
- `meta.booru` is the character's danbooru tag and, with `[meta.booru_sites]` for the sites that name the character otherwise (one tag, a list find ORs with `~` — moebooru only, since danbooru counts tags — or `[]` for a site that has none and is not asked; found by md5 and checked by the palette skill's `names.ts` and `tags.ts`), the only thing ttheme knows about finding its art: `preview`'s tab opens `find` (`src/find.ts`, a hidden CLI verb), which searches that tag live on the sites in `SITES` (`src/booru.ts` — danbooru, konachan through its safe-only `konachan.net`, and yande.re), each read at the ratings `TTHEME_FIND_RATING` lists — `safe` by default, asked for in the query (`rating:s` on Moebooru, `rating:g,…` on danbooru, which does not count it against its two-tag limit) — with the tag groups `TTHEME_FIND_BLOCK` names (nudity, underwear; both by default) dropped, and installs through `src/backdrop.ts`. What makes a good backdrop is judged from the tags each post carries — a konachan or yande.re post also borrows the tags danbooru holds for the same file, one `md5:` list per page (`fetchLent`, `src/booru.ts`), never a request per post — so `TTHEME_FIND_SOLO` drops a post only when it knows its headcount (`Post.solo`, danbooru's own or borrowed). The default `fit` order ranks each fetched page (`src/fit.ts`) in two steps — every post by its tags, then as many as the next screens need by their preview's palette colors too — and appends it; the queue is looked at only as far as the next screens (`ahead`) and reordered only while still off screen, so tiles never move under the cursor and no preview is fetched for a page nobody scrolls to. A session keeps every page it fetched, so switching tabs or between `fit` and `newest` asks nothing. Kin is settled when a post arrives, never by where it lands on screen (`src/works.ts`): the same file (md5, pixiv page) keeps the larger copy; a set (one uploader, one size, in a row as the site lists it), a parent's family, a source citing another post or file, or a preview dHash within 2 bits at the same ratio folds into the tile already shown. Measured: a 64-bit dHash of the previews cannot tell an expression variant from a re-encode, so a near shape only folds, never drops, and a konachan crop of a yande.re post differs in ratio, so only its source links it. danbooru.donmai.us is blocked by hostname on some networks (Korea): a search cut off with `ECONNRESET` offers the unblock proxy (`src/unblock.ts`), and `y` writes `TTHEME_FIND_UNBLOCK=1` to `config.zsh` and relaunches find through it — only the sites marked `tunneled` (danbooru) ride it, the rest are named in `NO_PROXY` as `host,.host` (node matches subdomains only on the dotted form), since the split handshake drops about one yande.re request in twenty; preview re-reads the `TTHEME_FIND_*` settings after find returns. Never add post ids, image URLs or curated picks to the repo; palettes that are not one character carry no tag.
- A palette keeps every picture installed on it. The one shown is `backgrounds/<palette>.conf` with its figure `<palette>.<hash>.png` and crop `<palette>.<hash>@fill-N.png` — the shell layer reads it, and the bakes it makes carry the same stem — and its conf names it with `# image <site>_<id>`. The hash is of the images' content (`installBackdrop`), because both terminals reload a background only when its path changes (Ghostty compares the `background-image` path, iTerm2 the profile, and its image cache keys on the path), so two pictures must never share a file name; the others sit whole under `backgrounds/shelf/<palette>/<key>/` with the palette name cut off their file names, and a conf without the line is not kept: the next install replaces it, as installs always did. Installing (`retire` in `src/backdrop.ts`) shelves the shown picture, `ttheme image <palette> next|prev|drop` (hidden verb, `src/images.ts`; preview's tune keys `,` `.` `D`) swaps or removes the shown one, and a switch touches its original so `origins` keeps naming the shown picture. Tuning belongs to the picture, not the palette: the shelf holds each picture's whole set — its conf, the figure and the `@fill` crop, the bakes, `.tune.conf` and `.off.conf`, all with the palette name cut off (`belongs`, `src/backdrop.ts`) — so a switch puts a picture back the way it was left and `drop` takes its tuning with it. Preview writes tuning that has not been confirmed to the picture before `,` `.` move off it; installing the same post again still starts from the defaults (`retire` clears them). There is no rotation and no per-tab picture: Ghostty's `background-image` is one app-wide setting and no escape sequence or script reaches a single surface, and kitty placements scroll with the text, so one picture is up at a time — the one `backgrounds/shown.conf` names in its single `config-file = ?<palette>.conf` line, which the ghostty block always includes. Wearing a palette — `ttheme use <name>`, preview's enter, `ttheme next`, `ttheme default`, a directory pin — points that line at it through `__tt_shown` (ghostty adapter) and reloads Ghostty, and the same sync runs whenever a tab takes focus: `__tt_precmd` turns focus reporting (mode 1004) on at every prompt, `__tt_preexec` turns it off before each command, and Ghostty's `\e[I` lands on the `__tt_focus` ZLE widget (`__tt_bind_focus`, bound in emacs, viins and vicmd) — so the picture belongs to the tab you are looking at, not to the last tab that switched, and a busy tab catches up at its next prompt. A palette with no conf shows none, a tab whose colors are not a palette leaves the picture alone, and nothing is written or reloaded when neither the old nor the new palette has one — which is also why a rotating new tab and shell startup need no call of their own.
- iTerm2 shows a picture per tab, through the palette's profile rather than a config include: `sync` reads `backgrounds/<palette>.conf` with its `.tune.conf` and `.off.conf` (`readBackdrop`, `src/backdrop.ts`) into that profile's `Background Image Location`, `Blend` (the opacity — 0 hides the picture) and `Background Image Mode` (cover 2, contain 3; iTerm2 has no position, so preview bakes a tuned picture that is not centered at the window's size and covers it — `__tt_bg_aligns`), and writes `""` for a palette without one, because a dynamic profile keeps a key its file drops. Whatever changes a picture — find's install, `ttheme image next|prev|drop`, and preview's saved tuning through `ttheme image <palette> tuned` — rewrites `ttheme.json` (`refreshProfiles`), and iTerm2 reloads it into every tab on that profile. The iterm2 adapter's `__tt_shown` sends `OSC 1337;SetProfile=ttheme · <palette>` when the old or the new palette has a picture and keeps the answer in `TTHEME_ITERM_SHOWN` (seeded from `ITERM_PROFILE`, and `default` while the tab is still on `ttheme · default`, read through `TTHEME_STARTUP` so it follows a default changed elsewhere); it never asks for a reload, and with no focus tracking the layer syncs once at shell start instead. The preview and tuning code both adapters share lives in `shell/adapters/_bg.zsh`; an adapter supplies `__tt_bg_cells` (the cell size, and Ghostty's relative-placement margins), `__tt_bg_shown` and `__tt_bg_crop` (how a picture reaches the screen cropped: Ghostty through the kitty source rectangle, iTerm2 through a band `sips` cut first, into a scratch dir `__tt_pv_bg_close` removes).
- One setup can wire Ghostty and iTerm2 together, and a change made from either reaches both. `palettes.zsh` carries the wired terminals as `TTHEME_TERMINALS`; preview's saved pictures go through `__tt_bg_saved` (`_bg.zsh`), which rewrites `ttheme.json` when iTerm2 is wired and reloads Ghostty when `shown.conf` names one of them; `ttheme default` and a catalog change that moves the startup palette (`__tt_catalog`) reload Ghostty too. `__tt_reload` (`ttheme.zsh`) does nothing unless Ghostty is wired. Tuning is written for every wired terminal: with iTerm2 wired, a picture that is not centered is baked at the window size even when it is tuned in Ghostty (`__tt_bg_aligns`), since iTerm2 cannot place one.
- WezTerm, Windows Terminal and Warp are wired by `sync` too, each through the one file ttheme may own there. WezTerm's config is Lua, so `sync` writes `~/.config/ttheme/wezterm.lua` (`weztermModule`, `src/emit/wezterm.ts`: the startup `color_scheme`, the colors dir, and a picture handler) and keeps a `-- ttheme begin`/`-- ttheme end` block that `dofile`s it just before the user config's last `return config` (`upsertLuaBlock`; `~/.wezterm.lua` wins over `$XDG_CONFIG_HOME/wezterm/wezterm.lua`, as in WezTerm) — a config with no such line is left alone and init says so; WezTerm reloads the module on its own because it watches it. Its OSC palette is per pane but a `background` is per window: the shell's `__tt_shown` (wezterm adapter) sets the pane's `ttheme_shown` user var, and the module's `user-var-changed` and `update-status` handlers put the active pane's picture on its window through `set_config_overrides`, reading `backgrounds/<palette>.conf` with its `.tune`/`.off` includes itself, so nothing reloads when a picture changes elsewhere; preview's hover sends the same var. Windows Terminal reads fragments but watches only `settings.json`: `sync` writes `%LOCALAPPDATA%/Microsoft/Windows Terminal/Fragments/ttheme/ttheme.json` (every scheme, plus an `updates` of the profile init ran in — `WT_PROFILE_ID`, else `defaultProfile` — wearing the startup palette) and then touches every `settings.json` it finds so the terminal reloads; init resolves `%LOCALAPPDATA%` (from WSL through `cmd.exe` and `wslpath`) and keeps it as `wtHome` in `installed.json`. A settings reload makes Windows Terminal reset every OSC color in every pane (`Terminal::UpdateColorScheme`, read in its source, not measured), so `sync` touches `settings.json` only when the fragment changed, the windows-terminal adapter's `__tt_reloaded` repaints the tab whenever `palettes.zsh` moves (every `sync` rewrites it), and the adapter binds focus reporting as Ghostty does, so a tab repaints at its next prompt or focus. Warp gets `~/.warp/themes/ttheme-<palette>.yaml` (`warpThemes` — the released Warp reads no subfolder there) and, when its `settings.toml` exists (a feature-flagged build), the startup palette as the `theme` key of `[appearance.themes]` (`withWarpTheme`, `src/wiring.ts`) — Warp edits that file with `toml_edit`, so every other line survives; the value it replaces is kept in `~/.config/ttheme/warp.base` and written back while ttheme is off (`ttheme off`, `off` in `installed.json`) or no palette is installed, or `"dark"` (Warp's default) when there was none, because Warp does not reset a key that disappears. Warp reloads the settings at once but its theme list asynchronously, so a theme file created in the same sync is not known yet and the setting silently falls back to the default and stays there: when the startup palette's file is new, `sync` hands the settings write to a detached process that makes it 1.5 s later if the file is still unchanged (`WARP_LATER`). It paints one theme app-wide, and it answers OSC color queries but never paints the background an OSC sets (measured by `mise run compat`), so the zsh layer treats `TERM_PROGRAM=WarpTerminal` as inactive and `ttheme use <palette>` there points at Warp's settings instead of half-painting. Terminal.app (`TERM_PROGRAM=Apple_Terminal`) takes every OSC color but ignores the OSC resets, so its adapter reads the 20 colors once at shell start (`__tt_terminal_base`, one batched query) and `__tt_osc_reset` puts them back.
- kitty is wired through a watcher `sync` writes to `~/.config/ttheme/kitty.py` (`kittyWatcher`, `src/emit/kitty.ts`), loaded by the kitty block (`watcher`, plus `window_logo_scale 100` and `window_logo_alpha 1` unless kitty.conf sets them itself). The kitty adapter talks to it through user vars (`__tt_kitty_var`): `ttheme_worn` on every paint and reset (the `__tt_worn` hook in `_osc.zsh`), `ttheme_shown` from `__tt_shown`, and `ttheme_startup` from `__tt_reloaded` after `palettes.zsh` moves. A window's picture is its logo, read from `backgrounds/<palette>.conf` with its includes and re-read on focus; kitty 0.49 draws logos at the global alpha and scale only (`draw_window_logo`), so the watcher fades the PNG's alpha to the opacity itself (`load_png_data`/`png_from_32bit_rgba_data`, about 0.3 s for a 1880×1008 picture, cached). kitty's `auto_reload_config` (on by default) reloads when `kitty.conf` or any file it includes changes, and a reload resets every OSC color (measured): the watcher wraps `boss.load_config_file` and puts each window's `ttheme_worn` palette back right after it, and `ttheme_startup` patches the configured colors (`patch_colors(…, True, ())`, which leaves open windows alone) for a kitty whose auto reload is off. Preview and find reuse `_bg.zsh`: kitty draws below-background placements above the logo, so preview's layers cover it; the adapter places them absolutely (no relative placements, no margins). `sync` writes a file only when its content changed, so an add or remove that leaves kitty's files alone reloads nothing.
- Alacritty takes its startup palette through `general.import`: `upsertAlacrittyImport` (`src/wiring.ts`) appends a `[general]` block to a config without that table, or puts the import line inside the config's own `[general]` (TOML defines a table once), and leaves a config that already imports there or defines `general` otherwise alone — init notes it. Alacritty live-reloads the config and its imports and keeps OSC colors through a reload (measured).
- `find` also takes the user's own pictures (`src/attach.ts`). It turns bracketed paste on and reads every paste as file paths or links (`pastedRefs`: backslash escapes, quotes, one per line, `file://` URIs, a raw path with spaces), a burst of typed path-like text as a paste (Warp types a drop instead of pasting it), an empty paste, `ctrl+v`/`alt+v` (anywhere, the search field included) or `v` as a request to read the OS clipboard (`readClipboard`: JXA on macOS, powershell from WSL, wl-paste or xclip — a picture is tried on, a path or link attached, other text goes into the search field, as Claude Code's image paste falls back to text), a focus-in (find turns focus reporting on) as a cue to look at the clipboard's types and say `picture on the clipboard · ctrl+v uses it` for 8 s (`peekClipboard`, once per macOS `changeCount`), and — when the terminal answers the probe `run()` sends after the cell size (DECRQM 5522, `OSC 72;t=q`, then DA1) — kitty's clipboard protocol (paste events with a one-time password, `CSI ? 5522 h`) and drag-and-drop protocol (`OSC 72`, kitty and iTerm2 3.7), which hand over the picture's bytes (`Grabber`). A picture becomes a post of the pseudo-site `LOCAL` (id from its content hash, below `KEY_SPAN`; `postKey` puts sites outside `SITES` after them), placed in the cache as its own original and preview, and opens in try exactly like a jumped-to post (`single`), so cut-out, try-on and install are the booru path's. Only PNG and JPEG under `MAX_PIXELS` decode; `normalize` sends anything else through `sips` on macOS. A paste while find asks a question, installs or shows a panel is dropped.
- `find` never decodes or encodes an image on its own thread: every decode, resize, tint and PNG write goes through `src/render.ts`, one worker for tiles and one for the try view. The worker entry is `import.meta.filename`, which is `src/render.ts` in dev and `bin/ttheme.js` in the bundle, so `src/bin.ts` guards `runCli` behind `isMainThread` and `bin:check` asserts the bundle answers a render message.
- `~/.cache/ttheme/<site>/` keeps what a `find` session paid for — `orig` (the downloaded post), `tile` (the grid thumbnail at the terminal's cell size), `thumb` (the booru preview — danbooru's 360 px variant, since a tile is wider than its 180 px one; preview and tile files carry a hash of the preview URL), `cut` (the Vision cut-out) — plus `probes.json` and `owners.json`. Only the palette-tinted try images are session-temporary. `sweepCache` trims the four image directories to `CACHE_BYTES`, oldest first, when find exits.
- The `@fill` background (`fillFrame`, `src/backdrop.ts`, shared by `find`'s try screen and install) is made at the shape of the window find ran in (`fillSize`, at most 2560 wide) and placed `top-right`, so a window of another shape later loses its bottom and left, never the head. A figure whose alpha box is at least `STANDS` 12 % transparent stands in it whole from the top — 4 % headroom, 3 % from the right edge, as tall as the larger of 115 % of the window and the height that makes it 40 % of the window wide (so a full body shows its upper half), shrunk to 95 % of the width when wider — which is what the owner's hand tuning converged on (107–128 %, center-right, head kept). Anything less transparent is a wallpaper and covers the window from its top, centred across. The numbers are `PLACEMENT`, which `dist/manifest.json` carries as `placement` beside each palette's `backdrop` tint (`backdropTone`), so the site's backdrop mode (`site/lib/backdrop.ts`, tinting a visitor's own picture in the browser — the site ships no art) draws what ttheme installs. `N` in `@fill-N` is the height of the figure at the window's middle, the focus preview's sizes above 100 % zoom around. Never widen the crop box past the image to make room — `resample` clamps out-of-range samples and streaks the edge pixels; the frame blits instead.
- `find` removes an opaque picture's background with the operating system's own segmentation — Vision through `osascript -l JavaScript` (`src/cutout.ts`, macOS 14+), nothing bundled. Measured on six anime pictures, small general models (u2netp, silueta) cut anime badly, the anime one (isnet-anime) is 176 MB, and every in-process runtime is 145–300 MB against a 0.4 MB bundle, so never add an ONNX runtime, model or `rembg` dependency; other systems keep the opaque picture.
- `meta.signature` names three palette slots (`cursor`, `foreground`, `background`, `selection`, `ansi0`-`ansi15`) — the colors that identify the character on a card. They must resolve to three different colors.
- `dist/manifest.json` is the data contract for everything outside the build: `init` and `site/` read it instead of re-parsing `themes/` (site tasks depend on `build`). Every dist artifact goes through an `Emitter` in `src/emit/` — terminals emit per theme, `shell`/`meta` emit shared files.
- Every setting has one owner. `~/.config/ttheme/installed.json` owns the install state (terminals, palettes, the startup palette) and `sync` derives the terminal config blocks from it — the zsh layer never edits those blocks itself; preview's keep goes through `ttheme default`, otherwise the next add/remove/update/browse would rewrite it. `backgrounds/shown.conf` owns which picture Ghostty shows, and only the shell layer moves it — the block's include never names a palette, so the startup palette and the picture are free of each other. `config.zsh` owns the runtime settings (`TTHEME_TAB_PALETTE` and friends), each default spelled out on a commented line and only a value that differs from it left live (`settingLine`, `__tt_config_line`), so a default a later version changes reaches every setup that never touched it: the Ghostty block routes new tabs through `launch-tab.zsh` (unless the user's config sets its own `command`, and then the layer rotates at shell start), which reads the setting when the tab opens, and open shells keep theirs until they restart. `palettes.zsh` does not wait: every open shell re-reads it at its next prompt once its modification time moves (`__tt_fresh`, nanoseconds through `zstat -F %s.%N` — whole seconds miss two writes in one second), so a palette added or a default changed in one tab reaches every other tab, in any terminal.
- iTerm2 has no config file, so `sync` owns `~/Library/Application Support/iTerm2/DynamicProfiles/ttheme.json` whole: one `ttheme · <palette>` profile per listed palette (`itermProfiles`, `src/emit/iterm2.ts`), rewritten on every add/remove/browse and reloaded by iTerm2 on its own, plus `ttheme · default` (Guid `ttheme-default`), a copy of the startup palette's profile: `ttheme default` rewrites it, and every tab still on it — new ones and ones never painted — follows within about 0.3 s, which is iTerm2's side of Ghostty's `theme =` and reload. It is also iTerm2's default profile, so a new tab or window is created wearing it and never switches after it opens — a shell that moved a new tab onto it would flash the old profile first, which is never acceptable. `init` and `ttheme default`, and an add, remove or browse that makes a startup palette appear or vanish (never any other, so a default the user picked in iTerm2 stays), point `Default Bookmark Guid` at it through `defaults` (`pointItermDefault`, `src/palettes.ts`) and write the profile they replace to `installed.json` as `itermBase`, which every ttheme profile names as its `Dynamic Profile Parent GUID` so fonts, keys and the rest keep coming from the user's own profile; `ttheme off` or removing the last palette gives `itermBase` back. A running iTerm2 takes the new default only at its next start — the notes say so. While off, or with no palette installed, there is no startup palette and no `ttheme · default`; `ttheme on` and `ttheme default` turn it back on, and init's "pick a default palette in ttheme preview?" answered no installs off. `TTHEME_ITERM_SUITE` names the preferences domain (`com.googlecode.iterm2` by default); the sandbox sets it to its own suite so nothing reaches the user's iTerm2. `palettes.zsh` carries the startup palette as `TTHEME_STARTUP`, so a shell that opens on `ttheme · default` knows whose picture it shows. Measured on 3.7.2: iTerm2 reads OSC colors as Display P3 (its `p3` default) and reports an sRGB profile color converted, so the profiles and `.itermcolors` are written in P3 or the shell's OSC 11 palette match fails; and a newly added dynamic profile inherits its parent's light/dark split and then ignores unsuffixed color keys, so every profile sets `Use Separate Colors for Light and Dark Mode` false.
- `src/verbs.ts` is the one list of commands: the CLI's parser and help read it (`cli.ts` adds the runs), and `palettes.zsh` carries its tab and catalog sections (`TTHEME_VERBS`, `TTHEME_VERB_ARGS`, `TTHEME_VERB_ABOUT`, `TTHEME_SHELL_VERBS`) for the shell's help, completion and argument checks. A palette is never a command — `ttheme use <palette>` paints a tab. `palettes.zsh` also names the `config.zsh` settings (`TTHEME_SETTINGS`, from `CONFIG_SETTINGS`), and `__tt_cli` hands every one that is set to the CLI, since `config.zsh` assigns without exporting.
- Every palette must pass the contrast gate (src/contrast.ts), which checks readability (WCAG ratios) and function (OKLCH: each accent's hue inside its ANSI role's band, a bright within 25° of its normal, no two accents that read as one color; ANSI slots in `meta.signature` and their twins are exempt from the band). Opting out needs `[contrast] waive = [...]` **plus** a `reason` — a waiver without a reason fails the test suite.
- `site/` consumes `@base-ui/react` only through `site/components/ui/*`, managed by the shadcn CLI (`site/components.json`, style `base-nova`): add parts with `bunx shadcn@latest add <name>` from `site/`, then adapt them in place — feature components never import `@base-ui/react` directly (biome enforces it). Color tokens use shadcn's vocabulary in a dark-only `:root`. The landing root wears the current palette: its inline style sets the raw slots (`--bg`, `--fg`, `--cu`, `--se`, `--a0`–`--a15`) and the `.wear` class in `globals.css` remaps the shadcn tokens onto them, so every part on the page — ui primitives included — wears that palette.

## Gotchas

- mise.toml task scripts are rendered as tera templates: zsh's `${#VAR}` reads as a tera comment opener. Wrap such scripts in `{% raw %}` / `{% endraw %}`.
- A mise task that hands the terminal to a TUI or a shell needs `interactive = true`; without it a task with `depends` gets no TTY on stdin and its output is line-prefixed.
- `init` copies the CLI bundle next to the shell layer (`~/.config/ttheme/ttheme.js`) and the layer only ever runs that copy, so both always come from one package version, offline. Installing from a checkout therefore needs `mise run bin:build` first — `init` refuses without `bin/ttheme.js`.
- Ghostty on macOS starts shells through `login -flp`, which resets `HOME` but keeps the rest of the environment — steer a Ghostty-launched shell with `ZDOTDIR`/`XDG_*`, never `HOME`. `open` hands the caller's environment to the app, so exporting before `open` is enough; `--env` only adds to it. It also reads `~/Library/Application Support/com.mitchellh.ghostty/config`, so a second instance needs `--config-default-files=false`. It creates its first window only once the app is active, so `open -g` leaves a windowless instance.
- Ghostty applies a SIGUSR2 reload asynchronously, an OSC reset returns a surface to the defaults Ghostty holds at that moment, and a reload does not repaint a surface's current colors (measured) — so a reset sent right after the config changes brings back the old `theme =`. `ttheme off` therefore writes everything first, reloads once, and `__tt_reset_reloaded` (ghostty adapter) resets again every 50 ms while the tab still shows the palette's background, for at most a second. Every other open tab turns itself off too (`__tt_off_here`) at its next prompt or focus, when `__tt_fresh` sees `TTHEME_STARTUP` go empty; `ttheme on` wears the default only in the tab that ran it, and new tabs.
- BSD `pgrep`/`pkill` skip their own ancestors, so from inside a Ghostty tab `pkill ghostty` misses that Ghostty. `__tt_reload` therefore walks up to the Ghostty that owns the shell and signals only it, falling back to `pkill` when the shell sits outside one (tmux, or another terminal such as iTerm2 changing a picture Ghostty shows); the walk runs once per shell and its answer is kept in `TTHEME_GHOSTTY_PID`, since a shell never outlives or changes its Ghostty.
- `shell/ttheme.zsh` only runs from an installed layer, with `palettes.zsh` beside it — there is no source-from-checkout path. `shell/check.zsh` assembles such a layer in a temp dir.
- The installed layer `zcompile`s the files it sources (`ttheme.zsh`, `palettes.zsh`, the adapters) into `.zwc` beside them at shell start, and zsh's `source` takes a `.zwc` stamped in the same second as a newer source — so whatever rewrites one of those files deletes its `.zwc` (`applyInit`, `sync`).
- Any source file using `import.meta.dirname` to reach the repo root must sit directly under `src/` — the npm bundle lives at `bin/ttheme.js`, so `join(import.meta.dirname, '..')` only resolves to the package root when the depth matches.
- `build` needs bun (`Bun.write`, `Bun.TOML.parse`); `init` must stay runnable under plain node — the published package ships the prebuilt `dist/manifest.json`, the only dist file the CLI reads (the per-terminal trees go out through the release archives), and bin:check installs from the `npm pack` tarball, the same one the release workflow publishes, so a new runtime read of `dist/` fails there.
- `bin/` is generated by `mise run bin:build`, never committed. The bundle ships a linked source map without `sourcesContent` (`bin/ttheme.js.map`, copied beside the installed CLI): `TTHEME_DEBUG=1` makes `bin.ts` relaunch node with `--enable-source-maps`, and the CLI prints the error's stack in `src/` lines instead of its message alone.
- iTerm2 3.7 keeps its sessions alive in `iTermServer` across a quit and saves dynamic profiles into its prefs (`New Bookmarks`), so a test run can come back on an old session or an old profile's values; a dynamic profile without `Dynamic Profile Parent Name` merges into the default profile, which can be itself. Like Ghostty, it starts shells through `login`, which resets `HOME`.
- iTerm2 3.7 shares kitty placement ids across images — a second image placed with `p=1` removes the first one's — so every placement takes its own image's id (preview's layers, find's tiles). It leaves `CSI 16t` unanswered, so cell sizes come from `OSC 1337;ReportCellSize` (points and a scale) first. `SetProfile` raises a permission bar until the user picks Always Allow; any keystroke dismisses it as a denial.
- iTerm2 3.7 keeps its default profile in memory: it reads `Default Bookmark Guid` at launch (and then adopts a dynamic profile it names), and writes its in-memory value back whenever that profile is replaced — a dynamic default is replaced on every dynamic-profile reload, so while the default is dynamic an outside write is undone within a second. No AppleScript command, escape sequence or dynamic-profile key sets the default (it strips `Default Bookmark`, issue 4115), a dynamic profile whose Guid a regular profile has is refused, and the Python API that can is off until the user enables it. A child profile's `Keyboard Map` replaces its parent's whole, so ttheme sets no key bindings.
- iTerm2 3.7's Metal renderer flips the `y` of a kitty source rectangle (asking for the top half draws the bottom one; the legacy renderer, which iTerm2 falls back to on battery, does not), and it draws no placement that leaves the grid, relative or not — so there is no way to show part of a picture vertically except cutting it first, which the iterm2 adapter's `__tt_bg_crop` does unless the crop is centered. Its `ED 2`, and `CSI H CSI J` in the alternate screen, push the whole screen into scrollback, kitty placements included, so preview and find clear with `\e[K\e[2H\e[J` and delete images with `a=d,d=A` instead.
- tmux keeps an OSC 11 as the pane's own background and then paints every cell with an explicit `48;2;…` (`input_osc_11` → `tty_default_colours`), and Ghostty draws an explicit cell background opaque over `background-image` (and iTerm2's) — so inside tmux the layer never tells tmux its colors: `__tt_tmux` (once, at shell start) turns the pane's `allow-passthrough` on when it is off and the server's `focus-events` on, and sets `TTHEME_TMUX` unless the client is control mode (`tmux -CC`, where iTerm2 reads the pane's raw output itself); then `__tt_out` wraps every color OSC and iTerm2's `SetProfile` in `\ePtmux;…\e\\` for the outer terminal, as tinted-shell does. The colors therefore belong to the terminal tab, not the pane: a pane re-wears its palette when tmux reports focus (`__tt_rewear`), the tab's current bg is kept in the session option `@ttheme_bg` (tmux answers OSC 11 from a bg it cached at attach, so `__tt_query_bg` reads the option first) and iTerm2's shown profile in `@ttheme_shown`, a pane ignores the `TTHEME_SPEC` inherited from the tmux server's environment, a shell outside tmux re-wears itself at the prompt after a `tmux` command (`__tt_mux`/`__tt_unmux`) — one that wears no palette sends iTerm2 an empty `SetProfile`, which iTerm2 reads as its default profile (`screenSetProfileToProfileNamed`), so the tab looks like a new one (`__tt_unshown`) — and `__tt_reload` walks up from the tmux client (`#{client_pid}`) instead of the shell. tmux answers `CSI 16t` but turns a kitty APC into the pane title (`input_exit_apc`, `allow-set-title`), so preview skips its picture layers, tuning and find inside tmux (`__tt_pv_bg_open` leaves `bgcw` 0).
- Alacritty's parser (vte) keeps at most 16 OSC parameters and drops an OSC 4 whose count then comes out even, so a palette in one OSC 4 never reached Alacritty's ANSI colors: every OSC 4 carries one color (`__tt_osc_apply`, `paletteOsc`).
- kitty on macOS draws nothing while its window is occluded or the screen is locked (`windowDidChangeOcclusionState`), and `get_window_logo_settings_if_not_default` reads a logo only once it has been drawn — so a kitty screenshot needs the window in front on an unlocked screen, while OSC queries and user vars work either way. `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked` tells.
- `tests/tui.zsh` unsets the terminal-identity variables (`GHOSTTY_RESOURCES_DIR`, `KITTY_WINDOW_ID`, …) before each capture: its tmux server inherits the environment of whatever terminal runs it, so without that the ghostty adapter loads locally but not on CI and the screens diverge.
- `bunx shadcn@latest add` can emit `import { cn } from "cn"` and add the unrelated `cn` npm package to site/package.json — point the import at `@/lib/utils` and `bun remove cn`.
- The shadcn parts carry `dark:` variants and `<html>` always has `.dark`, so a plain `hover:`/`data-*:` override loses to them on specificity — adapt the part in place or use a plain element.
